## 一、真正有技术深度的四块

按"这件事难在哪、有没有现成轮子"排，不按"好不好看"排：

### ① 记忆层 + 冲突归因（技术含量最高）

**难在哪**（不是"存个 JSON"）：
- **事实抽取**：从对话/笔记里抽实体与断言，而不是存整段文本
- **冲突消解**：同一事实出现两个版本，谁赢？
- **时效有效性**：事实带有效期，旧的自动失效（Zep 的核心卖点）
- **上下文压缩**：记忆不能无限膨胀，什么时候合并、什么时候淘汰
- **可解释**：为什么系统记住了 A 而忘了 B

这是 Mem0 / Zep / Letta 正在打的仗，**几乎没有现成轮子可以直接抄进本地应用**。

### ② 库内 Deep Research（多跳检索）

**难在哪**：
- 查询分解（一个问题拆成几个子查询）
- 迭代检索（第二轮查询依赖第一轮结果）
- 跨文档融合与去重
- **证据归属**：最终报告的每一句要能指回具体片段
- 停止条件（什么时候算查够了）

这不是"调一次大模型"，是一个真实的 agent loop。

### ③ 联网补充 + 证据归因

**难在哪**：不在"能联网"（接个搜索 API 而已），在
- **来源分层**：哪句来自你的笔记、哪句来自网络
- **冲突处理**：网上说的和你笔记里写的矛盾，怎么呈现？
- **权威性判定**：多个网络来源互相矛盾怎么办

### ④ 浏览器内本地检索（为 Demo，见下节）

**难在哪**：WASM / WebGPU 上跑 embedding + 向量检索，让"数据不出机器"这件事**在浏览器里也能成立**。

## 二、一个关键发现：① 和 ③ 是同一个技术内核

**它们其实是同一个问题**：

> **当同一件事有多个互相冲突的说法时，如何归因、判定时效、并按来源分层。**

| | 记忆层 | 联网补充 |
|---|---|---|
| 冲突来源 | 你上周说的 vs 这周说的 | 你笔记里的 vs 网上搜到的 |
| 要判定什么 | 哪个更新、哪个更可信 | 哪个是权威、哪个是噪音 |
| 输出要求 | 可解释 | 可溯源 |

**这意味着：把它们合成一个模块做，技术深度翻倍，而不是做成两个浅功能。**

而且这里有一个**大厂没做的角度**：NotebookLM 不联网，所以它从不需要处理"我的笔记 vs 网络事实"的冲突；Zep/Mem0 处理的是对话事实，不处理"个人知识库 vs 公开网络"。**你的场景（个人笔记 ↔ 网络）恰好是空白。**

这是我认为整个四条里**最值得当成技术主线**的一块。

## 三、在线 Demo：一个必须先解开的矛盾

**矛盾**：你的核心卖点是"全本地、数据不出机器"。把 Demo 部署到云上，等于自己打自己脸。

**三档方案（我按性价比排）**

| 方案 | 做法 | 成本 | 能证明什么 |
|---|---|---|---|
| **A. 受限在线 Demo** | 云上跑，**预置示例语料**，访客不能上传自己的笔记 | **低**（1–2 天） | 能看效果，但**证明不了"本地"** |
| **B. 便携免安装包** | 一键下载即用（免装），降低摩擦 | 低 | 本地真实性，但不是"在线" |
| **C. 浏览器内本地检索** | 语料**不上传**，用 WebGPU/WASM 在浏览器里做 embedding + 向量检索；生成走用户自带的 key | **高** | **同时证明"能在线体验"和"数据不出机器"** |

**我的建议：A + C 组合**

- **A 先做**：1–2 天把 Demo 立起来（用示例语料，明确标注"真实使用是全本地"）。马上有东西能点。
- **C 作为技术实验长期推进**：这才是"打磨技术"该干的事——**它把 Demo 这个需求变成了一个技术亮点**，而不是妥协。
  - 现实起点：BM25 在 JS 里是纯逻辑，先做；embedding 用 `transformers.js` / ONNX Runtime Web + WebGPU；生成环节让用户填自己的 API key（或走受限代理）
  - **即使 C 只做到"检索在浏览器里、生成在云端"，也已经能理直气壮地说"你的笔记没有离开浏览器"**——这一句比任何功能都有说服力

**C 的诚实评估**：这不是小工程。WebGPU 在小语料上可行，语料一大就要上分片和索引压缩。**建议先做 100–500 篇的中等语料 Demo，别一上来对标全量。**
*（置信：估算｜WebGPU 浏览器内 RAG 的可行区间基于常见做法推断，未实测；建议先做一个最小 POC 验证 500 篇量级的检索延迟）*

## 四、建议路线（每阶段都要有可验证产出）

| 阶段 | 做什么 | 产出的"可验证结果" |
|---|---|---|
| **P0** | 受限在线 Demo（方案 A） | 一个能打开的链接 |
| **P1** | **证据归因内核**（记忆层 + 联网分层合并做）— 先做"来源分层 + 时效判定"，不急着做全自动抽取 | 一组冲突样本上的判定准确率（**你自己的评测集，不是感觉**） |
| **P2** | 库内 Deep Research（多跳） | 检索跳数与最终答案质量的对照曲线 |
| **P3** | 浏览器内本地检索（方案 C） | 中等语料下的检索延迟与召回数字 |
| **P4** | 边缘项（信息图 → PPTX → 闪卡） | 只有前面都稳了才碰 |

**纪律（沿用）：每完成一块，立刻写进 README + 一篇 `docs/学习记录/`**——你的学习记录已经编到 33 篇，这是你的资产，别断。

## 五、风险

1. **P1 是深水区**：事实抽取 + 冲突消解是研究级问题，很容易陷进去出不来。**对策：先做"来源分层 + 时效判定"这两个可验证的子问题，别一上来做全自动记忆。**
2. **P3 容易失控**：浏览器内跑模型是工程量黑洞。**对策：定死语料上限（比如 500 篇），先验证延迟，再谈优化。**
3. **最大风险仍是摊子**：四个阶段如果并行，会全部做一半。**串行做，一个 P 完了再下一个。**
4. **别丢掉王牌**：评测集是你唯一别人没有的东西。P1/P2/P3 **每一个都要配一组能跑出数字的评测**，否则这轮"打磨技术"就变成了"堆功能"。
