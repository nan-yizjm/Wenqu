## 2. 架构地图

### 2.1 产品请求路径

```
资料层  导入 Markdown/PDF/Notebook  →  product/materials.py
   ↓ 标题感知切分（片段上限 800 字符）
索引层  按版本隔离的索引 + 每版独立向量缓存  →  product/materials.py  _publish_snapshot
   ↓
检索层  BM25 ／ E5 向量 ／ RRF 融合（rrf_k=60）  →  product/materials.py:788 + hybrid_retrieve.py
   ↓ 候选 → （可选 CrossEncoder 重排）
证据层  证据打包 + 能力边界守卫  →  evidence_context.py + query_guard.py
   ↓
生成层  Ollama NDJSON 真流式 ／ DeepSeek SSE  →  product/chat.py
   ↓
应用层  React SPA（问答·资料库·收藏） + SQLite  →  product/app.py + web/src
```

### 2.2 关键结论：产品只复用了 5 个底层模块

产品后端（`src/product/`）实际 import 的实验线模块只有：

`llm.py`、`query_guard.py`、`vector_retrieve.py`、`bm25.py`、`hybrid_retrieve.py`

**没有被产品使用的整条实验编排线**：`answer.py`(27KB)、`index_store.py`、`serve.py`(29KB)、`runtime.py`、`chat.py`(CLI REPL)、`context.py`、`evidence_context.py`、`citations.py`。

产品在 `product/retrieval_model.py` + `product/chat.py` 里**另写了一套 RAG 编排**（`RAGAnswerer` 未被复用）。

- 好处：改实验线不会波及产品，两条线互不干扰。
- 代价：同一件事（切分、索引、检索编排、上下文打包）长期存在两个版本，`serve.py` 与 `product/app.py` 的接口契约已经分叉（`/v1/answer` vs `/api/v1/conversations/{id}/messages/stream`；`/health/ready` vs `/api/v1/health`），且容器镜像装的是 `serve.py` 那套、桌面产品是另一套 —— 两套后端口径不同，容易互相误导。

### 7.2 锁竞争的复现（把推断变成实测）

用一个"慢编码器"替换真实 E5（其余走产品原装链路，`material_run_inline=False`），分别在不建索引与正在建索引两种状态下上传同一个文件，测量导入作业的状态变化。

结果：

| 场景 | HTTP 响应 | 作业等待（pending 时长） | 作业总耗时 | 结果 |
|---|---:|---:|---:|---|
| `bm25`（无索引构建） | 0.033 s | 0.058 s | 0.092 s | completed，两份文档均 ready |
| `hybrid`（构建中，模拟 4 s） | 0.033 s | **4.043 s** | 4.102 s | completed，两份文档均 ready |

两点结论：
1. 作业等待时间**精确等于**索引构建持锁的时间 —— 竞争真实存在，且机制就是 `_write_lock` 串行。
2. 两次的 HTTP 响应都是 0.033 秒 —— **接口本身没有被阻塞**，被排队的只有后台作业。这印证了 §4 对子 Agent 说法的修正。
