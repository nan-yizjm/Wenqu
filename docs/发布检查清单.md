# 发布检查清单

升版时要逐处核对的引用点与验收步骤。**这份清单存在的直接原因**：下面前 7 处此前只记在仓库外的计划文件（`.workbuddy/plans/`）里，克隆仓库的人看不到，升版时容易漏改。

## 一、版本引用点（8 处，逐处核对）

| # | 位置 | 当前内容 | 要改什么 |
| --- | --- | --- | --- |
| 1 | `src/product/__init__.py:4` | `PRODUCT_VERSION = "0.2.1"` | 常量值 |
| 2 | `src/product/resources.py:13` | `BUNDLED_DOCS` 内含 `"RELEASE_NOTES_0.2.1.md"` | 随包发布说明的文件名 |
| 3 | `product.spec:11` | `docs/RELEASE_NOTES_0.2.1.md` → `resources/docs` | 打进包的发布说明路径 |
| 4 | `installer/ObsidianRAG.iss:2` | `#define MyAppVersion "0.2.1"` | 版本号（第 15 行 `OutputBaseFilename` 由它派生） |
| 5 | `scripts/build_product.ps1:45` | `dist-installer\ObsidianRAG-Setup-0.2.1-win-x64.exe` | 产物校验路径 |
| 6 | `scripts/test_installer.ps1:2` | 同上（默认参数值） | 安装验收的默认包路径 |
| 7 | `docs/RELEASE_NOTES_0.2.x.md` | 现有 `_0.2.0` / `_0.2.1` | **新建**本版发布说明（文件名本身也是引用点） |
| 8 | `docs/用户指南.md:5` | "运行 `ObsidianRAG-Setup-0.2.1-win-x64.exe`" | **最容易漏的一处**：正文里写死的安装包名，不进任何构建脚本，只有人读得到 |

## 二、顺序

1. 改 1–8（第 7 项是新建文件）
2. 跑离线测试 + `npm --prefix web run build` + `scripts/check_css_tokens.ps1`
3. 把本版变更写进新的 `RELEASE_NOTES`
4. 打包：`scripts/build_product.ps1`（缺 Inno Setup 时至少产出 onedir 包，用 `-SkipInstaller`）
5. 校验产物：包内前端资源哈希与 `web/dist/assets` 一致；`dist-installer/*.sha256` 自验通过
6. 安装验收：`scripts/test_installer.ps1`（静默安装 → 随包资源文件名精确比对 → 导入示例 → 建索引 → 搜索命中 → 覆盖升级后数据保留 → 卸载后用户数据保留）
7. 对跑起来的交付版跑一遍 `node scripts/ui_acceptance.cjs [端口]`（真实点击 + 断言 + 截图，默认 15 项）

## 三、打包时已知的坑（都踩过）

- **先停掉正在运行的 `ObsidianRAG.exe`**。旧包目录被运行中的进程占用时，`mv` 会报 Permission denied，构建会卡在第一步。
- **不要直接删 `dist/ObsidianRAG`**。`PyInstaller --clean` 的 COLLECT 会先 `rmtree` 它（5000+ 文件），**触发批量删除保护**，构建以非零码失败。正确做法是把旧包**改名留下**，让 COLLECT 去建一个新目录，全程无需删除。
- **前端改过就必须先构建再打包**：`npm --prefix web run build` → 打 PyInstaller → 核对包内哈希：
  `find dist/ObsidianRAG -path "*web/dist/assets*" -name "index-*"`
  两边哈希不一致说明打的还是旧前端。
- **`build/` 可以随时删**，下次打包自动重建（但会多花几分钟）。留着它不影响产物正确性。
- **发布说明与用户指南是随包分发的**，改它们等于改交付物内容，别只在仓库里改完就以为完事——要重新打包才会进安装包。
