# 产品检索质量评测（首次）

日期：2026-09-16
目的：产品此前**没有任何检索质量评测集**，所以"混合检索要不要当默认"缺一把尺子。本次补上工具并在真实语料上跑出第一组数据。
配套工具：`src/evaluate_product_retrieval.py`（新增，未提交）
产物：`data/generated/product_retrieval_eval_*.json`（被 Git 忽略）

> 重要：本次结论与"语料构成"强相关，与检索模式的关系反而次要。请先读 §4。

## 1. 为什么另起一个入口

实验线已有 dev 30 题 / holdout 12 题，但 `src/evaluate.py` 跑的是 `src/serve.py` 那套编排。产品走的是另一条路（`product/materials.py` 的快照 + 按版向量索引 + `product/retrieval_model.py`），两者不共用检索编排，所以实验线的数字**量不到产品**。

新入口只测检索、不调生成模型：把每题送进产品自己的 `GET /api/v1/search`，返回片段按文档去重排序，与评测集的 `expected_source_files` 比对，算 Source Recall@1/@5/@8 与 MRR。检索层答不对的问题，生成层谈不上答对。

### 语料 A：完整目录（101 篇，含 Notebook 与 PDF）

## 4. 最重要的发现：语料构成与检索模式量级相当，且方向相反

把两组语料横向一比，结论就反过来了（严格口径，dev 26 题；1 道题 = 3.85pt）：

| 对比 | dev R@1（bm25） | dev R@1（hybrid） |
|---|---:|---:|
| 仅 56 篇 Markdown | 69.2% | 84.6% |
| 加上 44 个 Notebook + 1 个 PDF | **57.7%**（−11.5pt = 3 题） | **61.5%**（−23.1pt = 6 题） |

**入库 44 个 Notebook 和 1 个 PDF，让 BM25 的 dev R@1 掉了 11.5 个百分点（3 题）、混合检索掉了 23.1 个百分点（6 题），dev R@5 首次跌破 100%（100% → 96.2%）。**

> **原文此处写"这个影响比开不开混合检索大得多"，量级对不上，已更正。** 开混合检索在 56 篇语料上是 **+15.4pt（4 题）**、在 101 篇上是 **+3.8pt（1 题）**。拿最大的一对来比：语料效应 6 题 vs 模式效应 4 题，是"略大"，不是"大得多"；而在 BM25 这一列，语料效应（3 题）反而**小于**模式效应（4 题）。准确的说法是：**换语料、换检索模式，两者的影响量级相当，只是方向相反**——加 Notebook 把 R@1 往下推，开 hybrid 把它往上推。
>
> 另一个限定（§11 给出）：语料效应的绝对值**依赖判对口径**。严格口径下 bm25 是 −11.5pt、hybrid 是 −23.1pt；换宽松口径后两者都收敛到 **−7.7pt（2 题）**。所以"Notebook 代价"里，hybrid 那 6 题有 4 题、bm25 那 3 题有 1 题是"换人答对但 ground truth 不认"，不是检索失败。

失分归因（逐题看 Top-5 位置的来源类型）：

- 40 个 Top-5 位置里 **12 个是 `.ipynb`、1 个是 `.pdf`**，其余 27 个是 `.md`；
- 「大模型技术总览.md」反复抢占第一名（retrieval-003/004/014/015/016/018/021/022 的 Top-3 里都有它）——这正是 `README.md` 里 E01 记录过的"总览页/MOC 抢占第一名"现象。

> **§11 修正了上面这条的判断**：用期望关键词核对后，总览页每次抢到第一名时**都完整覆盖了该题期望关键词**（5/5、4/4、4/4、6/6），它是**合法答案**，只是不如特定笔记具体。所以它不是"检索没解决的问题"，而是"ground truth 偏好特定笔记"的口径问题。请以 §11 为准。
- 典型例子：`retrieval-002` 问 PagedAttention，期望 `06_推理与模型服务/推理与模型服务.md`，实际被 `01_硬件与算力/Triton 算子开发/09_Triton_PagedAttention.ipynb` 挤出前 8。

### 但对这条结论要加两个限定

1. **评测口径本身偏 `.md`。** 30 + 12 题的 `expected_source_files` 全部指向 `.md`，Notebook 命中**永远不算对**。所以"下降"里有评测集造成的成分：语料扩容改变了可检索空间，而 ground truth 没有跟着更新。
2. **它同时说明 Notebook 索引的价值无法被现有评测集衡量。** 换句话说，这不是"Notebook 功能做错了"，而是"加了新资料类型，尺子没跟上"。

正确的下一步取决于想回答哪个问题：若关心"记笔记查得到吗"，应把 Notebook 排除或独立成库；若关心"Notebook 也是资料"，则应扩充 ground truth 并接受检索难度上升。

## 5. 对"混合检索要不要默认开"的回答

> **本节结论依赖口径。** 下面两段用的是**严格口径**（只认权威笔记）。换成宽松口径（认任何能答的文档）后，bm25 在两种语料上都反超 —— 见 §11。口径未定之前，本节只应读作"严格口径下的答案"。

**在纯笔记语料上，可以开，且是净收益**：严格口径下 dev R@1 +15.4pt（69.2% → 84.6%）、MRR +0.084，改善 5 退化 1；holdout 一次退化都没有。

**在含 Notebook 的完整语料上，收益不稳定**：dev 小幅正向（+3.8pt），holdout 反向（62.5% → 50.0%）。

所以这件事的前置条件不是"混合检索准备好了吗"（它早就准备好了），而是**"用哪把尺子判答对"**——它决定 hybrid 是赢还是输；在此之上才是"索引里放哪些资料"。

## 6. 局限（别把这张表当定论）

- **holdout 只有 8 道内域题**，一道题的翻转就是 12.5 个百分点。它的作用是"不退化"的守门，不足以支撑"更准"的结论。
- 单机、单次运行，未做多轮方差；E5 编码有浮点非确定性，但排名影响通常小于一题的分辨率。
- 产品路径没有重排选项，因此本评测**未包含 CrossEncoder 重排**——实验线记录过重排有约 70–80ms 附加耗时且未证明总通过率提升，产品当前的选择是一致的。
- 与项目文档记录的 BM25 dev R@1 = 80.8% / MRR 0.879（实验线，`docs/学习记录/04`）不可直接比较：切分方式不同（产品片段上限 800 字符）、chunk 语料不同、去重口径不同。**该差距已在 §9 追查完毕，结论是那组文档数字本身已不可复现。**

## 8. 建议的下一步（按性价比排序）

1. ~~先决定 Notebook 与 PDF 要不要进默认索引。~~ **这一条已按 §11 下调。** 原文说它"比检索模式影响大一个量级"（见 §4 更正：实为量级相当、方向相反），且 §10 证明重排救不回来。但 §11 换尺子后显示，语料效应的绝对值本身依赖判对口径。所以**真正的第 0 步是定口径**（认特定笔记 vs 认任何能答的文档），定了之后才能说 Notebook 该不该进索引、hybrid 该不该默认开。
2. **扩充评测集的 ground truth**，让 Notebook 也能成为正确答案，否则新资料类型的价值永远测不出来。**这是第 1 步的另一种解法**：与其二选一，不如把 ground truth 补成"认所有能答的文档"，那时宽松口径就变成了正式口径。
3. **混合检索默认开**，重排保持关闭 —— 但**仅在严格口径下成立**。§10 实测：干净语料上 best 条件就是 hybrid 单开（dev R@1 84.6%），叠加重排反而降到 76.9%。§11 补充：宽松口径下 bm25 在两种语料上都反超。
4. **修 `retrieval-019`**（模型路由与级联）这道在两组语料、两种模式下都退化的题。**注意 `retrieval-007` 与 `retrieval-019` 的期望来源是同一份 `07_应用系统/应用系统.md`**，先查这份文档是不是有共同的结构性问题。
5. **修 `src/evaluate.py` 的语料写死**（见 §9）：它硬编码指向旧语料，导致实验线的主检索基线无法在当前语料上重跑。

## 9. 追查：产品路径与文档基线的差距

§6 留了一个未解问题：产品路径在纯 md 语料上是 R@1 69.2%，而文档记录的实验线是 80.8%。用实验线**自己的工具、自己的语料、同参数**（`--method bm25 --eval-file eval_set.json --top-k 5`）重跑，结果：

| 指标 | 文档记录（README E02/E03） | 本次实测 | 产品路径（§3 语料 B） |
|---|---:|---:|---:|
| Source Recall@5 | 100.0% | **92.3%** | 100.0% |
| Source Recall@1 | 80.8% | **76.9%** | 69.2% |
| MRR | 0.879 | **0.840** | 0.833 |
| OOD 拒答率 | 100.0% | 100.0% | 不适用（守卫不在检索层） |

**结论一：文档记录的那组基线已经不可复现。** 这不是产品的问题，实验线自己的入口也跑不出 100% / 80.8% / 0.879。本次失败的 2 题是 `retrieval-007`（Skills/Memory/Context Engineering 三者分工）与 `retrieval-018`（RAG 完整流程），都属于多概念比较题——失败**模式**和文档描述一致，但文档声称 dev 集 R@5 是 100%。

**原因很可能在这里**：`src/evaluate.py` 把语料路径写死成 `data/generated/chunks.json`（该文件现为 757 片段、2026-09-12 重建），而文档说当前语料是 `token_v1`（822 片段）。也就是说，这个"主检索基线"入口指向的是一份**早于 token 感知切分的旧语料**，它既不是 E02 记录时的那份，也不是文档声称的当前那份。中间没有任何一次基线复跑把它记录下来。

**结论二：我上轮"产品明显低于实验线"的担忧要撤回一半。** 同口径比下来：

- R@1：产品 69.2% vs 实验线 76.9%，差 7.7 个百分点；
- MRR：0.833 vs 0.840，基本持平；
- R@5：产品 **100%** 反而高于实验线的 92.3%。

即两条路径是**取舍不同**，不是产品退化。产品切分更细（56 篇 → 980 片段，实验线 757），R@5 更好、R@1 略差，这与"片段越细、正确文档越容易被同名片段内竞争压后"的直觉一致——但**这一点我没有直接证据，属于待验证假设，不要当结论用**。

### 顺带实测：产品切片的 token 截断

我曾怀疑 commit `40e82ce`（"cap chunks at 800 chars so e5 stops truncating them"）只是自我安慰，因为 800 个汉字看着远超 512 个 token。用真实 tokenizer 按 `vector_retrieve` 的调用方式数了一遍，**假设被否掉**：

| 切片来源 | 片段数 | 超 512 token | 最大 token |
|---|---:|---:|---:|
| 产品切片器（800 字符上限） | 980 | **6（0.6%）** | 551 |
| 实验线 `token_v1`（token 感知） | 822 | 0 | 480 |
| 实验线旧 `chunks.json` | 757 | **70（9.2%）** | 816 |

该 tokenizer 下中文约 0.55 token/字符（产品片段中位 226 token），所以 800 字符 ≈ 440 token，上限是有效的。

这个测量同时**复现了文档里"E5 超限由 70 降为 0"（阶段 06）这个数字**——旧语料 70 个、token_v1 0 个，完全吻合。

### 但由此暴露一个真实的小缺口

实验线把截断视为**硬失败**：

```python
# src/index_store.py:227
if vector.truncated_chunk_count:
    raise ValueError("构建后的片段超过模型 token 上限，拒绝发布")
```

产品侧 `src/product/materials.py:402-416` 构建同一个 `VectorIndex` 时**没有这个检查**，`truncated_chunk_count` 算了、写进了 npz，但没有任何地方读它（`grep truncated src/product/` 无结果）。所以产品会带着 6 个截断片段正常发布索引。

严重度 **P3**：量级很小（0.6%，最多丢 39 个 token），不影响可用性。但它是"实验线立过的不变量在产品线丢了"，和 §5 那批问题同类——写进缺陷清单比留在代码里好。

## 10. 重排能挽回 Notebook 造成的损失吗？——不能，而且更差

§4 的结论是"Notebook 入库让 dev R@1 掉 11.5～23 个百分点"，而"排除 Notebook"是个产品决策。那么在决定之前，应该先问：**能不能用重排把丢掉的名次抢回来？** 产品目前没有重排开关，但重排器就在本机缓存里，可以直接测。

做法：在同一批候选（`/api/v1/search` 上限 20 条，与项目 `rerank_top_n=20` 的既有约定一致）上加一次本地 CrossEncoder（`cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`，固定 revision，CPU，离线）重排，再算同一套指标。

### 纯笔记语料（56 篇 md）

| 条件 | dev R@1 | dev MRR | holdout R@1 | holdout MRR |
|---|---:|---:|---:|---:|
| bm25 | 69.2% | 0.833 | 75.0% | 0.854 |
| bm25 + rerank | 76.9% | 0.872 | 87.5% | 0.917 |
| **hybrid** | **84.6%** | **0.917** | 75.0% | 0.875 |
| hybrid + rerank | 76.9% | 0.872 | 87.5% | 0.917 |

### 完整语料（101 篇）

| 条件 | dev R@1 | dev R@5 | dev MRR | holdout R@1 | holdout MRR |
|---|---:|---:|---:|---:|---:|
| bm25 | 57.7% | 96.2% | 0.713 | 62.5% | 0.792 |
| bm25 + rerank | **53.8%** | **92.3%** | 0.718 | 75.0% | 0.854 |
| hybrid | 61.5% | 96.2% | 0.766 | 50.0% | 0.750 |
| hybrid + rerank | **53.8%** | **92.3%** | 0.712 | 75.0% | 0.854 |

### 结论有三条

**一、重排不但没能挽回 Notebook 造成的损失，在 dev 上还把结果压得更低。** 完整语料下两种模式的 R@1 都掉到 53.8%，而且 **R@5 从 96.2% 掉到 92.3%** —— 重排不只是改变了顺序，它把正确文档**挤出了前 5**，这是召回层面的损害，不只是排序问题。

**二、在干净语料上，最好的条件恰恰是 hybrid 单开（dev R@1 84.6%）。** 给 hybrid 叠加重排反而降到 76.9%，和 bm25+rerank 持平 —— 重排的排序主导了最终结果，把混合检索的收益抹掉了。

**三、dev 与 holdout 再次打架，而这次必须听 dev。** 完整语料下 dev 说重排有害（57.7→53.8、61.5→53.8），holdout 说有益（62.5→75.0、50.0→75.0）。**holdout 只有 8 题，一道题就是 12.5 个百分点**，75% 与 62.5% 的差别只有一道题。26 题的 dev 集给出的是方向一致、幅度明确的负面结论，应该采信它。

### 这对项目既有决定的意义

`rag.toml:14` 写着 `rerank = false`，注释理由是"重排已有首版，但上一阶段没有证明生成总通过率更高"。**这个决定是对的，本次给出了比原来更硬的依据**：在产品实际使用的检索路径上，重排会降低 dev R@1 与 R@5。

### 一个顺带发现：重排没法做成服务外面的一层

`materials.search()` 会主动剥掉片段正文（`materials.py:813-814`），`/api/v1/search` 只返回 360 字的 `preview`。所以任何基于 HTTP 接口的"外挂重排"都拿不到完整片段，只能拿到预览——本次评测是从 SQLite 按 `chunk_id` 取回正文才做的。若将来要把重排接进产品，它必须落在服务内部（`materials.retrieve` 与结果返回之间），而不是前端或中间层。

### 局限

- 候选池只有 20 条（与项目既有 `rerank_top_n=20` 一致）。更深候选池（如 100 条）可能改变结论，未测。
- 重排器用 `activation_fn=nn.Identity()` 的原始 logit 排序，passage 模板与产品一致（`标题路径：…内容：…`），未做分数归一化——与 `src/reranker.py` 的既有实现方式相同，没有额外失真。
- 单次运行，未做多重随机性方差。

## 11. 抢占第一名的那些文档，是合法答案还是排错了？

§4 把"入库 Notebook 让 dev R@1 掉 11.5～23 个百分点"当作主要问题，但"排除 Notebook"是产品决策。在拍板之前必须先回答一个更基本的问题：**那些抢到第一名的文档，究竟是不是错的？**

### 判据不由我定

评测集自带 `expected_keywords` 字段。用它当客观判据：排第一的文档**全文覆盖了该题全部期望关键词**，就说明它同样能回答这个问题（ground truth 只是没收录它）；一个都没覆盖，才是检索真的排错。

### 逐例分类（完整语料 101 篇）

**dev 集 / BM25（11 例可判）**

### 换一把尺子，代价还剩多少

"宽松口径"= 只要排第一的文档覆盖全部期望关键词就计为正确（不论它是笔记、Notebook、PDF 还是总览页）。

> **本节数字已于同日晚间复核修正。** 原表里 56 篇纯笔记的两格宽松值（bm25 88.5%、hybrid 88.5%）**不可复现**，已改为下表。原因：当初的临时脚本用的是"只看第一名 + 关键词大小写敏感"的判法，在 `Query Head`、`GQA` 这类混大小写关键词上会失配。现在改由 `src/evaluate_product_retrieval.py --rubric both` 统一产出，严格/宽松两套口径一次跑出、可单命令复现。
>
> 定位过程：把新口径施加到旧报告的名次数据上，得到 84.6% / 80.8%，与重新跑一遍的结果完全一致；而旧脚本按自己的判法在旧数据上重跑只得 80.8% / 76.9%，**连它自己报出的 88.5% 都复现不出来**。所以错在判法，不在数据。
>
> 其余各格（101 篇两种模式、两组 holdout）复核后与原文一致。另核对了"产品不回收旧版本片段"是否会污染宽松口径：实测两个评测库里历史版本残留均为 **0**（56 篇 980 片段、101 篇 2014 片段全部属于当前版本），故无需按版本过滤也不会虚高——新实现仍加了 `c.version_id = d.current_version_id` 约束以防将来。

### 三条结论（已按修正后的数字重写）

先把"Notebook 代价"定义清楚：它是 **R@1 从 56 篇纯笔记语料掉到 101 篇完整语料时的落差**。

| 检索模式 | 严格口径代价 | 宽松口径代价 |
|---|---:|---:|
| bm25 | −11.5pt（69.2 → 57.7） | −7.7pt（84.6 → 76.9） |
| hybrid | −23.1pt（84.6 → 61.5） | −7.7pt（80.8 → 73.1） |

**一、BM25 的"Notebook 代价"有一部分也是口径造成的。** 严格 −11.5pt，宽松缩到 −7.7pt，缩掉约三分之一。所以原文"跟口径无关、换尺子也没变"这个说法**不成立**，此处更正。

**二、hybrid 的代价大部分是口径造成的。** 严格 −23.1pt，宽松缩到 −7.7pt，缩掉约三分之二。

**三、换成宽松尺子后，两种检索的 Notebook 代价收敛到同一个数：−7.7pt（2 道题）。** 这是最干净的一条：在"认任何能答的文档"口径下，多入库 44 个 Notebook 对 BM25 和 hybrid 的伤害**完全相同**。严格口径下 hybrid 多承受的那 15.4pt，性质是"Notebook 把权威笔记的第一名抢走了"，而不是"Notebook 让这道题找不到答案了"。换句话说——**Notebook 进索引真正的代价不是"答案消失"，而是"答案换了个人给"，且这个换人效应在 hybrid 下被放大一倍。**

**四、换尺子会整体翻转"混合检索该不该开"。**

| 语料 | 口径 | bm25 | hybrid | 谁赢 |
|---|---|---:|---:|---|
| 56 md | 严格（认特定笔记） | 69.2% | **84.6%** | hybrid 明显赢 |
| 56 md | 宽松（认任何能答的文档） | **84.6%** | 80.8% | **bm25 小赢** |
| 101 篇 | 严格 | 57.7% | **61.5%** | hybrid 小赢 |
| 101 篇 | 宽松 | **76.9%** | 73.1% | **bm25 小赢** |

修正后的结论比原先更干脆：**严格口径下 hybrid 两种语料都赢；宽松口径下 bm25 两种语料都赢，没有平手格。** 也就是说：

> **混合检索的全部价值集中在"把那份权威笔记顶到第一"这一件事上，它从不提高"任何一份能答的文档排到第一"的比例，反而略降。**

对一个以引用为核心的问答产品来说，前者才是有用的（用户点开引用要看到权威笔记），所以严格口径更贴近产品目标——但这必须由产品主人确认，不是我能替他定的。

## 12. 阶段 1 收尾：三个缺陷的根因，与一个被否决的参数改动

### 12.1 `retrieval-005` 的根因在**查询侧**，不在 PDF 上

原假设是"长 PDF 的长度归一化没兜住"。用 `BM25Index.explain_score`（`src/bm25.py:131`）逐 token 拆开后，三条候选假设里**两条被推翻**：

| 假设 | 判定 | 证据 |
|---|---|---|
| a) PDF 抽取出的文本含重复样板，产生偶然命中 | **推翻** | 第 1 名的贡献全部来自真实词频：`injection` 片段内出现 **4** 次（idf 5.17，贡献 8.83）+ `prompt` **4** 次（idf 2.24，贡献 4.16）；标题命中数为 0，无样板成分 |
| b) 命中片段短，`b=0.75` 的长度归一化给了它额外增益 | **推翻** | 该片段 **134 token**，比全库平均 148.7 还长，长度归一化 **0.926**（略吃亏）；反而 `大模型技术总览.md` 的片段只有 97 token、归一化 0.739（更受益） |
| c) `Prompt Injection` 作为整词被保留，PDF 安全章节确实含该词 | **证实** | 该页确实讨论 prompt injection，属**词面命中合法但语言/语境不符** |
| d) `QUERY_STOP_PHRASES` 把"有哪些风险"整句滤掉，查询判别力不足 | **证实，且是主因** | `tokenize_query("Prompt Injection 有哪些风险？")` = `{'prompt', 'injection'}` —— **只剩两个词**；前 5 名命中的 token 全部只有这两个 |

机制：`tokenize_query`（`src/retrieve.py:101`）对停用词做**整串替换**，`"有哪些风险"` 被整体删掉，于是承载提问意图的 **"风险"也跟着消失**。查询退化成"prompt injection"这个纯主题词组，而 BM25 无法区分"提到过这个词的页面"与"讲这个词有什么风险的页面"。

**反事实验证**（同一个 BM25 索引，只改查询 token 集合）：

| 查询 token | 期望文档名次 | 前三名 |
|---|---:|---|
| 现状 `{prompt, injection}` | **4** | Llama3 PDF → 大模型技术总览.md → 应用系统.md |
| 保留被误删的 `风险` | **2** | 大模型技术总览.md → **横切专题_评测安全与治理.md** → Llama3 PDF |
| 再保留 `恶意`（用到 ground truth，仅作上界） | **1** | **横切专题_评测安全与治理.md** → … |

**只要不把"风险"吃掉，期望文档就从第 4 名升到第 2 名，那份 PDF 直接掉出前三。** 这是本次最具体、最可动手的一条发现。但把 `风险` 加回白名单会影响**全部**题目，必须先在 dev 全集、两套口径上验证才谈改默认——属阶段 2，本轮不动。

### 12.2 `retrieval-019`：RRF 的"名次平均主义"，且**调 `rrf_k` 修不好**

BM25 下期望文档的第 1、第 3 名片段都是它自己（文档级名次 1）；但这两个片段在**向量路只排到第 10、第 11**。RRF 只看名次，于是：

| 文档 | bm25 名次 | 向量名次 | 融合分（`rrf_k=60`） |
|---|---:|---:|---:|
| 期望文档（`07_应用系统/应用系统.md`） | 1 | ~10 | 1/61 + 1/70 = 0.0307 |
| `06_推理与模型服务/推理与模型服务.md` | 2 | 4 | 1/62 + 1/64 = 0.0318 |

**"一路第一、一路很差"输给了"两路都中游"。** 根源是 `rrf_k=60` 把名次差压得极扁：第 1 名 1/61=0.01639，第 11 名 1/71=0.01408，**只差 14%**，两路的补偿权重几乎相等。

顺带修正一个此前的猜测：`07_应用系统/应用系统.md` 只有 **12 个片段、平均 390 字**，比全库平均（980/56 = 17.5 片段/篇）**更少更短**，所以"总览文档被切太碎导致稀释"**不成立**，问题在融合而不在切分。

### 12.3 `rrf_k` 扫描：R@1 上去了，但**不能改**（又一个实测负结果）

`fuse_rankings`（`src/hybrid_retrieve.py:33`）只用名次、不用分数，而两路候选都固定是 top-20，报告里又存了每个命中的两路名次——所以**换 `rrf_k` 重算是精确的，不是近似**。可信度校验：离线重算在 `rrf_k=60` 处精确复现了真实运行（101 篇 61.5%/73.1%、MRR 0.766；56 篇 84.6%/80.8%、MRR 0.917）。

| 语料 | 口径 | rrf_k | R@1 | R@5 | R@8 | MRR |
|---|---|---:|---:|---:|---:|---:|
| 101 篇 | 严格 | **2** | **69.2%** | 96.2% | 96.2% | **0.798** |
| 101 篇 | 严格 | 60 | 61.5% | 96.2% | 96.2% | 0.766 |
| 101 篇 | 宽松 | **2** | **76.9%** | **92.3%** ↓ | 96.2% | 0.833 |
| 101 篇 | 宽松 | 60 | 73.1% | 96.2% | 96.2% | 0.830 |
| 56 md | 严格 | 2 / 60 | 84.6% | 100.0% | 100.0% | **0.910 / 0.917** ↓ |
| 56 md | 宽松 | 2 / 60 | 80.8% | 88.5% | 88.5% | **0.833 / 0.846** ↓ |

**判定：不改，维持 `rrf_k=60`。** 它不满足"两套口径都不退化"：

1. **101 篇宽松口径的 R@5 从 96.2% 掉到 92.3%** —— 代价来自 `retrieval-004` 宽松名次 4→6。这是拿"能不能答上"换"答得够不够权威"，与产品目标相反。
2. **56 篇 MRR 从 0.846 掉到 0.833**（严格 0.917→0.910）。
3. R@1 的上涨看着大，但**逐题看是"改善 3 处、退化 4 处"**（101 篇）：只是恰好有 2 道题从第 2 名跨到第 1 名（`retrieval-007`、`014`），同时另外 4 处名次变差。26 题集上 1 题 = 3.85pt，**这个量级不足以支撑改默认**。
4. 两组 holdout 在 `rrf_k=2` 下**完全没有变化**（0 改善 0 退化）——既印证"holdout 分辨率太低"，也说明看不到收益。
5. `retrieval-019` 在 `rrf_k` 从 1 到 200 的全部取值下**都停在第 3 名**，所以原以为"小 `rrf_k` 能救 019"的猜测**被推翻**。

**结论**：`rrf_k` 既不是 `retrieval-019` 的杠杆，也不是一个能换来净收益的旋钮。要修 019 得换思路（例如给"单路夺冠"额外加权、或惩罚"两路都中游"），那属于改算法而不是调参，本轮不做。

## 13. 「候选窗口」是片段数，不是文档数

这一节不是原来计划里的一项，是本轮验收时**顺着 `retrieval-002` 的异常追出来的**，也是本轮最有产品含义的发现。

### 13.1 起因：一道题的 R@5 对不上

真实运行里 101 篇 BM25 的严格 R@5 是 **96.2%**（有一题没进前 5），而我的离线闸门复现出 **100%**。差的正是 `retrieval-002`（PagedAttention）。查下去发现：

```
retrieval-002 的 bm25 候选前 10 名（未去重）：
  rank=1..10  全部是 01_硬件与算力/Triton 算子开发/09_Triton_PagedAttention.ipynb
去重后接口只返回 2 篇文档：该 Notebook + Llama3-2407.21783v3.pdf
```

**一份 Notebook 独吞了整个候选窗口。** 原因是语义上的：`/api/v1/search` 的 `top_k` 和 `candidate_k` 都是**片段数**，而评测与界面把它当"文档数"理解——按文档去重之后，剩下的文档数完全取决于片段有多少来自不同文档。

### 13.2 指标侧：R@8 有近一半的题在构造上不可能满分

`candidate_k` 取满 20 个片段，按文档去重后的文档数分布：

| 语料 | 查询数 | 最小 | 中位 | 最大 | 平均 | 不足 8 篇的查询 |
|---|---:|---:|---:|---:|---:|---:|
| 101 篇 | 84 | 2 | 8 | 17 | 8.7 | **42%** |
| 56 md | 84 | 2 | 8 | 17 | 8.0 | **50%** |

**Source Recall@8 的分子因此被分母限制住**：约一半的查询返回的文档本来就不到 8 篇，"命中前 8"与"出现即命中"没有区别。这也解释了前面所有表里 **R@8 几乎恒等于 R@5** 的现象。

> 口径提示：本文所有 R@8 都在这个约束下取得，**不应单独解释**，也不该用来比较检索模式——它测到的是候选窗口塌缩的程度，而不是检索质量。

### 13.3 产品侧：问答的证据窗口中位只覆盖 3 篇文档

`src/product/chat.py:256` 调的是 `self.materials.retrieve(retrieval_query, top_k=5)` —— 而 `materials.retrieve()`（`materials.py:807-808`）把这个 `top_k` 原样透给 `engine.search`，`_sources()`（`chat.py:160-167`）再**逐片段**建 S1…S5 引用，**不做文档去重、也不按文档配额**。

所以问答真实拿到的证据是"5 个片段"，覆盖几篇文档完全被动：

| 语料 | 集合 | 查询数 | 最小 | 中位 | 最大 | 只来自 1 篇文档 |
|---|---|---:|---:|---:|---:|---:|
| 101 篇 | dev | 60 | 1 | **3** | 5 | 4（7%） |
| 101 篇 | holdout | 24 | 2 | 4 | 5 | 0 |
| 56 md | dev | 60 | 1 | **3** | 5 | 3（5%） |
| 56 md | holdout | 24 | 2 | 4 | 5 | 0 |

也就是说：**标称"多源证据"的问答，中位数只给了 3 篇文档，偶尔只有 1 篇。** `retrieval-002` 恰好是极端例——问答那 5 个片段全部来自同一个 Notebook，而它在严格口径下"没进前 5"其实是因为**唯一被检索到的那篇不是期望的那篇**。

**这属于产品缺陷，不是评测缺陷**，而且和"Notebook 该不该进索引"是不同的问题：即使只收 Markdown，一个片段多、段落长、术语密集的笔记同样会挤占窗口。可选修法（都还没做，需要产品主人定）：按文档去重后再取前 N 篇、或按文档设配额（每篇最多 K 个片段），再让 `top_k` 名副其实。

### 13.4 窗口扫描：扩大窗口是**纯改善**，但收益全在第 5 名之后

弄清机理之后就能精确测了。两条路径的语义完全不同（`src/hybrid_retrieve.py:105-113`）：

```python
if top_k < 1 or self.candidate_k < top_k:
    raise ValueError("要求 1 <= top_k <= candidate_k")
...
count = self.candidate_k
if method != "hybrid":
    count = len(self.chunks)      # BM25 对全库打分，candidate_k 只限返回条数
```

- **BM25**：候选深度就是**全库**，`candidate_k` 只是返回条数的上限。所以 `/api/v1/search` 的 `le=20` 对 BM25 来说**纯粹是输出截断**，放宽它不会改变任何名次。
- **hybrid**：`count = candidate_k`，它同时是**每路召回深度**与返回上限，放宽它会改变送进 RRF 的候选池。

第一段：把 `candidate_k` 抬到 600（对 BM25 不改变名次），扫输出窗口（101 篇，dev 26 题，已含停用词修复）：

| 窗口 | 去重后文档中位 | 严格 R@1 | 严格 R@5 | 严格 R@8 | 严格 MRR | 宽松 R@1 | 宽松 R@5 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 5 | 3 | 57.7% | 88.5% | 88.5% | 0.696 | 80.8% | 88.5% |
| 8 | 4 | 57.7% | 96.2% | 96.2% | 0.722 | 80.8% | 92.3% |
| 20 | 8 | 57.7% | 96.2% | 96.2% | 0.722 | 80.8% | 92.3% |
| 40 | 14 | 57.7% | **100.0%** | **100.0%** | **0.730** | 80.8% | 92.3% |
| 80 / 200 / 600 | 25 / 48 / 74 | 57.7% | 100.0% | 100.0% | 0.730 | 80.8% | 92.3% |

**饱和点在 40 附近**，再往上（到 600）一个数字都不动。第二段：hybrid 改每路召回深度：

| candidate_k | 严格 R@1 | 严格 R@5 | 严格 R@8 | 严格 MRR | 宽松 R@1 |
|---:|---:|---:|---:|---:|---:|
| 10 | 61.5% | 92.3% | 96.2% | 0.762 | 73.1% |
| 20（现状） | 61.5% | 96.2% | 96.2% | 0.766 | 73.1% |
| 40 | 61.5% | 96.2% | **100.0%** | **0.771** | 73.1% |

**两条结论，一条比一条重要。**

**第一，R@1 在任何窗口、任何 `candidate_k` 下都不动**（BM25 恒 57.7%、hybrid 恒 61.5%）。这不是巧合：窗口只决定"尾部还能看到多少"，而 R@1 问的是"第一名对不对"。**所以上面那些 R@1 问题——`retrieval-003`、`019`、`005`——全都不是窗口问题，是排序问题**，靠加宽缓冲一个都修不掉。这条把问题的归属彻底钉死了。

**第二，扩大窗口是"纯改善"，零退化由构造保证。** 逐题核对（dev 26 题 × 两套口径）：

| 加宽 | 改善 | 退化 | 逐题明细 |
|---|---:|---:|---|
| BM25 5 → 8 | 3 | **0** | `retrieval-003` 严格 None→5、`018` 严格 None→2、`018` 宽松 None→2 |
| BM25 8 → 20 | 1 | **0** | `retrieval-004` 宽松 None→8 |
| BM25 20 → 40 | 1 | **0** | `retrieval-002` 严格 None→5 |
| hybrid 5 → 8 | 2 | **0** | `retrieval-003` 严格 None→4、`004` 宽松 None→4 |
| hybrid ck 20 → 40 | 1 | **0** | `retrieval-002` 严格 None→8 |

两组 holdout 在所有加宽下**全部零变化**。

**为什么零退化是必然的**：BM25 的名次在全库打分时就已经定了，窗口只截断尾部——把窗口从 5 加到 8，只可能让原本"根本没出现"的文档出现在第 6～8 位，**不可能把已经在前面的文档推后**。这与 `rrf_k=2` 的形状完全不同（那个是"改善 3、退化 4"，因为它改了融合本身）。**只截尾的旋钮天然单调，这是它的价值，也是它的天花板。**

**所以可动的旋钮有两个，价值差别很大：**

1. **`chat.py:256` 的 `top_k=5`（真正有价值的那一个）。** 提到 8：dev 26 题里**改善 3 处、退化 0**，而且改善的全是"期望文档完全没进证据"的题（`retrieval-003`、`retrieval-018`）——**也就是说当前用 5 个片段时，26 题里有 3 题的期望文档根本不在证据里，模型无法给出正确引用**。代价是多 3 个片段进上下文（每段 ≤800 字符）。
2. **`app.py:424` 的 `le=20`。** 对 BM25 抬到 40 零退化（严格 R@5 96.2%→100%、MRR +0.008，都来自 `retrieval-002` 一题），hybrid 要同时抬 `candidate_k`。但收益全部落在第 8 名之后，**用户几乎感知不到**，holdout 也毫无变化。

**纪律上的判断（先说清楚，避免误读）**：这两个都**满足**项目定的"两套口径都不退化"门槛，但**收益量级不同**——第 1 个补的是"证据里压根没有正确答案"（影响能不能引用），第 2 个补的是"第 8 名以后的排序"（几乎不影响体验）。

**最后一条限制必须写明**：这些都只测了检索，**没有生成侧评测**。"证据多 3 段"不等于"答得更好"——上下文变长同样可能让生成分心。所以 §16 里我把第 1 条列为**待决产品改动**，而不是直接改掉。

### 13.5 顺带修正我自己的一条方法学主张

§12 里我写过"离线闸门精确复现了真实运行，所以换 `rrf_k` 重算是精确的"。**这句话只在 R@1 和 MRR 上成立，R@5 上不成立**——

离线闸门是在**全部 2014 个片段**上排序再去重，真实运行只在**top-20 片段**上去重。候选窗口塌缩只影响后者。实测偏差：

| | 离线闸门 | 真实运行 | 差 |
|---|---:|---:|---:|
| 101 篇 bm25 严格 R@1 | 57.7% | 57.7% | 0 |
| 101 篇 bm25 严格 R@5 | 100.0% | 96.2% | **−3.8pt** |
| 101 篇 bm25 严格 MRR | 0.721 | 0.713 | −0.008 |

**结论：离线闸门只能用来筛选和看增量方向，正式结论必须真实运行确认。** §12 里 `rrf_k=2` 的否决结论不受影响——它靠的是逐题"改善 3 处、退化 4 处"和 56 篇 MRR 下降，这两个结论在真实运行里只会更保守（真实运行的候选窗口更窄）。

## 15. 产品侧补回截断防护：记录，而不是拒绝

实验线对"片段超过模型 token 上限"是**硬失败**（`index_store.py:227` 直接 `raise ValueError("构建后的片段超过模型 token 上限，拒绝发布")`）。产品侧此前完全没有这道检查——`vector_retrieve.py:68` 一直在算 `truncated_chunk_count`，但**产品没有任何地方读它**。

现在按"记录并说明"落地（`src/product/materials.py`）：

- 建索引时读 `index.truncated_chunk_count`，写进任务消息；索引仍然发布，只是把代价说出来。
- `_vector_state()` 在 `ready` 时上报 `truncated_chunks`；`off`/`building` 不带这个键——"没有索引"和"索引干净"是两回事，报成 0 会被读成"检查过了，没问题"。
- 设置页在就绪且计数 >0 时把提示语追加出来，并把状态色调从绿转黄。

**为什么不照抄实验线的"拒绝发布"**：向量索引在产品里是**辅助通道**，`retrieve()` 在索引不可用时本来就会退回 BM25（`materials.py:806`）。为它拒绝发布，会把关键词检索一起挡掉——用一个小概率缺陷换一次全功能不可用。而实测超限占比极低：

| 语料 | 片段总数 | 超 512 token | 占比 |
|---|---:|---:|---:|
| 101 篇（含 Notebook/PDF） | 2014 | 8 | 0.40% |
| 56 md（纯笔记） | 980 | 6 | 0.61% |

> **修正一条我此前的记录**：记忆里"980 片段中仅 6 个超限"这个数字属于**56 篇纯笔记语料**，不是完整语料；完整语料是 2014 段 / 8 段。两者都从向量缓存文件的 `truncated_chunk_count` 直接读出，不是推算。

新增回归测试 2 项（`tests/test_product_hybrid.py`）：超限时报出计数且任务不判失败、干净索引明确报 0。离线测试总数 **155 → 158**，全通过。

## 17. 阶段 2 单变量矩阵：八个候选，一个默认值都没改

一次跑完、两套口径同时留下的复现命令（`--sweep` 写法是 `检索方式:参数=值`）：

```
./.venv/Scripts/python.exe -X utf8 -m src.evaluate_product_retrieval \
  --vault "<语料目录>" --data-dir data/generated/product_eval \
  --sweep hybrid:rrf_k=10 hybrid:rrf_k=20 hybrid:rrf_k=100 \
          bm25:b=0.3 bm25:b=0.5 bm25:heading_repeat=0 bm25:heading_repeat=2 \
          bm25:k1=1.2 hybrid:candidate_k=40 \
  --rubric both --output data/generated/sweep_matrix_20260917.json
```

参数名与上下限见 `materials.RETRIEVAL_PARAMETERS`；`b` / `k1` 是短名，落到的设置键是 `bm25_b` / `bm25_k1`。**每条条件开始前都会把五个参数显式写回默认值再打补丁**——否则上一条实验改过的值会留到下一条，单变量会悄悄变成多变量。

### 逐项结论

阈值是「四个格子都不退化」，所以下表没有一个候选达标——**默认值一律不动**：

- **`hybrid`（该不该默认开）**：dev 严格 +3.8pt / MRR +0.044 赢，但 dev 宽松 −7.7pt / −0.040、holdout 严格 −12.5pt / −0.042 都退。又回到同一个结论：它擅长把「权威笔记」顶到第一，不擅长把「任何能答的文档」顶到第一；口径没定之前不翻默认值。
- **`rrf_k`**：dev 严格下 **10 最好**（R@1 65.4%，比 60 的 61.5% 高 3.8pt），dev 宽松下也比 60 好（−3.8pt vs −7.7pt），但 holdout 严格三种取值都是 −12.5pt。三档之间 holdout 完全没差别，说明它调的是融合锐度、不是召回上限。**不改默认，但 rrf_k=10 是最值得留档的候选**。
- **`b`（长度归一化）**：0.3 让 dev 严格 R@5 掉到 88.5%、MRR −0.012；0.5 在 dev 两套口径都是微正，但 holdout 严格 −12.5pt / MRR −0.062。holdout 上 `b` 一动就掉，**维持在 0.75**。
- **`heading_repeat=0`（标题不再额外加权）**：**唯一接近达标的候选**——dev 严格 R@1 持平、MRR +0.008、R@5/R@8 双双升到 100%；holdout 严格与宽松都是持平（+0.0 / +0.000）。唯一的退格是 dev 宽松 R@1 −3.8pt / MRR −0.019。按纪律它仍然不能改默认，**但它是「严格口径下明确更好、宽松口径只掉一题」的那一个**，与口径决定同一件事：如果最终认定「引用为核心、只认权威笔记」，它就该开。
- **`heading_repeat=2`**：dev 双双微正，holdout 严格 −12.5pt。不加权比加两次权重稳。
- **`k1=1.2`**：dev 两套口径都 −0.002 / −0.006 退，holdout 持平。**维持 1.5**。
- **`candidate_k=40`（候选窗口）**：**完全没人动**——先核实它不是空转：30 题的候选片段列表**30/30 全部不同**，说明窗口确实被加宽了，但最终 top-8 一名不差，四个格子 Δ 全为 0。
  ⇒ 阶段 1 遗留的「`/api/v1/search` 把 top_k 限在 20、要不要放开」到这里有了答案：**不用放开**。瓶颈不在候选窗口宽度上。

一句话总结：**八个候选里没有一个是「四个格子全不退化」，所以这一轮不改任何默认值**；两个最值得跟着口径决定一起定的，是 `hybrid` 和 `heading_repeat=0`。
