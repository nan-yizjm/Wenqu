# 41 · 上下文窗口与证据预算：把"静默截断"变成一句签了字的话

日期：2026-09-19。这是 P3 遗留清单里挂了两天的一项：`qwen2.5:7b` 的上下文窗口实测 4096 token，而 Studio 指南的证据要放 12 条片段（最多 12×800 字符 ≈ 6600+ token），问答也要放 8 条——**超窗无防护未测**。

## 一、超窗的真正问题：不是崩，是不说话

排查现状时确认的第一件事：超窗不会报错。Ollama 对超出 `num_ctx` 的输入**静默截断**——不抛异常、不给说明，模型只是"没看到"后半段证据。叠加产品自己的两层字符硬切（问答 `evidence[:9000]`、产出 `evidence[:12000]`），一共**三层静默**：本地硬切一层、Ollama 默认窗口再截一层、哪层都不说话。症状是指南质量变差、引用丢失，而用户查不出原因。

这比崩溃糟：崩溃至少有个错误页。静默退化只有两种下场——被"看起来还行"骗过去，或者被某次较真的人花两小时对照原始片段才能发现。

## 二、修法：签约窗口 + 字节预算 + 一句签字的话

三层决定：

1. **窗口是产品的签约值，不是碰运气。**`default_chat_client` 给 OllamaClient 显式传 `num_ctx=8192`（`OLLAMA_CONTEXT_TOKENS`）。8192 的取舍：让多数证据装得下（本地 7b 的 prefill 与显存代价仍可接受），同时不再依赖"Ollama 模型默认 4096"这种看不见的约定。DeepSeek 窗口大得多（64k+），不走这条预算——按 provider 分流，否则要么本地撑爆、要么把远端的证据也无谓砍掉。

2. **证据按字节预算整条裁，不硬切。**`fit_evidence(results, budget_bytes)`：预算 = `(8192 − 512 系统与主题裕量 − 2048 回答预留) × 2.5 字节/token ≈ 14080 字节`。两个纪律：
   - **整条裁**。字符硬切会让最后一条只剩半段，而 `[S12]` 标签还在——界面上出现一个模型只见过半句的引用就是撒谎。裁掉的是尾部（检索分低的在后），保留编号永远是连续前缀。
   - **至少保留 1 条**，且**按 UTF-8 字节而不是字符算**：同样 1000 个"字符"，英文约 1000 字节、中文约 3000 字节——按字符裁会高估中文可装条数，正好把窗口撑爆。
   - 2.5 字节/token 是**高估**（中文 ≈ 3 字节/字）：宁可少装一条证据，也不要把窗口又撑爆。

3. **裁了必须说出来，而且要能翻旧账。**`evidence_note`（"模型上下文窗口为 8192 token，证据从 12 条减到 6 条；被减掉的条目没有参与生成。"）同时出现在流事件里和落库里（v10 迁移一并加了 `messages.evidence_note` 与 `artifacts.evidence_note`，旧行 NULL——NULL 表示"没有记录或没裁过"，不替历史编结论，口径与 39 号的 `web_state_json` 完全同构）。来源面板、引用编号、`artifact_sources` 落库、`backlink_report` 的标签集合**全部按裁剪后的清单走**：模型没看过的片段不能出现在界面的任何地方。

## 三、测试：6 点短路 + 真模型端到端

| 层 | 数字 | 关键断言 |
| --- | --- | --- |
| Python | **325 项**（原 315，+10） | `fit_evidence` 纯函数（整条裁 / 保底 1 条 / 字节口径）；`num_ctx` 签约；问答流裁剪 + 重放一致 + DeepSeek 不裁；产出流裁剪 + 落库来源一致 |

| 真模型端到端 | **A 段 3 + B 段 7 全过** | 见下 |

真模型端到端（本机 qwen2.5:7b）分了两段，因为防护要同时证明两件相反的事：

- **A 段（真实语料，101 篇）**：主题"上下文工程"召回 12 条，真实笔记的片段比 800 字符上限短得多，总字节在预算内 → **不裁、无 note、正常生成 1773 字符指南**。防护不许误伤正常场景。
- **B 段（空库 + 一篇 20 节长文）**：12 条召回全部来自它，总字节必超预算 → **裁到 6 条、S1–S6 连续、note 如实、落库读回一致、生成完成**。

## 四、端到端抓出来的两个既有事实（不是本次引入，如实记录）

1. **双实例并发抢同一个 Ollama 会撞 120 秒超时**。B 段第一次跑时失败（`ollama_unavailable`，正文写到 235 字符断），当时 8793（真实库）与 8794（空库）两个实例同时挂着，各自生成排队进同一个 Ollama；`OllamaClient` 的读超时 120 秒等不起另一个实例的长生成。单实例独占后重跑即过。这与 P3 遗留 ③"一次生成 7 分钟未返回（未复现）"很可能同源——**并发 + 120 秒读超时**，值得单独修（调 timeout 或加排队提示）。
2. **真实语料的 12 条证据总字节很少超预算**——8192 窗口对真实笔记基本够用。预算真正生效的场景是"满长中文片段"或未来把召回上限调大时。这不是白做：签约窗口消灭的是"Ollama 默认值静默截断"这层不确定性，预算和 note 保证将来任何参数组合下退化都是**可见的**。

## 五、没解决的 / 边界

- **token 折算是估算不是实测**。2.5 字节/token 对 qwen 分词是保守高估，但没有接 tokenizer 精确计数——接了会把 `src/llm.py` 拖进 tokenizer 依赖。预算宁紧勿松，方向是对的。
- **num_ctx 尚未在设置页暴露**。8192 是对所有本地模型一刀切的签约值；换一个上下文更小的本地模型（或者 Ollama 显存不够分配 8192）时，只能改常量。做成设置项要连着"每模型窗口探测"一起做。
- **问答侧的裁剪说明只挂在消息流**（`messages.evidence_note` 落库、重取读回），界面上是来源面板上方一行小字；要不要在"生成中"也给个过渡提示，等朋友试用反馈再定。
- **120 秒读超时与并发生成**的冲突没修（见 §四.1）。
- **历史回答的 evidence_note 与 web_state 一样是 v10 之前的 NULL**——旧行不补话。
