# 39 · 联网状态入库

补 P2 留下的第二个口径缺口：**联网状态只活在一帧流式事件里**。刷新界面、或者只是答完之后那次自动重取，提示就没了——于是"这次没联上"变成"看起来就像今天没什么可网的"。

这一篇的重点是两层判断：**哪些情况该存成"没有记录"而不是"没联网"**，以及**同一件事不能既存在事件里又存在消息上**。

## 一、缺口是什么

`chat.py:_web_results()` 返回 `(来源, 状态)`，状态随 `retrieval` 事件到界面，前端把它存进组件状态（`ChatPage.tsx` 的 `webStates`）。原来那行注释就写着理由："消息答完会从服务端重取一遍，而联网状态没有入库。"学习记录 35 §五把它列进了两处口径缺口。

后果落在**唯一需要它说话的两个状态**上：

- `unconfigured`：开关开着但没配后端——**一个请求都没发出去**；
- `failed`：后端报错——用户以为搜过了，其实什么都没搜到。

这两种都不是"没搜到"（那是真实结果）。而它们只在那几秒里存在：刷新页面、换台机器打开同一条会话、或者只是 350 毫秒后那次自动重取没带上——提示消失。**一次可核查的事实，退化成了一次转瞬即逝的提示。**

## 二、交付了什么

| 层 | 文件 | 说明 |
|---|---|---|
| 库 | `src/product/database.py` | v10：`ALTER TABLE messages ADD COLUMN web_state_json TEXT` |
| 写入 | `src/product/chat.py` | `stream()` 建 assistant 消息时与来源同一时刻落库 |
| 读回 | `src/product/chat.py` | `_row_message()` 加 `web_state`；没有记录是 `None` |
| 接口 | `src/product/app.py` | **没改**——会话接口本来就整个转交 `chat.get_conversation()` |
| 前端 | `web/src/api.ts`、`web/src/ChatPage.tsx` | `ChatMessage.web_state`；**删掉** `webStates` 那张组件状态表 |
| 测试 | 后端 3 个文件 / 前端 1 个文件 | 后端 +5 项、前端 +3 项 |

## 三、三个判断

**1. 存 JSON，不存一个枚举列。**

"没联网"不是一种情况，是四种：`off`（开关关着）／`unconfigured`（没配后端）／`empty`（问了没结果）／`failed`（查询失败，**还要带异常名**）。前端要把它渲染成不同的句子，`failed` 那句还得把 `detail` 嵌进去（"本次未能联网（TimeoutError）"）。一个枚举列装不下，加列又要再迁移一次。

顺带一个反例：本来想写"还要带上后端名与结果条数"，去核 `web.py:augment()` 的返回值才发现状态只有 `{status, provider, detail?}`——**没有条数**。注释里写一个库里不存在的东西，下次就会有人照着它去读。

**2. `NULL` 不等于 `off`。**

旧行留 `NULL`，不补默认值。这一条与 v8 的 `origin` 补 `'note'` **故意相反**：

- v8 那里，`'note'` 是**已知的历史事实**——v8 之前的来源只可能是笔记片段，补上是在还原真相；
- 这里我们**不知道**当时联没联上，补 `off` 就是替历史编了一句"当时没联网"。

同一个道理还有第二种 `NULL`：**被能力守卫拦下的回答**。它压根没走到联网那一层，所以对它断言不了任何事。两种 `NULL` 在界面上都是"不说话"，但库里必须分得开——有测试固定两种都留 `NULL`、且旧行**不许**被补成 `off`。

**3. 落库的只有结论，没有查询词，也没有搜回来的正文。**

`web_state_json` 里只有 `status`/`provider`/`detail` 三个键。存快照会让"数据不出机器"这条承诺在**磁盘上**失效：一份外部正文躺在库里，就再也没人记得它来自外部了。要复读当初搜到了什么，去来源表看 `origin='web'` 那几条——那是它该在的地方。有一条测试拿问题原文和结果正文去反查落库内容。

## 四、顺手做的结构清理：删掉那张组件状态表

原来同一件事存在两处：事件里来一份（进 `webStates`），消息里一份（现在从库里读回）。两处存放的代价不是"多余"，是**它们会不一致**，而这次改动本身就是在处理不一致。

删掉 `webStates` 之后只剩一处，但**只靠"从库里读回"还不够**：答完之后还有 350 毫秒的窗口（`finally` 里那次 `setTimeout(..., 350)` 的重取）才把消息换成服务端版本。所以 `retrieval` 事件到达时也直接把状态写进消息对象——**答案落地那一刻就该说话，不能等重取**（重取慢、重取失败、用户抢在那之前滑到这条回答，都是真实场景）。

这条时序有测试钉着：让第二次重取**永远不返回**，提示必须已经在屏幕上。去掉那行写入，这条就挂——短路点 4。

## 七、踩过的坑

**1. 一次迁移要改 4 处写死的期望版本号。** `tests/test_product_foundation.py` 3 处、`tests/test_product_memory.py` 1 处（`test_schema_is_version_nine` → `_ten`）。这**是约定不是遗漏**：每次加迁移都要在提交里解释这个数字的变动，所以它就该写死。改动顺序照旧——**先改测试让它挂**，3 项如期 `AssertionError: 9 != 10` 之后才动 `database.py`。

**2. 三层里最容易漏的是"读回那一层"，而它的症状最不像。** 只加了 `_row_message` 而忘了迁移，报的**不是**"没有联网提示"，而是每次打开会话直接 `no column named web_state_json`——整个会话页打不开。反过来，加了迁移却忘了 `_message` 的写入，症状是"界面上有提示、刷新就没了"，正好是这次要修的东西。两个方向都不好从截图上看出来，所以三个方向各有一个短路点。

**3. 前端全量跑出过一次假失败。** `StudioPage` 的"导出信息图"那条，14 个测试文件抢 CPU 时 `findByTestId` 撞上 testing-library 默认的 1 秒上限，单独跑就通过。给 `vite.config.ts` 的 `test` 加了 `asyncUtilTimeout: 3000`：**机器忙闲不该决定测试结果**。这不是这次改动的缺陷，是顺手修掉的。

**4. 端到端验证需要前置数据。** 真实数据根里有 103 篇资料、1 个会话，但**一条消息都没有**——而且问答要一个能出话的模型。所以先跑一个一次性脚本造出那条回答（`.workbuddy/live_web_state_check.py`），再用 CDP 脚本去验界面（`.workbuddy/check_web_notice.cjs`）。两个都在 `.workbuddy/`（未跟踪），第三个脚本才是可以重复跑的。

## 八、还没解决

1. **界面只在出问题时说话。** `failed` 与 `unconfigured` 才有提示；`ok`／`empty`／`off` 一言不发（P2 的取舍：每轮都提示是噪音）。所以**"这轮确实联网了"在界面上仍然看不出来**，只能去来源列表看 `web` 那一层。库里现在有这份记录了，界面要不要给它一个位置（比如回答下方一行"联网：搜到 3 条"）没定。
2. **`ui_acceptance.cjs` 没有覆盖这条**，理由见 §七.4：它跑在真实数据根上，那份数据里没有消息，问答还要模型。所以这次的界面证据来自一次性脚本，43 项验收里没有它——`README` 里两个数字不能相互替代。
3. **一次性脚本没有做成可重复的一键流程**：它要求"默认会话里已经有一轮开了联网的问答"，得先跑另一个脚本造数据。
4. **`web_state_json` 与来源表的 `origin='web'` 有轻微冗余**（都要回答"这轮有没有网"）。两个都需要——"当时联网成没成"和"这轮最终引了几条网上的"是两个问题——但没有一致性校验，将来若有一条改口径，另一条不会跟着报错。
