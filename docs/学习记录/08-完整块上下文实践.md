# 阶段 8：完整块上下文实践

日期：2026-09-12。

## 原来的问题

排名靠前的来源不一定完整进入上下文。此前按字符预算截断，可能留下半条定义或半段代码；同一段证据还可能从多个重叠 chunk 重复进入上下文。

本轮新增 `src/evidence_context.py`，通过 `--context-policy blocks` 启用。旧 `legacy` 策略保留用于比较，没有把默认行为偷偷替换掉。

## 新策略如何打包

1. 去除空片段与内容完全重复的候选。
2. 识别段落、列表条目、代码块、表格等原文块。
3. 来源内部优先考虑有命中词的块，但不删掉所有无同词的语义证据。
4. 各来源轮流尝试放入一个完整块，避免首个来源独占预算。
5. 能完整放入才加入；放不下就记录 budget_skipped_blocks，不把尾部硬切成半句。
6. 最终按各来源原文顺序重新组织选中的块，并绑定引用标签、chunk ID、文档快照行号。

预算仍为字符数，默认 2200。所有标题、行号、续片说明、围栏和分隔符都计入预算。它还不是按生成模型 tokenizer 精确计算的整个请求窗口；长问题、系统提示与重写历史的预算管理留待服务阶段完善。

## 遇到的几个具体问题

### 1. 去重过度归一化会损伤代码

初版去重键折叠了所有空白，检查时发现这样可能把缩进不同的 Python 代码当成同一段。改为仅统一换行形式和首尾空白，保留内部缩进与字符串空格，并补了对应检查。

### 2. 续片中的闭围栏可能被误认成开围栏

一段代码被切开，第二片可能直接从代码内部开始。单独解析它时，原来的闭围栏就可能变成“新的开围栏”，影响后续来源的结构。

对已标记 continuation 的 chunk，本版整体作为带说明的文本片段保留，外层使用比内部更长的围栏。这样保留原文、标明它不完整，也不会编造缺少的代码。正常代码块仍尽量整体保留。

### 3. 完整性与来源数量并不总能兼得

完整块太大时可能被跳过，所以实际来源数不一定等于 Top-5。极小预算下可以没有任何可用上下文，问答流程此时不调用生成模型。引用标签也可能有间隔，例如 S1、S3；合法性依据实际传入的来源集合，而不是要求数字连续。

### 4. 局部完整不代表全局语义完整

一条列表虽然没有截半句，也可能依赖前面的定义或后面的限制条件。当前策略只是结构性改进，不是“证据足够性判断模型”，也不是事实校验器。

## 不调用生成模型就看上下文

新增 `src/explain_context.py`，可以直接检查打包结果：

```powershell
.\.venv\Scripts\python.exe -X utf8 -m src.explain_context "PagedAttention 是什么？它解决什么问题？" --chunks-file data/generated/token_v1/chunks.json --rerank
```

它输出候选数、实际来源数、总字符数、真实上下文、跳过/去重统计和重排输入长度，不调用 Ollama 或 DeepSeek。

## 接到实际问答

```powershell
.\.venv\Scripts\python.exe -X utf8 -m src.chat --provider ollama --retriever hybrid --chunks-file data/generated/token_v1/chunks.json --rerank --context-policy blocks
```

仍是各问题独立的连续入口，不是有多轮记忆的助手。退出用 `:quit`；用 `:method vector` 切换候选来源时，已启用的 rerank 与 blocks 设置保持不变。

生成报告新增 context_diagnostics。读取本轮报告示例：

```powershell
.\.venv\Scripts\python.exe -X utf8 -m src.inspect_report data/generated/evidence_20260912_rerank_blocks.json --case gen-001 --context
```

## 练习与参考答案

问：为什么预算更紧时选择“少一个完整段落”，而不是“多个只剩半句的段落”？答：半句可能失去限定条件，来源数量高也不能弥补证据含义被破坏。但丢弃完整大块也会漏答案，因此必须记录两种取舍并看真实回答。

问：能直接把这里显示的行号用于当前 Vault 文件吗？答：只有文档内容仍与快照一致时才可靠；先核对版本，不要把旧坐标当实时位置。
