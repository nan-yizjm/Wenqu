# 阶段 25：分阶段耗时、滑动窗口与监控口径

日期：2026-09-14。接续[阶段 24](24-有界队列与背压.md)。已有接口只返回总耗时、模型报告的生成耗时和一个笼统的 `non_generation_ms`。它能证明请求慢，却不能回答慢在排队、检索、证据打包、token 计数还是生成。

本阶段增加请求级分段耗时和 `/v1/metrics` 轻量聚合。它是本机调试观测，不是 Prometheus 或完整生产监控。

## 1. 计时层级

一次普通请求现在可观察：

```text
service_elapsed_ms
└─ queue_wait_ms
└─ runtime_total_ms
   ├─ prepare_total_ms
   │  ├─ guard_ms
   │  ├─ retrieval_ms
   │  ├─ context_pack_ms
   │  ├─ message_build_ms
   │  ├─ token_count_ms
   │  └─ other_ms
   ├─ generation_wall_ms
   ├─ finalize_ms
   └─ runtime_overhead_ms
└─ HTTP/线程调度等未单列开销
```

实际字段加 `prepare_` 前缀，例如 `prepare_retrieval_ms`。准备阶段子项包含在 `prepare_total_ms` 内，不能把所有数字全部相加，否则会重复计算。可相加的顶层近似是：

```text
runtime_total ≈ prepare_total + generation_wall + finalize + runtime_overhead
service_elapsed >= runtime_total + queue_wait
```

使用 `time.perf_counter()` 测相对耗时，避免系统时间调整影响。数值保留到 0.01 ms 只是输出格式，不代表 Windows、线程调度和 CUDA 同步具有 0.01 ms 的测量精度。

## 2. 为什么同时保留模型耗时与 wall time

`generation_wall_ms` 是调用者从进入模型接口到返回的墙钟时间。`local_model_metrics.generation_ms` 是本地模型客户端记录的生成路径时间。两者当前很接近，但语义不同：

- wall time 包含 Python 调用与 streamer 周边开销；
- 模型指标可以携带 prompt/generated token、停止原因和 CUDA 内存；
- 远程 provider 的服务端计时与本地网络墙钟更不应混为一谈。

因此没有用一个字段覆盖另一个，也没有把 `non_generation_ms` 继续当成检索耗时。

## 3. 请求级返回与轻量聚合

成功回答的 `phase_timings_ms` 示例：

```json
{
  "prepare_retrieval_ms": 11.47,
  "prepare_context_pack_ms": 0.39,
  "prepare_token_count_ms": 2.14,
  "prepare_total_ms": 14.02,
  "generation_wall_ms": 4776.68,
  "finalize_ms": 0.04,
  "runtime_total_ms": 4790.77,
  "queue_wait_ms": 0.01,
  "service_elapsed_ms": 4791.36
}
```

`GET /v1/metrics` 返回：

- 进程启动以来的观察总数和 outcome 计数；
- 最近 100 条数字记录的 avg、p50、p95、max；
- 当前 scheduler 状态和索引版本；
- 明确的隐私说明。

窗口使用固定长度 `deque(maxlen=100)`，因此内存有界。累计 outcome 不随窗口淘汰而减少，而延迟分布只针对当前保留窗口；两者口径不同，字段分别命名为 `observed_total` 和 `retained`。

p50/p95 使用 nearest-rank，从真实观测中取值，不插值生成一个并未实际出现的延迟。只有两三个样本时，p95 往往就是最大值，不能把本阶段小样本当成稳定 SLO。

## 4. 隐私边界

聚合记录只允许以下内容：

```text
outcome、HTTP status、各阶段数字耗时
```

不保存问题、答案、上下文、来源正文、API Key 或异常详情。真实探针会在序列化后的 metrics 中搜索问题和回答标志词，确认没有正文泄露。

单次回答接口本来就需要返回答案与来源，这与聚合指标的隐私边界不同；保存到 `data/generated` 的实验报告仍可能含问题、回答和检索轨迹，因此继续由 `.gitignore` 排除。

## 5. 第一版聚合的口径错误

第一轮报告：

```text
data/generated/adapter_observability_probe_20260914_213257_754523.json
```

8 项实现检查都通过，但人工查看聚合发现：OOD 请求没有调用模型，其响应正确记录 `generation_wall_ms=0`；聚合器却把这个 0 加入 generation 平均值。两道真实生成约 5300/5422 ms，加入 OOD 的 0 后平均值变成约 3574 ms，显著低估“执行过生成的请求”的生成耗时。

这是典型的 absent 与 zero 混淆：

- 请求级：0 表示这一题没有执行生成，信息有用；
- 阶段延迟分布：未执行阶段应当缺席，不能当成一次 0 ms 生成。

修复后，HTTP 响应仍保留 0，但送入聚合窗口前，若 `generation_calls=0` 就移除 generation/finalize 字段。最终报告明确检查 generation 样本数为 2。

## 6. 最终真实 adapter 实验

最终报告：

```text
data/generated/adapter_observability_probe_20260914_213426_751280.json
```

启动环境仍为 Qwen2.5-1.5B + QLoRA adapter、911 chunks、hybrid 检索、2048 prompt token、160 最大生成 tokens。服务为新进程，先后请求 OOD、单概念和综合题。

| 请求 | prepare | retrieval | token count | generation wall | runtime total | service total |
|---|---:|---:|---:|---:|---:|---:|
| 北京明天天气（OOD） | 0.01 ms | 未执行 | 未执行 | 0 ms | 0.05 ms | 1.47 ms |
| PagedAttention | 277.61 ms | 257.10 ms | 18.86 ms | 5143.90 ms | 5421.65 ms | 5422.76 ms |
| 基础 RAG 流程 | 14.02 ms | 11.47 ms | 2.14 ms | 4776.68 ms | 4790.77 ms | 4791.36 ms |

9 项检查全部通过：行为符合预期、字段完整、层级关系成立、OOD 零生成、两道知识题各生成一次、新增三条观察、聚合字段存在、generation 聚合排除 OOD、指标不含正文。

当前两次真实生成的聚合：

```text
generation count = 2
avg = 4960.29 ms
p50 = 4776.68 ms
p95/max = 5143.90 ms
```

最明显的结论是生成占总时间约 95% 以上；在当前问题上，优先优化几百微秒的 finalize 没有意义。

另一个现象是第一道知识题 retrieval 为 257.10 ms，紧接着第二道只有 11.47 ms。索引和模型虽已在启动期加载，首次实际 CUDA 编码仍可能触发 kernel、allocator 或运行时预热。只有两个不同问题，不能精确拆分题目复杂度和 warm-up；它足以提醒我们性能实验要区分首题与热题。

## 7. 普通、流式与错误路径

- 普通成功回答把排队和 service 总耗时并入 `phase_timings_ms`，同时送入聚合；
- 排队拒绝、排队超时、HTTP 回答超时和模型错误按不同 outcome 计数；
- 流式 final/cancelled/error 在 producer 真正收尾后记录一次；断线看不到最终事件时，从运行时的 `last_request_summary` 取数字阶段；
- OOD 流不启动模型，但仍记录 prepare/runtime/service；
- 日志里的中间件 `elapsed_ms` 对 StreamingResponse 仍主要是响应头建立时间，完整流继续看 `stream_finished.body_elapsed_ms` 和阶段计时。

## 8. 自动验证与复现

单元检查覆盖：

- AnswerResult 对知识题包含检索、生成和 finalize 字段；
- OOD 的 generation 明确为 0；
- `/v1/metrics` 累计成功 outcome 且不出现假回答正文；
- 容量为 2 的窗口观察三条后只保留后两条，累计 outcome 仍为三条；
- 两条 20/30 ms 的 nearest-rank p50=20、p95=30；负耗时不会进入统计。

真实复现：先启动 adapter 服务，再运行：

```powershell
.\.venv\Scripts\python.exe -m src.observability_probe
```

日常只看数字摘要：

```powershell
Invoke-RestMethod http://127.0.0.1:8000/v1/metrics |
  ConvertTo-Json -Depth 8
```

## 9. 当前限制与下一步

- 所有指标只在当前进程内，重启清零；
- 固定 100 条是实验默认值，尚未做配置项；
- 小窗口 p95 抖动大，没有时间桶、速率和跨进程聚合；
- 没有 GPU 利用率、功耗或显存的连续时间序列；单次模型指标只有请求结束时的快照；
- 当前时钟测到 wall time，不是 CUDA kernel 精确时间；需要 profiler 才能拆 prefill/decode/kernel；
- 错误 outcome 有计数，但没有结构化最近错误时间和错误率窗口；
- 服务端统计不能取代离线质量评测，回答很快也可能是错的；
- 暴露 metrics 目前仍依赖 localhost Host/Origin 边界，若公开部署必须先做认证和网络隔离。

下一阶段进入容器化与启动自检：先定义哪些文件应该进入镜像、哪些模型/索引应作为运行时挂载，再做不携带私人语料和密钥的 Docker 构建。8 GB Windows 本机的 GPU 容器兼容性要单独验证，不能假设装好 Dockerfile 就能使用 CUDA。

## 10. 练习与参考答案

### 练习 1

为什么不能把 `prepare_retrieval_ms + prepare_total_ms + generation_wall_ms` 当作总耗时？

参考答案：retrieval 已包含在 prepare_total 中，再加一次会重复计算。应使用 prepare_total、generation、finalize 和 runtime_overhead 这些同层字段。

### 练习 2

OOD 的 generation=0 为什么在单题响应中合理，在生成延迟聚合中却不合理？

参考答案：单题的 0 表示阶段未执行；生成延迟分布要回答“执行过生成时有多慢”，未执行的样本不属于这个总体，应缺席而不是作为 0 值。

### 练习 3

本实验 p95=最大值能否作为服务性能承诺？

参考答案：不能。生成阶段只有两个样本，nearest-rank 的 p95 必然取最大观测。需要足够样本、固定负载、区分冷热路径，并给出时间窗口和硬件环境。

### 练习 4

为什么 `/v1/metrics` 不应记录问题文本，哪怕这是个人本机服务？

参考答案：问题可能包含私人笔记、账号、路径或密钥；性能聚合不需要正文。数据最小化也能减少以后把服务暴露或导出指标时的泄露风险。

### 练习 5

PagedAttention 题 retrieval 257 ms，而下一题 11 ms，能否断言前者语义检索更难？

参考答案：不能。它是新进程中的首个实际知识查询，可能包含 CUDA/kernel/allocator 预热；问题内容也不同。要交替题序、重复多轮并单独记录 warm-up 后才能归因。
