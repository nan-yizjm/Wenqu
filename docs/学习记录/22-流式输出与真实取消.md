# 阶段 22：流式输出、真实取消与断线清理

日期：2026-09-14。接续[阶段 21](21-常驻Adapter服务与冷热路径.md)。本阶段不是简单把完整回答切成几段发送，而是让取消信号进入模型的逐 token decode 循环，并验证客户端断开后模型线程、HTTP 清理和唯一 GPU 席位都真正结束。

## 1. 要区分的三件事

```text
流式显示：生成一点，客户端看到一点
请求取消：客户端不再等待或连接断开
模型取消：decode 循环观察停止条件并真实退出
```

前两项不自动推出第三项。普通 `model.generate()` 被放进线程后，即使 HTTP 返回 504 或 Future 被 cancel，CUDA 生成仍可能继续。阶段 21 的单请求锁正是为了防止这种情况下第二个任务重入 GPU。

## 2. 模型层实现

`src/hf_qlora_client.py` 增加两部分：

- `TextIteratorStreamer`：模型每生成一小段文本就放入线程安全队列；
- `EventStoppingCriteria`：每次 decode 后读取 `threading.Event`，并记录是否真的观察到取消。

核心线程关系：

```text
调用线程                         生成线程
   │                                │
   ├─ 迭代 TextIteratorStreamer     ├─ model.generate(...)
   │      ↑                         ├─ 每步检查 EventStoppingCriteria
   │      └──── 文本队列 ───────────┤
   ├─ 断开/close → event.set()       │
   └─ join，确认线程结束  ←──────────┘
```

`StoppingCriteria.__call__` 返回与 batch 大小一致的布尔张量，而不只返回日志标记。指标同时记录：检查次数、事件是否被模型观察、生成 token 数、首段时间、线程 join 后是否仍存活。

同步 `chat()` 和 `stream_chat()` 共用一个客户端级生成锁，防止绕过 HTTP 后直接并发调用同一个 4-bit 模型。

## 4. HTTP 协议为什么选择 NDJSON

新增：

```text
POST /v1/answer/stream
Content-Type: application/json
Response: application/x-ndjson
```

每行是一个独立 JSON 对象：

```json
{"type":"metadata","complete":false,"sources":[...]}
{"type":"token","text":"结论"}
{"type":"token","text":"："}
{"type":"final","complete":true,"answer":"...","citation_validation":{...}}
```

取消时终止事件是：

```json
{"type":"cancelled","complete":false,"partial_answer":"...","citation_validation":null}
```

这里特意不把半截文本送入普通 finalize，也不声称引用通过。OOD/静态拒答不调用模型，直接返回单个 `final` 事件。

选择 NDJSON 是因为当前入口是带 JSON body 的 POST，Python、PowerShell 和浏览器 `fetch()` 都能逐行消费。浏览器原生 `EventSource` 只便于 GET；若未来需要自动重连和事件 ID，再考虑 SSE。

## 5. RAG 为什么要拆成 prepare 与 finalize

原 `RAGAnswerer.answer()` 把守卫、检索、上下文、模型调用和引用校验串在一个方法里。流式运行若复制前半段，很容易让普通回答和流式回答使用不同的检索逻辑。

现在拆为：

```text
prepare(question)
  → OOD/无上下文的 immediate_result
  或 messages + sources + retrieval trace + context diagnostics

完整生成结束
  → finalize(prepared, full_answer)
  → citation validation + AnswerResult
```

原 `answer()` 仍调用这两个阶段，所以默认 Ollama/DeepSeek 的外部行为不变。取消的流只有 partial text，禁止调用 `finalize()`。

## 7. 实际遇到的两个取消竞态

### 7.1 模型停了，但 HTTP 锁没有释放

第一次断线实验中：

```text
last_request_summary.mode = cancelled
health.ready.busy = true
恢复请求 = HTTP 429
```

根因是客户端断开导致 ASGI 响应 task 被取消；该 task 进入 `finally` 后，第一个异步 `await` 又立即抛 `CancelledError`，后面的 `lock.release()` 永远没执行。

修复后，关键清理区不再依赖已取消协程继续 await：设置取消事件，同步等待生成 producer 最多 30 秒，只有线程确实退出才释放锁。若线程仍活着，宁可保持 busy 并记录 `stream_producer_stuck`，也不冒险允许第二个 GPU 任务进入。

### 7.2 cancelled 状态早于席位释放

运行时先记录 cancelled，ASGI 流随后才执行清理。因此 probe 看到 cancelled 后立刻恢复仍可能太早。检查逻辑改为同时等待：

```text
last_request_summary.mode == cancelled
AND
health.ready.busy == false
```

这比固定 `sleep(1)` 更可靠，也展示了“业务状态完成”和“资源清理完成”是两个状态转换。

### 7.3 自然结束被误记成 cancel requested

streamer 读到结束标记时，`model.generate()` 的线程可能还差极短的函数返回。早期实现只要此刻线程仍 alive 就设置取消事件，导致正常完整请求出现：

```text
stop_reason = eos_or_length
cancel_observed_by_model = false
cancel_requested = true   ← 指标矛盾
```

修复方式是单独记录是否自然读到 streamer 的 stop signal。只有消费者提前关闭且线程仍活着才主动设置取消事件。最终报告中完整流和恢复流均为 `cancel_requested=false`，断开请求才是 cancelled。

## 8. 流式监控不能沿用普通请求耗时

FastAPI 中间件的 `call_next()` 在 StreamingResponse 建立响应头后就返回。因此普通 request 日志只有约 3～5 ms，而客户端实际收到完整回答需要约 3.7 秒。

服务新增独立 `stream_finished` 日志：

```json
{
  "event":"stream_finished",
  "cancel_reason":"response_closed",
  "runtime_summary":{"mode":"cancelled","generated_tokens":1},
  "body_elapsed_ms":391.41
}
```

普通日志测的是响应建立，`body_elapsed_ms` 才覆盖流的生命周期。监控流式服务时若只看中间件延迟，会得到“请求只有 4 ms”的错误结论。

## 9. 当前限制

- 为保证断线清理不可被再次取消，producer 收尾会最多同步阻塞事件循环 30 秒；本机单用户可接受，生产设计应使用独立资源管理器/reaper；
- producer 到 HTTP 的队列当前无界；慢客户端会累积文本片段，后续应加有界背压；
- 一个连接一个生成任务，没有等待队列、优先级或持久化；
- HTTP 头发出后出现模型错误，状态码已是 200，只能在 NDJSON 中发送 `type=error`；
- `request_timeout` 在流中表现为 cancelled 事件而不是 504；连接已断开时客户端看不到终止事件，只能服务端记录；
- 取消粒度是一次 decode step，不是正在执行的单个 CUDA kernel；
- 没有浏览器 UI、SSE 重连、心跳或代理缓冲的跨环境验证；
- adapter 的依据过度作答问题没有因流式能力而改善。

## 10. 练习与参考答案

### 练习 1

客户端已经关闭连接，为什么还要在服务端保存 cancelled 状态？

参考答案：断开的客户端收不到最后事件，但运维侧仍要知道模型是否真实停止、生成了多少 token、席位何时释放。否则无法区分正常取消、后台泄漏和 GPU 卡死。

### 练习 2

为什么 cancelled 事件不能带 `citation_validation=true`？

参考答案：部分文本可能尚未输出引用或语义未结束，对它执行完整答案规则会产生假阳性/假阴性。取消结果不是最终回答，应明确 `complete=false`、validation 为 null。

### 练习 3

为什么 `response.status=200` 不能证明流式生成成功？

参考答案：200 在响应头建立时已经发送，模型错误可能发生在后续 body。客户端必须读取到显式 `final` 事件才算完整成功；`error`、`cancelled` 或连接中断都不是成功完成。

### 练习 4

为什么“模型观察取消”和“busy=false”要分别检查？

参考答案：前者说明 decode 停止，后者说明线程、响应生成器和锁等资源清理结束。它们按顺序发生，但不是原子动作。
