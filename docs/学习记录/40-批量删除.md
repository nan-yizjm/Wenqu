# 40 · 批量删除：三个列表，一套诚实的确认

日期：2026-09-19。需求来自使用者一句话："增加一个批量删除的功能"。范围经确认收敛为**资料库 / 收藏 / 产出**三个列表（会话不做），确认时把后果说清，**不做撤销、不做回收站**。

## 一、范围怎么定的

动手前先盘点：产品里能删的有四类（会话 / 资料 / 收藏 / 产出），全部只能一条一条删。四类的删除语义差别很大，批量做在哪、怎么做必须先问清楚：

| 列表 | 现有单条语义 | 批量化的关键约束 |
| --- | --- | --- |
| 资料 | 软删（`status='removed'` + `removed_at`） | **文件夹来源的"移除"是暂时的**：行还在、磁盘文件还在，刷新那个文件夹会被重新导入。批量把这句话放大 30 倍，必须在确认框里如实写出 |
| 收藏 | 硬删，`favorite_sources` 级联 | 收藏是副本，删了不影响原会话 |
| 产出 | 硬删 + 级联 + 删 `exports/` 里的导出文件 | 正在生成的产出**不能删**（生成线程还在往 `artifact_sources` 写行，主表没了会撞外键），单条是 409，批量必须变成"跳过并如实报" |

使用者确认：批量加在资料 / 收藏 / 产出三处；删错了不撤销；确认时把后果说清。回收站是已知缺口（软删资料、快照、旧索引本来就没有清理策略），不在这次做。

## 二、后端：一个请求体、三次事务、一次快照

三个批量端点共用**一个**请求体模型 `BatchDeleteBody`（`app.py:170`）：`ids: list[str]`，`min_length=1`（空选择回 422——空请求回 200 会把一次根本没执行的删除显示成"已完成"）、`max_length=500`、字段级去重（同一个 id 出现两次必然报"不存在"，那条 skipped 只是噪音）加 id 限长校验。资源写在路径里（`POST /api/v1/documents/delete`、`/favorites/delete`、`/artifacts/delete`）。

服务层三条批量方法，各自守住自己的语义：

- **`remove_documents`**（`materials.py:824`）：一次事务里改所有行的软删标记，**`_publish_snapshot()` 只调一次**。逐条调 `remove_document` 也能删掉同样多的东西，但每条都会重建一次检索快照——选 30 篇就是 30 次重建，中途每一次正在看的检索都会换版本号。找不到的进 `skipped` 如实报回。单条 `remove_document` 改为复用它，再保留 404 语义（找不到要报错，而不是"删了 0 条"）。
- **`delete_favorites`**（`organize.py:247`）：一次事务，级联带走 `favorite_sources`，缺失条目逐条进 `skipped`。
- **`delete_artifacts`**（`studio.py:318`）：正在生成的跳过（`code: 'busy'`，带标题回去——界面要说得出是哪一份），不存在的报 `not_found`，删除成功后逐个清 `exports/` 导出文件，**删掉几个就报几个**：`unlink(missing_ok=True)` 会把"文件本来就不在"也算成一次删除，那样报出来的数字就没法核实了。

三个端点返回同一个形状：`{ "deleted": N, "skipped": [{"id", "label", "code", "reason"}], "files_removed"?: M }`。

## 三、前端：选择模式，一条 bar，两段式确认

三个页面共用一个 `BatchDeleteBar` 组件 + `useSelection` 钩子。入口是列表头部的"批量选择"按钮：进入后每行多一个复选框，底部出现操作条（全选 / 计数 / 退出 / 删除）。

确认走**页面内两段式**（和退出入口同一条线）：第一下"删除"只展开确认框，写出"将删除 N 项"与该资源的具体后果；"再想想"退回；第二下才真正发请求。不用 `window.confirm`——无头验收里它会卡死，而且装不下"每类资源一句后果"的文案。

结果条不报喜不报忧的两件事：

1. **skipped 的每一条都要说清是谁、为什么**。只报"已删除 2 项"会把一次不完整的删除说成成功的——"在生成的产出被跳过"必须出现在结果里。
2. 删除失败（请求层错误）回到确认框并显示错误，**不假装删成功**。

资料页的确认文案按选中内容动态写：勾了文件夹来源的资料，追加"其中 N 篇来自已连接的文件夹，只是暂时移除——刷新那个文件夹时它们会被重新导入"；只勾上传来源就不说这句（对上传资料说"暂时移除"反而是错的——它们不会回来）。

## 四、测试与短路

| 层 | 数字 | 说明 |
| --- | --- | --- |
| Python | **315 项**（原 307，+8） | 批量语义：一次事务、快照只发一次、skipped 如实、busy 经 API 是 200+skipped 而非 500、单选行为不变、空/超量 422 |
| vitest | **124 项 / 16 文件**（原 107 / 14） | BatchDelete 组件 6 项 + 三页各 2–3 项集成（含"文件夹来源要说暂时移除""上传来源不说"） |
| 真实界面验收 | **57 项**（原 43，第 13 步 +14） | 造两篇专用资料走完整流程：选择 → 确认 → 再想想 → 真删 → 服务端核对，跑完不留痕迹 |
| 短路 | **7 点全挂** | 只删第一条报成功、快照发两次、收藏吞缺失、busy 被连同删、空选择回 200、skipped 不显示、确认框不写"暂时移除" |

短路验证里有一个值得留意的点：**API 测试挂的是 `StudioApiTests` 而不是服务层测试**——因为 harness 里 `service` 与 `app.state.studio` 是两个实例，`_active` 各自持有，走 API 必须把 busy 状态塞进 `app.state.studio` 才能命中。测试 therefore 挂在"经 API 的 busy 报 200+skipped"上。

## 五、真实验收抓出来的两件事

**1. 结果条消失案（脚本错误 + 构建过期叠加）。** 第一次跑验收 56/57："删除后如实报告已删除 2 项"失败，但服务端确认删除成功。排查链：

- 直接计时端点：**1.4 秒**（96 篇资料下删 1 篇）——不是快照重建慢，推翻了"等 45 秒不够"的假设；
- 用 CDP 复现 1 篇全流程：结果条 2 秒内出现——组件没问题；
- 对齐版复现（2 篇 + 再想想往返）：结果条**一直显示着**，但 `document.querySelector('[data-testid="batch-result"]')` 查不到——`className` 有 `batch-result`，`data-testid` 没有。

根因：给结果条加 testid 的那次编辑**在最后一次 `npm run build` 之后**，验收实例（源码启动，服务 `web/dist`）跑的是旧产物。**源码对了、构建旧了**，这和"组件测试全绿但交付物不可用"是同一类事故的另一面：这次连源码都是对的，错的只是"改了源码忘了重建"。教训落在验证纪律上：**改完前端源码，构建必须重跑在验收之前**——不管这次改动多小。

**2. fetch 直传不触发界面刷新。** 验收脚本用 fetch 绕开无头环境点不开的文件选择器上传资料，上传后界面列表不更新——轮询 20 秒都是旧列表。切走再切回（LibraryPage 重新挂载）就出现。这不是产品缺陷：真实用户从界面上传，上传成功后立即 `load()`。但脚本必须显式"切走切回"才能看到新资料，已在脚本里写明，防止下次误判成缺陷。

## 六、没解决的 / 边界

- **选择模式不跨页**：96 篇资料一页渲染，没有分页，"全选"就是全选这一页（= 全部）。将来真分页了，"全选"的语义要重新定。
- **收藏的批量删除不走列表选择**：收藏页用筛选 + 详情布局，选择模式挂在左侧列表上，右侧详情在选择模式下不可选。
- **导出文件计数**在产出删除里是"尽力而为的如实"：`unlink` 失败不阻塞删除，但也不会谎报删掉了。
- **会话批量删除**没做（使用者没选），四类里它是唯一带"收藏的结论会保留"这类间接语义的，要做时要单独过一遍确认文案。
- **回收站 / 清理策略**仍是已知缺口（软删资料、快照、旧索引无清理），这次确认了"不做撤销"，但没有取消那个更大的缺口。
