# 阶段 11：笔记更新、向量复用和可回退的索引

日期：2026-09-12。入口：`src/index_store.py`，向量复用：`src/vector_retrieve.py`。

## 1. 先分清两种缓存

之前的缓存判断是：**整份 chunks 的内容、顺序和模型配置是否完全相同？** 相同就加载整个 NPZ，不同就整体重建。这适合学习矩阵行与片段的对应关系，但一篇笔记改变也会触发全库编码。

现在增加第二层：即使新旧 chunk 列表不同，也检查每个片段的**实际 passage 输入**能否在兼容的旧索引里找到。

```text
笔记字节变化 → 哪些文档需要重新分片？
passage 变化 → 哪些片段需要重新编码？
模型/模板变化 → 旧向量是否仍可复用？
```

这三个问题不能合并成一个“文件变了”的布尔值。

## 2. 完整更新过程

1. 获取索引目录的单写入者锁。构建和激活都用同一把锁，避免两个进程互相覆盖 current。
2. 只读扫描配置的 Markdown 目录，计算文件字节 SHA-256，并建立 UTF-8 文本快照。
3. 和当前版本的 `files` 比较，识别新增、修改和删除。
4. 文件与分片流水线都没变化，直接返回 `unchanged`，不加载 tokenizer 或 E5。
5. 未变文档复用旧 chunks；变化文档重新分片，更新来源行号、字符位置和文档哈希。
6. 对每个新 chunk 构造真实 E5 输入，在兼容旧矩阵中查找同一字符串。找到就复制相应行，否则批量编码。
7. 在临时目录写完整文档快照、chunks、NPZ、清单和统计；确认没有超限编码。
8. 再次检查笔记哈希与流水线签名。构建过程中变了就拒绝发布，旧版本继续有效。
9. 把完整临时目录重命名为新版本目录，再原子替换小型 `current.json` 指针。

代码把这些动作放在 `IndexStore.build` 中。没有文件监控器，没有后台自动构建；你运行一次 `build` 就得到一次快照。最终检查后继续编辑的内容，要等下次更新才进入索引。

## 3. 为什么不能只按 chunk ID 复用

矩阵行的位置不是知识的身份。文档排序变化后，原第 0 行可能变成第 5 行；如果只拿旧矩阵拼接，答案就会引用错误文件。

实现的复用键是 `PASSAGE_TEMPLATE.format(**chunk)` 的**完整字符串**。例如在原段落前新增一节：

- 原段落正文和标题路径不变 → 编码输入不变 → 旧向量可复用。
- 原段落行号改变 → 新 chunks 元数据必须更新。
- 旧向量要填入新列表的正确行号，而不是沿用旧矩阵位置。

模型 revision、模板、query 前缀、最大长度、归一化方式、维度和相关包版本都必须兼容。否则记录 `reuse_status = incompatible` 并重新编码。本版对包版本变化采取保守策略，即使某次升级实际不影响数值，也不会冒险盲用。

额外检查包括重复 chunk ID、float32、矩阵维度、有限值和单位长度；NPZ 读取禁止 pickle。它们是格式与完整性校验，不是密码学签名，也不能阻止有本机写权限的人同时改数据和清单。

## 4. 目录结构与版本切换

```text
data/generated/index_store/
  .writer.lock               OS 锁使用的一字节文件
  current.json               只存当前版本号和清单哈希
  versions/
    <UTC时间-随机后缀>/
      documents.json         当次原文快照
      chunks.json            片段及来源位置
      vector_index.npz       与 chunks 行序对应的矩阵
      manifest.json          输入/代码/模型/产物哈希、变更清单和耗时
```

更新失败发生在发布前时，current 保持原样。如果进程恰好在版本目录已写完、指针还没切换时退出，会留下一个完整但未激活的版本，可以用 `list` 查看和手动激活；不会在启动时自动删除它。

原先的 `data/generated/chunks.json`、`vector_index.npz`、`token_v1/` 以及历史报告全部保留。新的“不可变版本”是应用层约定，不是把目录设置成 OS 只读；不要用旧实验命令指向 `versions/` 去重建缓存。

```powershell
.\.venv\Scripts\python.exe -X utf8 -m src.index_store list
.\.venv\Scripts\python.exe -X utf8 -m src.index_store status

# 将 list 输出的某个完整版本号填到这里。仅切换索引指针，不回退 Git 或笔记。
.\.venv\Scripts\python.exe -X utf8 -m src.index_store activate <版本号>
```

激活前检查固定产物清单与 SHA-256。非法版本号、越界路径、损坏文件会被拒绝。运行中的 CLI/HTTP **仍固定启动时版本**；停止并重启后才使用新的 current。回退索引不回退笔记原文，也不回退运行参数或模型代码；旧版本和当前环境不兼容时仍会报错。

## 5. 本轮实测，不混淆旧语料与新语料

真实 Vault 当前扫描得到 **56 篇笔记、911 个片段**。上一阶段的文档快照是 52 篇、822 个 token 片段，因此 911 不是“换了同一批数据的切分算法就增加 89 个”的证据。

首次真实构建：

```text
版本：20260912T062623795056Z-2d6e3a20
documents = 56
chunks = 911
parsed_documents = 56
encoded_chunks = 911
elapsed_seconds = 13.657
```

紧接着不改笔记再构建：

```text
status = unchanged
版本号不变
encoded_chunks = 0
elapsed_seconds = 0.042
```

这是整次 `build` 内部计时，不含 Python 进程启动的全部成本；单次观察不能当作长期性能基准。首次版本没有旧的 managed store 可复用，因此编码 911 个；没有跨目录自动搬用历史实验缓存。

增量编辑、删除、回退没有拿你的真实笔记做破坏性演示，而是在自动清理的临时小语料上验证：两节笔记修改第一节后，**1 个片段重新编码、1 个复用**；旧 chunks 哈希不变；新增/删除反映在新版本；激活旧版本能回退指针。矩阵重排验证使用不同方向的假向量，确认不是只检查计数。

## 6. 出错时应该发生什么

| 情况 | 已实现的行为 | 你需要做什么 |
|---|---|---|
| 路径不存在 / 读取无权限 | 报错，不当作“全部笔记被删除” | 检查路径与权限 |
| 扫描得到 0 篇 | 默认拒绝发布 | 只有确实需要空索引才加 `--allow-empty` |
| 编码失败、GPU 错误 | 清理本次临时目录，保留 current | 检查显存，必要时改 CPU 再 build |
| 编码时笔记被改动 | 拒绝发布 | 编辑完成后重试 |
| 另一个进程正在构建 | 立即报告忙碌 | 等待另一进程结束 |
| 进程被杀但锁文件还在 | OS 会释放锁；文件保留正常 | 不要因文件存在就删除它 |
| 版本产物被手动改坏 | 校验失败，不激活 | 选择完好旧版本；不要假装修好了 |

扫描不进入隐藏目录、符号链接目录和 Windows junction；文档文件符号链接会拒绝处理。这是明确的扫描范围限制，不是“支持所有 Obsidian 链接”。普通 wikilink 只是文本，不会被当路径执行。

当前仍会读取全库字节计算哈希，并把完整快照和矩阵写入每个新版本；**节省的是分片与模型编码，不是无限规模的 IO 或存储**。版本不会自动清理。大语料再考虑文件事件、共享对象存储、增量向量数据库和安全 GC，现在先保留可理解的实现。

## 7. 练习与参考答案

**题：删除一篇笔记后，旧版本为什么仍能检索到它？**

答：旧版本是历史快照。新版本才排除删除文件。运行时若未重启，仍服务旧快照；要看响应的 `index_version`，不能只看当前文件夹。

**题：为什么激活失败时不自动重建或修改清单哈希？**

答：失败可能意味着损坏或错误版本。自动改哈希只是掩盖问题，会失去可追溯性。应选完好版本或明确重新 build。

**题：仅修改题目评测脚本会触发全库更新吗？**

答：不会。流水线签名只覆盖与导入/切分/向量编码有关的代码和参数。更新 API 路由也不要求重编码；修改分片源码则触发重新分片，但未变 passage 仍可复用。
