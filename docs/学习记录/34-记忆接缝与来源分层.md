# 34：记忆接缝与来源分层

> 2026-09-18 ｜ 对应 `docs/新功能实施计划-2026-09-18.md` 的 P1

**这一轮做了什么**：给"这条依据来自哪一层"在数据里留出位置，并把记忆系统挡在一个协议后面。

**这一轮刻意没做什么**：没有实现任何记忆存储。交付的是**接缝**，出厂行为与"没有记忆"逐字段一致。

## 二、遇到什么问题

### 问题 1：测试改全局状态没复原，18 项测试以完全不相干的形态变红

`tests/test_product_foundation.py` 为了验证"迁移失败会被回滚"，把 `MIGRATIONS[8]` 换成了非法 SQL。v8 以前只是"还没写的下一个版本"，所以它顺手 `MIGRATIONS.pop(8, None)` 也无害。

v8 变成**真实迁移**之后，这个 `pop` 会在进程里把它永久删掉。unittest 按模块名字母序执行，`test_product_foundation` 之后建的库全部停在 v7，而 `chat.py` 已按 v8 写 `origin` 列，于是：

```
sqlite3.OperationalError: table message_sources has no column named origin
```

**报错的是 `test_product_organize` 与 `test_product_support`**，与迁移毫无关系。全量 219 项里 18 项红（2 failures + 16 errors）。

> **教训**：测试不许修改模块级共享状态而不复原。跨模块的污染症状会指向**错误的地方**——如果只看报错的两个模块，会一路往收藏和备份里找，永远找不到迁移头上。伪装失败必须存原值、`finally` 恢复。

### 问题 2：收藏会丢掉"来源分层"

`favorite_sources` 表没有 `origin` 列，`organize.py` 的复制也没有带它。结果是收藏页的记忆/网络来源**退化成"看着像笔记"**——而用户恰恰是为了核对依据才收藏的。

抓到它的是既有的那条契约测试（`test_favorite_keeps_the_retrieval_evidence_of_its_sources`）：

```
AssertionError: Items in the second set but not the first: 'origin'
```

它断言"收藏与实时消息的来源必须是同一个形状"。**接缝只在主路径上闭合是不够的**——同一条来源有三个存储点（`message_sources`、`favorite_sources`、以及流事件里的 payload），漏一个就有一处会静默降级。

### 问题 3：点开记忆来源必然 404

记忆条目的 `document_id` / `version_id` 都是占位串 `"memory"`。`SourcePanel` 原本无条件按 `document_id` 去请求原文快照，于是点开记忆来源会请求：

```
/api/v1/documents/memory/versions/memory/source   → 404
```

修法不是"给它一个假文档"，而是**按 `origin` 分流**：只有笔记层的来源才取得到快照，记忆与网络的正文就是它自己的 `preview`。同时面板不再对记忆层说"历史快照"——记忆条目没有版本可言。

### 问题 4：来源卡片的选中态会串到另一轮回答

来源卡片的选中判定原先比较 `label`（`S1`/`S2`）。而 `label` 是**每轮回答各自从 1 开始**的编号，两轮之间必然重号——点第一轮的 S1，第二轮的 S1 会跟着亮。改成比较 `chunk_id`。

### 问题 5：验收脚本每次泄漏一个 50 MB 的 Chrome profile

`scripts/ui_acceptance.cjs` 用 `mkdtempSync` 建 Chrome 的 `user-data-dir`，收尾只 `kill` 进程，从不删目录。实测 4 次运行在 `TEMP` 里留下 **176 MB**（56/56/12/52 MB）。已修：等进程真的退出再 `rmSync`，并在失败路径上也清理。删之前必须等——Chrome 还占着的时候删只会留下删不掉的半个目录。

### 问题 6：原方案里的图片渲染路径在冻结版里不成立

前一份计划把"图片产出复用 `scripts/ui_acceptance.cjs` 的 CDP 通道"列为**最省钱的发现**。但 `product.spec` 不打包 Node，`dist/ObsidianRAG/` 里只有 `ObsidianRAG.exe` + `_internal`，用户机器也不保证有 Node。

**改用本机 Edge/Chrome 的 `--headless=new --screenshot=`**，纯 `subprocess`，零新依赖。本机 Edge 与 Chrome 都在标准路径，已核实。这条更正记在 `docs/新功能实施计划-2026-09-18.md`。

## 三、为什么这样处理

**为什么只交付协议，不顺手把存储做了？**
接什么还没定（自研 / Mem0 / Zep 这类带事实抽取与冲突消解的）。接口形状定错的返工成本远高于先留一个空实现，而空实现的成本是零——它不建文件、不返回条目。现在协议里**刻意没有**"新事实取代旧事实"的表达；等定了再补一个字段，只改 `memory.py` 一处。

**为什么是"关着时根本不调用"，而不是"调用了再丢弃结果"？**
这是这个接缝唯一能被第三方验证的隐私承诺。接进来的实现不需要相信产品会丢掉结果——产品压根不会问它。有测试固定这一点（断言 `recall` 的调用次数为 0）。

**为什么记忆坏了只记录、不拒绝服务？**
记忆是辅助通道。它坏了让用户连笔记都问不了，代价远大于少几条记忆。与既有的"向量索引截断只记录不拒绝"是同一个取舍。失败会写 `app_events`，不静默。

**为什么只有一层来源时不显示层名？**
出厂状态只有笔记层。多一层"笔记"标签是纯视觉噪音，还会让人以为存在别的层。**出现第二种层时才显示**——那一刻才真的需要提醒"这条不是来自你的笔记"。

**为什么便携版没有重打？**
`dist/ObsidianRAG` 是 0.2.1 的**发布产物**。为一次未发布的改动重打它，会让它变成一个版本号说不清的东西——这正是仓库里"0.2.1 安装包不含 09-16 三项界面修复"那条教训的成因。升版是独立的一步，见 `docs/发布检查清单.md` 的 8 个版本引用点。

## 五、还没解决什么

1. **没有真实记忆系统**。协议是空实现，`memory_enabled` 打开了也不会有条目——设置页会如实说明这一点，而不是假装有记忆。
2. **协议里没有冲突与取代的表达**。要接 Mem0/Zep 这类系统时，`MemoryItem` 需要加 `supersedes_id` 之类的字段。
3. **记忆召回上限是 5，且是拍出来的保守值**，不是调出来的。要等接入真实系统后用样本调。
4. **记忆条目在面板里最多显示 360 字符**（`preview` 的截断）。协议说记忆是"一句事实"，但没有任何东西强制它短——长条目会显示不全。
5. **`heading_repeat` 默认 1 → 0 仍待拍板**。它是单变量矩阵里唯一四格全不退化的候选，但依赖的那把尺子（宽松口径）刚被发现接近饱和。
6. **便携版与安装包仍未重打**，`dist/` 里还是 0.2.1 的前端。
7. **本轮的测试是先写实现后补测的**：`test_product_memory.py` 与两个前端测试文件是在接缝写完之后补的。按既有纪律应当先写测试并确认它会失败——这次只对新增的迁移测试与 SourcePanel 的两条做了"短路验证"，其余是事后补的。**下一阶段（联网）应当先写隐私边界的四条测试，再写实现。**
