# 学习记录 42：断开归类

> 日期：2026-09-19。需求来自使用者实测：批量删除把资料删光后，资料页顶部的文件夹归类卡片（「大模型 98/101」→「0/101」）依然留着，卡片上只有「刷新」——前后端都没有删除归类的入口。

## 一、为什么删光资料归类还在

「移除资料」是软删（`documents.removed_at` 标记，行与版本快照都保留，收藏与历史引用不悬空）。文件夹来源的资料还有第二层：文件在磁盘上，刷新时 `_import_folder_file` 会把 `removed_at` 清掉重新导入（学习记录 40 的确认文案专门说过这件事）。

归类（`libraries` 行）与文档是两级：删文档不动 `libraries`。所以删光 101 篇后，归类卡片必然还在——这是设计使然，但缺一个「不要这个来源了」的出口。

## 二、方案：断开（`DELETE /api/v1/libraries/{id}`）

语义一句话：**停用来源 + 其下资料一并移除 + 原文件夹与文件不动**。

- `materials.remove_library()`：一次事务里 `libraries.active=0` + 该来源下未移除文档全部软删；`_publish_snapshot()` 只调一次（理由同批量删除：逐条删会重建 N 次索引版本）。
- 界面立即消失的三个理由：`list_libraries`/`list_documents` 都是 `active=1` 视角；快照查询也带 `active=1`（见下）；`connect_folder` 的「已连接」判断只看 `active=1`，同一路径重新连接会创建新归类从头导入，旧软删行不复用。
- uploads 库不是「归类」（没有磁盘目录语义），断开回 422 `library_not_removable`，逐篇移除即可；未知 id 保持 404。
- 前端 `DisconnectBar`（`BatchDelete.tsx`）：与 `BatchDeleteBar` 同一套两段式与结果口径，但没有「已选 N 项」的 idle 相——第一段确认就是卡片上的「断开」按钮本身。确认文案两条：资料将从工作台移除不再可搜索；**原文件夹与文件不会被删除，重新连接即可再次导入**。

## 三、竞态防护：快照查询加 `libraries.active=1`

断开与刷新扫描并发时的坏路径：`_scan_folder` 开头查过一次 `active=1`，之后断开发生，扫描继续跑，中途 `_import_folder_file` 把个别文档的 `removed_at` 清掉（「复活」），扫描收尾 `_publish_snapshot()` 把复活文档带进检索——来源已经停用，资料却还能被搜到。

修法是把 `_load_snapshot` / `_publish_snapshot` 的查询都加上：

```sql
JOIN libraries l ON l.id=d.library_id AND l.active=1
```

来源停用 ⇒ 资料进不了快照，无论它的 `removed_at` 是什么。代价是快照查询多一次 join，可忽略。

## 四、验证

- 后端：`tests.test_product_materials` 20 项（+5：断开主流程、重连重新导入、uploads 422、未知 404、复活防护），全库 330 项；短路 3 点全挂（`.workbuddy/shortcircuit_library.py`：去掉快照 active 过滤 / 不 deactivate / 不软删）。
- 前端：vitest 128 项（+2：断开主流程、取消不发请求）；`tsc -b` + `vite build` 过，产物含 `library-disconnect`。
- 交付版界面验收 7/7（`.workbuddy/accept_disconnect.cjs`）：按钮渲染 → 确认条文案（含「不提永久删除」纪律断言）→ 再想想取消 → 确认 → 结果条「已断开，移除 2 篇资料」→ 点完成后卡片收起。对真实实例（8765）只做「按钮渲染 + 取消」，真断开在临时实例（8795）上走。
- **真实用户即最终验收**：重启实例自动弹的浏览器标签里，使用者自己把「大模型」「Linux学习」两个归类都断开了（DB 查证：两库 `active=0`、103 篇文档全部 removed、Obsidian Vault 原文件未动）——这正是他报这个问题的原始诉求。

## 五、教训

1. **「防护生效」的测试必须走防护挡的那条路**。复活测试初版只改库不发布快照——复活文档根本进不了内存快照，去掉 active 过滤测试照样过，是空壳。短路验证把它抓了出来：改成显式调 `_publish_snapshot()` 模拟扫描收尾，短路才如期挂。
2. **npm.cmd 链路在 Git Bash 会话里会解析错 node**：`npm.cmd exec node` 甚至从 registry 自动下载 node@26.9.0 的 npm 包来跑——vitest 的 worker 继承这个错乱环境，撞上 vitest 5.0.1 不兼容的 node 26，报 "Vitest failed to find the runner"，16 个文件 0 用例收集。**前端测试/构建改走 `cd web && ./node_modules/.bin/vitest run`、`./node_modules/.bin/tsc -b && ./node_modules/.bin/vite build`**（bin 的 sh shim 用 PATH 里的 managed node 22，一切正常）。症状特征：全套件失败 + 0 用例收集 = 环境问题，不是代码。
3. **CDP 断言要等数据渲染**：固定 sleep 1.5 秒，真实库 4 个并发请求没回来，断言落在骨架屏上（按钮 0 个的假 FAIL）。改成轮询等特征元素（最多 15 秒），等不到再断言。
4. **取确认条文案要取容器**：testid 在确认按钮上，按钮的 `textContent` 只有「确认断开」——要 `closest('.batch-bar')` 才拿到整条文案。同理，「卡片消失」的断言要放在点「完成」之后：完成才触发 `load()` 刷新（与批量删除同一交互模式）。
