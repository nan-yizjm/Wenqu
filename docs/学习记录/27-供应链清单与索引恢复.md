# 阶段 27：供应链清单与索引备份恢复

日期：2026-09-14

## 1. 这一阶段解决什么

前一阶段已经能把服务装进容器，但“镜像曾经跑通”不等于以后还能回答下面三个问题：

1. 当前服务究竟由哪些源码、配置和依赖组成？
2. 当前索引损坏或目录丢失后，能否从备份恢复？
3. 恢复出来的文件只是哈希正确，还是确实能完成一次 RAG 问答？

本阶段新增两个边界不同的产物：

- **可分享的供应链清单**：只有版本、统计量、依赖版本和 SHA-256，不含绝对私人路径、笔记文件名、正文或密钥值。
- **不可公开的索引备份**：包含 `documents.json`、`chunks.json` 和向量矩阵，因此含有私人笔记派生内容，只能保存在被 Git 忽略的目录或受保护的备份介质。

这两个产物不能合并。清单用于盘点和比较；备份用于恢复真实数据。

## 2. 新增入口与核心数据结构

| 文件 | 作用 |
|---|---|
| `src/index_backup.py` | 创建、校验和恢复索引 ZIP |
| `src/recovery_drill.py` | 自动演练有效备份、篡改拒绝、新目录恢复和真实问答 |
| `src/release_manifest.py` | 生成源码、依赖、镜像和索引的公开清单 |
| `tests/test_index_backup.py` | 覆盖篡改、路径穿越、已有目标和恢复成功 |
| `tests/test_release_manifest.py` | 覆盖隐私字段、稳定哈希和外部命令超时 |

备份 ZIP 只有五个白名单成员：

```text
recovery_manifest.json
index/manifest.json
index/documents.json
index/chunks.json
index/vector_index.npz
```

`recovery_manifest.json` 保存每个成员的字节数和 SHA-256。`index/manifest.json` 原有的三项制品哈希仍保留，因此校验是两层的：

```text
ZIP 成员白名单
    ↓
恢复清单的大小与哈希
    ↓
索引清单的版本与制品哈希
    ↓
写入临时目录
    ↓
IndexStore.current() 再校验
    ↓
原子发布为新的目标目录
```

恢复没有 `--force`：目标只要已经存在，就拒绝覆盖或合并。即使恢复失败，也不会修改源索引或当前服务正在读取的目录。

## 3. 为什么不能直接复制目录

直接复制 `current.json` 和 `versions/` 有几个常见问题：

- 复制过程中进程中断，会得到半份目录；
- 只验证 ZIP 能解压，只证明 CRC 正常，不证明内容仍是备份时的内容；
- `extractall` 面对不可信文件名可能发生路径穿越；
- 恢复到当前索引目录会覆盖一个仍可工作的版本；
- 只检查文件存在，无法发现向量矩阵和 chunk 顺序不再对应。

本实现只接受固定成员名，不调用 `extractall`，逐个读取预期成员；恢复先进入同一父目录下的临时目录，完成 `IndexStore` 校验后才通过目录重命名发布。

## 4. 真实恢复演练

演练对象是 Windows 日常索引，而不是伪造测试数据：

| 项目 | 实际结果 |
|---|---|
| 源版本 | `20260912T062623795056Z-2d6e3a20` |
| 文档 / chunks | 56 / 911 |
| 备份大小 | 1,875,278 bytes |
| 备份 SHA-256 | `552e7d8689cd34fb835da401e90283b2cc5e6c71533486e51f996d5a01c8d06c` |
| 篡改方式 | 给 `index/chunks.json` 增加一个换行，再构造 CRC 正常的新 ZIP |
| 篡改结果 | `ValueError: 备份成员校验失败：index/chunks.json` |
| 失败目标 | 没有创建 |

| 恢复后问答耗时 | 5093.66 ms |

恢复后的实际答案是：

> PagedAttention 是一种优化技术，用于管理 KV Cache，类似于操作系统中的分页机制，旨在减少 KV Cache 中的碎片问题 [S1]。

这次验证比“文件能打开”多了一层：向量索引能够按当前环境只读加载，检索、上下文、生成和引用校验都走完了。但它仍不是灾备全覆盖，因为 Ollama 模型和 E5 缓存这次没有从零恢复。

## 5. 公开供应链清单记录什么

最终清单记录：

- 30 个构建配方、运行时源码和恢复工具文件的路径、大小、SHA-256；
- 源码清单整体哈希 `99ee1c4fcba8b3f9ad0cf7e345096b5489ca61c1f39f2d8706d46944e0600245`；
- Git HEAD、分支、是否 dirty 和变更条目数，但不写 diff 内容；
- 本机 Python 及 RAG 相关包版本；
- 索引版本、统计量、三个制品哈希和构建管线版本；
- Docker 可用时的 image ID、大小、rootfs diff IDs、容器内 pip 包列表；
- Docker 可用时逐个比较镜像内 `/app/src/*.py` 与宿主源码哈希。

最终清单的 payload SHA-256 是：

```text
d4f4c8e3546f928b29b71ed5fa568ccb58acd78fcbe25f793e0d73b4a01b899d
```

它明确记录当时 Git 工作区是 dirty，共 94 个状态条目。这不是错误：它说明清单对应尚未提交的工作树，而不是把旧 commit 冒充当前源码。

## 6. 本轮遇到的三个真实问题

### 6.1 隐私说明自己触发隐私检查

第一版公开摘要没有私人路径，但 `privacy` 的说明文字直接复述了被禁止的内部字段名。测试因此失败：

```text
AssertionError: 'vault_dir' unexpectedly found
```

修复不是删除检查，而是把说明改成“省略笔记定位信息与正文”。这说明敏感扫描面对的是最终序列化产物，不会猜测某个字符串只是说明还是数据。

### 6.2 Docker 进程存在，但 daemon 永久不响应

Docker Desktop 启动后可以看到桌面和 backend 进程，但两次有界探测都在 20 秒后超时。第一版 `release_manifest` 只处理返回码和 `OSError`，所以 `docker image inspect` 把整个清单生成挂住。

修复后，所有外部命令都有硬超时：普通命令 20 秒，容器内包清单和源码哈希 60 秒。超时被转换为返回码 124 和可记录的原因：

```text
container_image.available = false
container_image.reason = "command timed out after 20s"
```

这比无限等待或沿用阶段 26 的旧镜像结果更诚实。供应链清单允许部分可用，但不能把未采集的镜像证据写成已验证。

### 6.3 Docker 的优雅停止也超时

因为管理 daemon 本身不响应，`docker desktop stop` 同样没有完成。确认没有启动任何容器后，只终止了本轮 23:11～23:12 启动且进程名严格匹配的 Docker Desktop/backend PID，未删除镜像、卷、缓存或 WSL 数据。最终这些进程均已停止。

这类问题说明“给子进程超时”与“给 HTTP 请求超时”同等重要。健康检查也不能仅凭桌面进程存在来判断 Docker 可用。

## 7. 如何复现

在项目目录执行：

```powershell
$stamp = Get-Date -Format 'yyyyMMdd_HHmmss_ffffff'
$backup = ".\data\generated\index-backup-$stamp.zip"

.\.venv\Scripts\python.exe -X utf8 -m src.index_backup create `
  --store .\data\generated\index_store `
  --output $backup

.\.venv\Scripts\python.exe -X utf8 -m src.index_backup verify $backup

.\.venv\Scripts\python.exe -X utf8 -m src.index_backup restore `
  $backup ".\data\generated\restored-index-$stamp"
```

完整演练，包括故意篡改和恢复后真实问答：

```powershell
.\.venv\Scripts\python.exe -X utf8 -m src.recovery_drill `
  --store .\data\generated\index_store `
  --runtime-config .\rag.toml
```

生成公开清单；Docker 不可用时仍会生成部分清单并显式标记：

```powershell
.\.venv\Scripts\python.exe -X utf8 -m src.release_manifest `
  --store .\data\generated\index_store `
  --image obsidian-rag:local
```

## 8. 常见故障应该怎样理解

| 现象 | 含义 | 正确处理 |
|---|---|---|
| `目标已存在` | 工具在阻止覆盖当前数据 | 使用新目录；人工验证后再改服务配置 |
| `备份成员校验失败` | 字节已变化，即使 ZIP CRC 正常 | 不恢复；回到可信备份源重新复制 |
| `额外成员` / `非法路径` | 归档超出固定格式或有路径穿越风险 | 拒绝整个归档，不选择性忽略 |
| 镜像 `available=false` | 当前机器没有采集到镜像证据 | 修复 daemon 后重跑；不要引用旧结果顶替 |
| `source_matches_host=false` | 本地源码与现有镜像不是同一份 | 重建镜像或明确部署旧镜像，不能混写版本 |
| 恢复后 Runtime 拒绝 Vault | 索引记录的来源身份与配置不一致 | 使用与备份对应的 Vault 挂载/配置，不篡改清单 |

## 9. 这些哈希不能证明什么

SHA-256 可以高概率发现字节变化，但不能证明：

- 最初生成这些字节的人或 CI 是可信的；
- Docker base image 没有漏洞；
- 依赖来源没有被入侵；
- 私人备份已加密；
- 清单没有被攻击者连同制品一起替换。

因此当前结果是 **inventory + integrity check**，不是代码签名、SLSA provenance、SBOM 漏洞审计或完整灾备。

## 10. 尚未解决

- 目前校验会把整个 ZIP 成员读入内存；对数十 GB 索引应改成流式哈希和流式恢复。
- ZIP 没有加密；敏感备份需要使用受控存储或单独的加密方案。
- 没有远端副本、保留周期、RPO/RTO 和定期自动恢复演练。
- 模型权重与 Hugging Face 缓存未纳入备份；当前只登记模型名和固定 revision。
- Docker daemon 本轮不可用，所以最终清单没有新的镜像内依赖和源码匹配证据；阶段 26 的成功结果只能作为历史记录。
- 没有签名、漏洞扫描和构建证明。

下一阶段不急着堆 Kubernetes。更有价值的是把现有索引、服务和模型的运行配置统一成一次可重复的“发布候选验收”，并明确失败时阻止切换。

## 11. 练习与参考答案

### 练习 1

为什么损坏测试要重新构造一个 CRC 正常的 ZIP，而不是随便翻转压缩文件里的一个字节？

参考答案：随便翻转通常先触发 ZIP CRC 或解压错误，只能证明 ZIP 自带校验有效。重新构造后 CRC 与新内容匹配，仍被恢复清单中的旧 SHA-256 拒绝，才能证明应用层完整性校验确实生效。

### 练习 2

为什么恢复工具没有 `--force`？

参考答案：恢复是低频高风险操作。覆盖模式会把路径写错、备份选错或恢复中断直接变成现有索引损坏。恢复到新目录后验证，再由配置或部署层切换，失败域更小，也保留回退路径。

### 练习 3

镜像进程存在，为什么还要给 `docker image inspect` 设置超时？

参考答案：CLI 需要与 daemon 通信；桌面进程存在不代表 named pipe、虚拟机或引擎已就绪。外部依赖可能不返回，只有硬超时才能保证诊断工具本身不会成为新的不可用点。

### 练习 4

如果公开清单和备份都有 SHA-256，为什么公开清单仍不能代替备份？

参考答案：哈希只是固定长度指纹，不能从哈希还原 `chunks.json` 或向量矩阵。清单用来确认“拿到的制品是不是预期制品”；备份才保存恢复所需的实际字节。
