# 学习记录 49：产出的渲染形态

> 起因是一句用户反馈：**"学习指南、思维导图的渲染有问题，并且不够精美好看"**。
> 查下去发现两件事：主观的"不好看"背后是三处**客观缺陷**（一处形态退化、一处结构性
> 冗余、一处静默丢内容），而且其中两处**测试和指标都是绿的**。

## 一、先看真实产出，别先看代码

判断"渲染有问题"不能靠读代码推。三个探针同时上：

| 探针 | 看什么 | 拿到什么 |
| --- | --- | --- |
| `.workbuddy/studio_preview.py` | 产出**落库前的原文**（指南 Markdown / 导图树形） | 指南八句陈述之间只有一个 `\n`；树是三层同义套娃 |
| `.workbuddy/studio_shots.cjs` | 界面上**渲染后的 DOM** | `段落数: 1`、`引用按钮: 8` —— 八句挤在一个 `<p>` 里 |
| `.workbuddy/inspect_mindmap.cjs` | 元素的**计算样式** | 树线是画出来了（`1px / rgb(225,223,215)`），而分组 chip 的底是 `rgba(0,0,0,0)` |

第三个探针是这一轮最值钱的一个。1px 的线在缩略截图里根本看不清，"有没有画出来"靠眼睛
判断会得出错误结论；而"chip 的底色是透明的"这种事，肉眼看只觉得"淡"，只有读计算样式
才知道是变量名写错了（见 §五）。

## 二、缺陷一：八句陈述被 Markdown 合并成一段

**症状**：指南正文在界面上是一大坨，八句话连成一片，中间还夹着八个引用按钮。

**根因**：`render_json_guide` 把每句渲染成**普通行**，行间只隔一个 `\n`。Markdown 的软换行
规则会把段落内的单换行渲染成**空格**——所以八行源码渲染成一个 `<p>`。这是我上一轮改
"逐句 JSON"时引入的：以前模型自己写 Markdown（段间有空行），换成程序渲染后就撞上了这条规则。

**修法**（`src/product/studio.py:render_json_guide`）：每句渲染成**列表项**：

```markdown
## 融合
- 两路召回的名次用 RRF（倒数排名合并，k 取 60 是常见默认值。 [S1]
- 融合之后再接重排，效果通常比单独调 RRF 参数更明显。 [S1]
```

为什么是列表而不是"给每句加空行"：

- 列表项天然一行一条，不存在被合并的问题；
- **仍然是"一行一句"**，所以 `backlink_report` 数的还是句子数——命中率的口径一点没变
  （若改成"同源句子合成一段"，断言数会从 8 掉到 4，那等于把句子级的指标偷换成段落级）；
- 在 Obsidian 场景里，带 `[S1]` 的 bullet 本来就是标准形态，复制过去能直接用。

配套：`_assertion_lines` 的**判定**仍按原行（列表项算断言），只在"缺来源"清单的**展示**
上去掉 `- ` 前缀（`_display_text`）。判定与展示分开，两者都有测试钉着。

## 三、缺陷二：思维导图的第一层是"文件名 = 文档标题"的套娃

**症状**：树是 `主题根 → 检索与融合.md → 检索与融合 → 融合/重排/…`，真正有用的章节被压到
第四层，前三层几乎同名。

**根因**：`build_mindmap` 本来就有一条"首段与文档标题重复就去掉一层"的规则，但它用**逐字
相等**判断：

- `title` 来自文件名 → `检索与融合.md`（带扩展名）
- `heading_path` 首段来自文档里的一级标题 → `检索与融合`（不带）
- 同一个东西，逐字比较判成两件事 ⇒ 那层没被去掉。

**为什么测试没抓住**：既有夹具写的是 `source(1, "推理.md", "推理.md > 推理 > PagedAttention")`
——**首段带 `.md`**，逐字相等成立、折叠生效、测试通过。而真实数据里 `heading_path` 首段
**从来不带扩展名**（`materials.py:84` 的 `" > ".join(headings)` 用的是文档内的标题文本）。
**夹具造了一个不存在的输入，于是测试绿着、功能坏着。**

**修法**：`_same_title` 去扩展名后比较（同时覆盖 pdf / 无 H1 的 md —— 那两种情况下首段
**就是**文件名）。夹具一起改成真实形状，并扩成四种真实输入（pdf、无 H1 的 md、有 H1 的 md、
`.markdown` 后缀），外加一条"文件名与文档标题不同名时**不能**折叠"。

**顺带加了 `aggregate`**：文档层节点自己没有片段，界面上"这篇笔记用到了什么"因此是空白。
每个节点补一个"自己 + 后代"的编号并集，前端只在节点**自己没有** `sources` 时显示它——
父节点只显示 `S1` 是骗人的（它下面还有 S2–S4），而把每个编号在每层祖先上重复一遍又太吵。
字段是可选的，因为此前落库的产出里没有它。

## 四、缺陷三（最严重）：`sections` 键被重复，内容静默丢掉大半

**症状**：连跑三次指南，两次只产出 2 句（另一次 12 句）。命中率**都是 100%**。

**根因**：qwen2.5:7b 在长指南上会这样吐：

```json
{"sections": [{"h": "融合"}, ...], "sections": [{"h": "重排"}, ...], "sections": [{"h": "评测"}, ...]}
```

**同一个对象里重复了 `sections` 键**。标准解析只保留最后一个 → 十二条陈述剩两条。而剩下的
那两条都带来源 ⇒ **命中率仍然 100%**。

这是本项目最不能接受的一类缺陷：**数字对、内容少、界面看不出异常**。它和"编造来源"是
两个反面——前者多说了没有证据的话，后者**少了本该说出的话，还报了一个满分**。

**量化**（`.workbuddy/degradation_check.py`，同一主题连跑 5 次，对每份真实 raw 分别用旧解析
和新渲染器算句子数）：

| 轮次 | raw | 旧解析（只留最后一个键） | 新渲染（按顺序合并） |
| --- | --- | --- | --- |
| 1 | 782 B | 2 句 · 100% | **12 句 · 100%** |
| 2 | 753 B | 4 句 · 100% | **12 句 · 100%** |
| 3 | 138 B | 2 句 · 100% | 2 句 · 100%（模型这次确实只写了两句） |
| 4 | 782 B | 2 句 · 100% | **12 句 · 100%** |
| 5 | 782 B | 2 句 · 100% | **12 句 · 100%** |

**5 次里 4 次的内容在修复前被静默丢掉 6–10 句。**

**修法**：渲染层接住坏形状，但**不猜内容**——只把模型已经写出来的东西拼回去。

- `_gather_sections`（`object_pairs_hook`）：把同一个对象里重复的 `sections` 按出现顺序合并；
  用 `_Sections` 子类区别于"顶层本来就是数组"，不带 `sections` 键的对象一律不算小节来源。
- 解码改为 `raw_decode` 循环：多个并列的顶层对象也接得住；**尾部半截**（模型写崩或被截断）
  不影响已经拿到的部分。
- 既有失败语义一条不动：`不是 JSON` → `json_parse_failed`、`没有 sections` → `json_shape_failed`、
  空小节 → `json_empty`。

四条新测试把退化形状钉住（重复键、并列对象、半截尾巴、裸数组）。

## 五、缺陷四：CSS 引用了不存在的变量

**症状**：导图分组层的编号 chip "看起来有点透明"。探针给出 `背景: rgba(0, 0, 0, 0)`。

**根因**：我写了 `var(--surface-3)`，而这套 token 只定义到 `--surface-2`。**`var()` 引用未定义
的变量不报错，只是静默回落到初始值**——颜色类的初始值就是透明。于是那个 chip 一直是透明底。

**这是门禁的缺口**：`check_css_tokens.ps1` 一直查"定义了但没使用"，却从没查过"**使用了但没定义**"。
补上这条检查（PS 脚本 + 同步进 skill 的 `check_theme_blocks.py`）。检查一上线就报出 8 个变量，
其中 7 个是 PDF.js 在运行时写内联样式的（`--scale-factor` / `--total-scale-factor` / `--rotate` …），
**内置进白名单**（跨项目一样），项目另有自定义的用 `--extra-runtime` 追加。

## 六、观感：把"缩进列表"变成"树"

纯 CSS 改动（组件标记没有为它新增容器）：

- **树线**：竖线由每个子节点自己画一段（`:last-child` 只画到横线处，否则末端的线会悬空），
  横线接在节点左侧。颜色用 `--accent-border` 而不是 `--border`——后者在 1:1 下几乎看不见
  （这是先在截图上试错、再用计算样式确认的）。
- **文档层做成分组条**：浅底 + 内描边 + 圆角，并且 `display: inline-flex`（**不撑满整行**，
  贴合内容才像"标签"而不是"标题栏"）。
- **编号分两级**：自己带的编号用强调色 chip；分组层的聚合编号用白底灰字 chip，一眼能区分
  "这个节点的编号"和"这一组包含的编号"。
- **指南**：小节标题加左侧强调竖条（3px `--accent-border`）——这样和页面 h2（25px）在视觉上
  是两个层级，不会再糊在一起；列表项间距 3px → 8px，列表标记用 `--accent-muted`。

## 八、教训

1. **"渲染有问题"要先量，不要先猜。** 这一轮三个探针分别定位到形态、样式、内容三个层面；
   其中"树线看不见"如果我凭缩略截图下结论，会得出"CSS 没生效"的错误判断（它其实生效了，
   只是颜色淡）。
2. **夹具必须是真实数据的形状。** 导图那条折叠规则一直有测试罩着，但夹具的 `heading_path`
   首段带了扩展名——真实数据不带。**测试绿、功能坏，差别就在这个字符上。**
3. **最危险的缺陷是让指标变好看的那种。** 内容丢掉 80% 时命中率从 100% 变成 100%——
   一个只看指标的验收流程对它是完全失明的。所以这次加了"句子数"这个**内容量**的观察，
   而不是只看命中率。
4. **`var()` 的静默回落值得单独设一道门禁。** 未定义的变量不报错，只是让某个颜色变成透明；
   同类风险还有 `env()`、字体族回退——凡是"写错了不报错"的地方都该有静态检查兜着。
