# 阶段 16：真正训练一次，并验证断点恢复

日期：2026-09-12。接续 [模型与数据准备](15-小型Decoder与数据准备.md)。本章记录已经执行的实验，不是待执行计划。

## 1. 先看结果与边界

443904 个参数（约 0.444M）的字符级模型在本机 GPU 完成 300 次优化器更新。中途在第 100 步保存，退出进程，随后恢复到 300 步；另一次从 0 连续训练到 300 步，用于核对恢复是否正确。

验证 NLL 从 4.9995 降到 0.1291，生成从杂乱字符变成了训练题材的短文。但语料模板高度重复，模型仍不会回答技术问题；它不是新的通用 LLM，也没有替换 RAG 中的 Qwen。

## 2. 每一步训练到底做什么

先读 `src/train_tiny_lm.py` 的主循环，再读保存和报告代码：

```python
model.train()
# 从训练窗口中有放回抽取 batch；使用单独的随机数生成器
optimizer.zero_grad(set_to_none=True)
logits, _ = model(x)
loss = next_token_loss(logits, y)
loss.backward()
clip_grad_norm_(model.parameters(), max_norm=1.0, error_if_nonfinite=True)
optimizer.step()
```

这段省略了设备搬运、学习率和有限值检查，只展示顺序，不是替换整段实现的补丁。

1. 前向计算得出每个位置的词表 logits。
2. 用真实的下一字符作为标签计算损失；PAD 标签忽略。
3. backward 根据链式法则累积参数梯度，此时权重还没更新。
4. 裁剪过大的全局梯度范数，非有限梯度则停止。
5. AdamW 使用梯度、内部动量状态和当前学习率更新参数。

`zero_grad` 不是重置权重，而是清除上一次的梯度。这里每一步只用一个 batch，没有实现梯度累积；如果忘记清除，就变成了非预期的累积。

训练使用 FP32，没有 AMP、梯度检查点、分布式训练或训练用 KV Cache。这样便于追踪基本流程，不把这些后续功能假装已经学完。

## 3. 怎样理解这份配置

配置在 `tiny_lm.toml`，和 RAG 参数分开。

| 参数 | 本次值 | 意义 |
|---|---:|---|
| steps | 300 | 总优化器更新次数，不是 epoch 数 |
| batch_size | 16 | 每一步抽取的窗口数 |
| block_size | 96 | 每个窗口的最大输入位置数 |
| learning_rate | 0.0005 | warmup 结束时的基准学习率 |
| warmup_steps | 20 | 前 20 步线性增加学习率 |
| weight_decay | 0.01 | AdamW 的权重衰减参数 |
| grad_clip | 1.0 | 全局梯度范数上限 |
| eval_every | 50 | 每 50 步跑完整训练/验证窗口的评估 |

20 步之后按余弦下降，第 300 步为 0.00005，即基准的 10%。这不是自动调参得到的最优配置，只是一份足够跑通教学流程的固定起点。

窗口采用有放回抽样，不保证每个 epoch 遍历一次。长短尾窗被同样概率选中，训练 batch loss 又按该 batch 有效 token 平均，所以它也不等于对所有文档/字符均匀采样的训练过程。完整评估另行遍历所有窗口。

`--stop-after 100` 只表示本次进程跑到 100，计划总数仍是 300。不要把 TOML 的 steps 改成 100 跑完，再改成 300 冒充断点恢复：那会改变第一段的学习率曲线。

## 4. Loss 是怎么汇总的

交叉熵接收未归一化 logits 和整数目标；这里等价于对正确下一字符的负对数概率取平均。代码将 `[B,T,V]` 展为 `[B*T,V]`，标签 `[B,T]` 展为 `[B*T]`，忽略 -100。本机接口已与 [PyTorch 交叉熵文档](https://docs.pytorch.org/docs/main/generated/torch.nn.CrossEntropyLoss.html) 核对。

每次完整评估采用：

```text
NLL = 所有有效目标的损失之和 / 有效目标总数
```

不能先算各 batch 平均再直接平均：最后一个 batch 和尾窗有效 token 数不同，那会给一些字符不合理的额外权重。当前训练有效目标 11194 个，验证 2854 个，PAD 不计入分母。

评估同时调用 `model.eval()` 和 `torch.inference_mode()`，前者关掉 dropout，后者禁用梯度相关工作；结束后恢复原模式。训练模式下启用 dropout 的最后一个 batch loss，和 eval 模式的全量训练 NLL，不是同一个指标。

历史报告中 `last_batch_loss_before_update` 是更新前那个 batch 的 loss，`grad_norm_before_clip` 是裁剪前范数，不是裁剪后的值。

## 5. 实际训练轨迹

| Step | 完整训练 NLL | 验证 NLL |
|---:|---:|---:|
| 0 | 5.0012 | 4.9995 |
| 50 | 1.6329 | 1.6456 |
| 100 | 0.3692 | 0.3773 |
| 150 | 0.1895 | 0.1956 |
| 200 | 0.1472 | 0.1497 |
| 250 | 0.1328 | 0.1350 |
| 300 | 0.1270 | 0.1291 |

验证 perplexity 从约 148.34 降至 1.14，计算为 `exp(NLL)`。NLL 不是错误率，不能解释成“准确率 87.1%”；字符级 perplexity 也不能直接拿去和不同 tokenizer 的大模型比较。

这里验证集用于选择 best，没有独立测试集。训练和验证曲线接近，与共享模板的容易任务相符，不能据此宣称对任意中文都泛化良好。

第 0→100 步这次调用内部计时约 2.809 秒，第 100→300 步恢复调用约 3.014 秒；不含 Python 进程启动/导入全部开销，含调用内的评估与保存，不是纯 GPU kernel 吞吐。它们也不能直接拿来比较谁训练更快。

本次训练循环观测到 PyTorch 峰值分配约 105.49 MiB，allocator 预留约 132 MiB。这是当前进程、当前小模型的口径，不是 `nvidia-smi` 整卡占用，更不能推断 7B 模型也能这样训练。

## 6. 不只保留成功样例

相同前缀“小周来到”，训练前输出：

```text
小周来到发明整真样日责任真整样日责纸读需并次样日并原开整纸练天方方全标练任馆需并束始始始知第始的续查陈曲
```

第 100 步已经形成句式，但重复动作：

```text
小周来到工作室，准备处理今天的项目记录。第一步是检查材料，第二步是检查材料。遇到不清楚的地方，小周会先记
```

第 300 步：

```text
小周来到工作室，准备处理今天的项目记录。第一步是检查材料，第二步是标记编号。遇到不清楚的地方，小周会先记
```

这里尾部被 `max_new_tokens=48` 截断，报告是 `max_new_tokens`，不是模型已经完整写完。生成器还分别报告 `eos` 和 `context_limit`，便于区分模型主动结束、输出预算到达、位置窗口到达。

其他真实问题：

- 第 100 步，用“工作结束时，”开头时，前面人物为小许，后面突然变成小周；这是当时的身份不一致，不冒充第 300 步仍原样出现。
- 第 300 步，同一前缀仍生成“工作结束时，小周负责整理项目记录。开始工作以前，小周先检查材料是否齐全……”，结束后又回到开始，时间逻辑不自然。
- 第 300 步，用训练分布外的“什么是注意力？”实际得到 `什么是<UNK><UNK><UNK><UNK>在纸上。`，随后 EOS。词表缺少相关字符，模型也没学过这类问答行为。

训练和验证时每一步都看真实前文；自由生成时看到的是自己刚生成的内容，错误会传递。这个区别，加上验证模板有限，解释了为什么 loss 很好看却仍有生成缺陷。不是把所有问题都归因于“模型太小”就结束分析。

## 7. 断点要保存的远不止权重

| 文件 | 保存内容 | 用途 |
|---|---|---|
| `best.pt` | 最佳验证步的模型 state_dict、结构配置、词表、实验身份 | 加载后生成 |
| `last.pt` | 当前权重、AdamW 状态、step、CPU/CUDA RNG、抽样 RNG、历史最佳权重及记录、实验身份 | 继续同一次训练计划 |
| `history.json` | 各评估步的 NLL、有效 token 数、学习率、梯度信息 | 观察曲线 |
| `summary.json` | 数据统计、前后生成、运行时间、显存、父检查点哈希与限制 | 复盘本次调用 |

只保存模型权重，下一次 AdamW 的一阶、二阶统计会重新开始；只保存 seed，随机状态也会回到起点，无法知道第 100 步之后应该抽哪个 batch、使用哪个 dropout mask。

恢复流程先构建模型/优化器，再加载状态，最后恢复 RNG，避免模型初始化消耗掉恢复后的随机序列。数据抽样使用单独的 CPU Generator，也单独保存。

学习率是总计划和 step 的纯函数，所以不用另外保存 scheduler 对象；但配置里总步数和 warmup 必须不变。后续若换成有内部状态的调度器，就要重新考虑它的 checkpoint。

文件通过临时文件、flush/fsync 和替换写入，减少写一半破坏旧检查点的风险。保存发生在完整验证/更新边界；Ctrl+C 或出现非有限值时，不保存被打断的半步，恢复最近一个完整 `last.pt`，可能需要重跑未保存的几步。它不是每一步都持久化，更不是任意硬件故障下的数据零丢失保证。

## 8. 这次恢复有没有真的接上

实际比较：同代码、同数据、同 PyTorch、同 GPU 上，连续 300 步与“100 + 恢复到 300”。

```text
模型配置/训练计划/源码/数据身份：相同
最终 step：300 / 300
模型每个参数：逐元素相同
AdamW 状态：相同
CPU / CUDA / batch 抽样 RNG：相同
历史指标：相同
最大参数绝对差：0.0
```

使用 `src.compare_training_checkpoints.py` 读取并递归核对状态，而不是只比最后一行 loss。两个 `.pt` 文件整体 SHA256 不同不代表参数不同，序列化文件字节与内部张量相等是不同层次的比较。

这只是本次同环境的实证。代码启用 deterministic algorithms，并在当前进程首次 CUDA 计算前配置 CUBLAS 工作空间；PyTorch 不保证跨平台、版本、设备都逐位复现，见 [官方可复现性说明](https://docs.pytorch.org/docs/main/notes/randomness.html)。没有更改 Windows 系统环境变量。

恢复校验还会拒绝源码、数据、模型结构、训练配置、设备或 torch 版本变化。修改训练源码之后，旧的严格恢复命令可能报不匹配，这是保护，不是让你关闭校验的理由。想改算法应建新实验；“只加载旧权重开始另一次训练”是另一种 warm start，当前没有单独实现该模式。

四个训练源文件被记录哈希；修改测试或学习文档不影响身份。旧实验并非凭哈希就能在任意未来环境复现，仍需要保留兼容源码和环境。

加载使用 `weights_only=True` 与 `map_location='cpu'`，保存 state_dict 而不是整个模型类实例。它减少任意 Python 对象反序列化的风险，不等于不可信检查点绝对安全；本入口只使用自己生成的文件，参见 [PyTorch 序列化说明](https://docs.pytorch.org/docs/main/notes/serialization.html)。

## 11. 常见故障怎么判断

- CUDA unavailable：这是环境/设备检查，先看 torch 是否能看到 GPU；可用 `--device cpu` 新开实验，不应把 CPU wheel 和 CUDA wheel 反复混装。
- 数据版本已存在：说明保护生效。换新 output 和配置，不清空旧结果。
- 恢复身份不匹配：核对是否改了数据、训练代码、TOML、device 或 torch；不要为了继续运行就删掉身份判断。
- 从 best.pt 恢复失败：best 用于生成，不含继续优化所需状态，恢复要用 last.pt。
- 词表 UNK：输入超出训练字符范围，不是终端 UTF8 乱码。两者排查方向不同。
- 生成半句话停了：查看 stop_reason，区别输出上限、上下文上限和 EOS。
- loss 下降但输出重复：检查自由生成和数据多样性，不只延长训练或降低评测要求。

本轮完整检查 84 项通过，包含新模型因果性、缓存位置、多层 logits、梯度、PAD 和 CPU 精确恢复；另做了上面的真实 GPU 恢复核对。`pip check` 无依赖冲突。已有 Starlette TestClient 的 httpx 弃用提醒仍存在，没有为一个未导致失败的提醒随意替换整个环境。

旧 RAG 的 56 篇/911 片段索引版本未变；原文档/chunks 快照和三个评测数据文件的 SHA256 保持一致。没有更改原始笔记、调用 DeepSeek、提交或推送 Git，也没有启动常驻训练进程。

## 12. 练习与参考答案

**练习 1：只保存 model.state_dict，再重新设 seed，能精确恢复吗？**

答案：不能。AdamW 动量、当前随机数状态、抽样位置、训练 step/计划都会影响下一次更新；seed 只是起点，不是当前状态。

**练习 2：一个 batch 有 100 个有效 token，平均 loss=1；另一个只有 10 个，平均 loss=3。总 NLL 是多少？**

答案：`(100×1 + 10×3) / 110 ≈ 1.1818`，不是 `(1+3)/2=2`。

**练习 3：用 best.pt 生成时还要保留训练 dropout 吗？**

答案：通常这类对比应关闭 dropout，并关闭梯度；本实现 generate 内部处理这两件事，结束后恢复原训练/推理模式。

**练习 4：验证 NLL 0.129 能否证明模型会解释 Attention？**

答案：不能。这里统计的是重复叙事语料上的字符预测，任务、词表、数据分布均不相同。实际域外生成已经展示了反例。

**练习 5：接下来最有意义的实验是什么？**

参考方向：保留本版管线，换成来源明确、题材更丰富的数据版本；建立按来源/模板隔离的验证和独立测试划分，观察过拟合与域外生成。之后再为一个具体行为目标做 SFT/LoRA，而不是把这个小模型扩一倍就宣布完成微调。
