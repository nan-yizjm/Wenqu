# 38 · 退出入口与诚实响应

补一个缺口：**产品在正常使用下没有退出入口。** 这一篇的重点不是"加了个按钮"，而是两个判断——**什么叫"关掉不算退出"要说清楚**，以及**做不到退出时不许报成功**。

## 一、缺口是什么

产品是个常驻的本地服务：`console=False`（没有控制台窗口）、没有托盘图标、浏览器只是它的一个客户端。于是：

- **关掉浏览器标签不会让它退出**，进程继续活着（占着内存、开着 SQLite 句柄、可能还占着模型）；
- 全前端只有两处"退出工作台"，都是**条件渲染**——一处在恢复页（数据库升级失败时才出现），一处在设置页（只在"保存后需要重启"时才出现）；
- 结果是：正常用完想退出，只能去任务管理器结束进程。

## 二、交付了什么

| 层 | 文件 | 说明 |
|---|---|---|
| 接口 | `src/product/app.py` | `POST /api/v1/system/shutdown` 改为**两种情况都说实话**（见 §三） |
| 组件 | `web/src/ExitControl.tsx` | `ExitControl`（两段式确认）+ `SignedOff`（退出后的收尾页） |
| 接线 | `web/src/App.tsx` | 侧栏常驻入口；`signedOff` 状态整页换成收尾页；设置页与恢复页复用同一个组件 |
| 样式 | `web/src/styles.css` | `.exit-control` / `.signed-off`；窄屏折成图标条时只留"退出"两个字 |
| 测试 | `tests/test_product_support.py`、`web/src/ExitControl.test.tsx` | 后端 2 项 + 前端 7 项 |
| 验收 | `scripts/ui_acceptance.cjs` | 第 12 步，5 项（真的退出时 7 项） |

原来那两处按钮**删掉了，改成复用同一个组件**：同一个动作在不同地方有三份文案和三种行为，是"看起来一致其实不一致"的经典来源。

## 三、三个判断

**1. 出口要常驻，不能只放在设置页。**

设置页那一处只在"保存后需要重启"时出现——那等于说：正常使用时没有退出入口。所以新入口挂在**侧栏底部**，任何时候都在，和资料计数挨着。这是桌面应用放"退出"的常规位置。

**2. "关标签不算退出"必须写出来，因为它是这个入口存在的理由。**

按钮下面直接一行小字：`关掉浏览器标签不会停止本地服务。` 这不是装饰文案——多数人对"本地服务 + 浏览器界面"的心智模型就是"关掉网页 = 关掉程序"，不说清楚，用户永远不知道自己漏了一步。

**3. 做不到退出时，接口不许报成功。**

原来的实现是这样：

```python
if shutdown_callback:
    shutdown_callback()
return {"status": "shutting_down"}          # ← 没有 callback 也这么回
```

`create_product_app()` 的 `shutdown_callback` 默认是 `None`（测试、以及任何没接启动器的实例都是这样）。此时它回 200 + "正在退出"，**而进程什么都不会发生**；界面照着这句话显示"已退出"，就是让产品替用户说了一句假话。

改成：

```python
if not shutdown_callback:
    return JSONResponse({"error": "shutdown_unavailable",
                         "message": "这个实例没有连接启动器，无法自行退出；请结束它的进程。"},
                        status_code=503)
shutdown_callback()
return {"status": "shutting_down",
        "message": "本地服务正在退出。资料、索引和会话都会留在原处。"}
```

这与 P2 联网那一块是同一条线——**没有搜索后端就说"未配置"，不说"没搜到"**。同一个道理换个场景就又出现一次。

顺带一句放在这里：**"退出不删数据"由接口自己在响应里说出来**，不只写在前端文案里。这是这个动作唯一的对外承诺，值得让服务端签字。

## 四、两个界面决定

**1. 两段式确认，而且不用 `window.confirm`。** 退出不可逆（要回来得重新启动），值得一次确认；但 `window.confirm` 在无头浏览器里会阻塞页面求值，验收脚本点不动它——这个坑 `ui_acceptance.cjs` 里已经为删除产出记过一次（当时是先把 `window.confirm` 短路掉）。所以确认做成页面内的状态：第一下展开"确认退出？…"+ [确认退出] [取消]，第二下才真的退。

**2. 退出之后整页换成收尾页，而不是留在原界面。** 服务已经停了，任何后续请求都会失败——留在原界面会让每个点击都报错，看起来像产品坏了，其实是**我们自己把服务关了**。收尾页只交代两件事：东西都还在（资料、索引、会话、收藏），以及下次双击图标就回来。

## 五、真实证据（2026-09-18）

跑法：源码启动交付版，数据目录是真实数据根的拷贝，然后跑验收脚本。

**默认那一遍不真的退出**（退出会关掉正在被验收的这个实例），43 项全过：

## 六、决定不做：心跳 + 闲置自动退出

显然的"更聪明"做法是：前端定时发心跳，服务端发现没人连着就自己退出——这样"关掉标签"就真的等于退出了，用户什么都不用做。**没做**，四条理由：

1. **后台标签页的定时器被节流。** 浏览器会把隐藏标签页的定时器压到约 1 分钟一次（更久还有"密集节流"）。心跳窗口要么短到会误杀一个正常工作的后台标签页，要么长到基本不触发——而"挂在后台开着"是完全正常的用法。
2. **长任务会被误杀。** 导入资料、生成产出都是服务端在跑，看门狗看不见它们。要么让每个长任务都去登记"我在忙"（把看门狗和之后每个新功能耦合起来），要么接受"导到一半被关掉"。
3. **自动化场景会把自己杀掉。** 产品被脚本以 `--no-browser` 起好几分钟是仓库里的常态（`test_product_bundle.ps1`、`test_product_model.ps1`、验收脚本），那些场景**一个心跳都不发**。看门狗会把正在做验证的实例关掉——这不是假想的风险，是现成的三个调用点。
4. **关标签其实不造成损坏。** `InstanceLock` 保证再启动一次会复用正在跑的实例并把浏览器指回去。所以遗留进程的代价是内存，而不是"产品不可用"。既然如此，把"什么时候停"交给使用者（点退出）比替他猜更稳妥。

要看这条判断的原始依据，读 `src/product/launcher.py` 的 `InstanceLock` 那一段和三个 PS1 脚本的启动方式。

## 七、踩过的坑

- **入口不能被窄屏样式吃掉。** 侧栏在 ≤1000px 折成 76px 图标条，规则是 `.sidebar-status>div{display:none}`——把按钮放进那个内层 `div` 里，窄屏就**看不见退出入口**了，而这正是"正常使用下要有出口"的反面。解法：`.exit-control` 做成 `.sidebar-status` 的**兄弟节点**，并按仓库已有做法给"工作台"三个字套一个 `.exit-label`，让它跟着 `.nav-label` 一起在窄屏收掉（`title` 里保留完整说明）。
- **验收脚本不能把被测对象关掉。** "点退出"是这条链最该验的动作，但验完应用就没了，后面的断言全部作废。解法是 `UI_ACCEPT_EXIT=1` 显式开启，默认只验到"取消之后应用照旧运行"，并在输出里写清楚跳过了什么、怎么开。
- **一个动作有三份文案就是隐患。** 替换掉原来那两处按钮时要给 `Settings` 和 `Recovery` 传 `onExit`；不传就会留下两处仍直接 `api.shutdown()`、没有确认、文案也不一样的旧路径。
- 顺带一条不算坑的观察：把"没有启动器"这条路做成 503 之后，`Invoke-RestMethod` 在 PS 5.1 下对 4xx/5xx 是会抛的——但两个 PS1 脚本调的都是**接了启动器的冻结版**，走的是 200 那条，所以不受影响。

## 八、还没解决

1. **没有托盘、没有窗口，所以退出只能由页面发起的这个交互完成。** 如果浏览器标签在退出前就被关掉，还是得靠任务管理器——这一条要靠 §六 那个被否掉的心跳方案才能真正解决，而它被否掉的理由仍然成立。
2. **退出是"立即"的：** 服务端如果有正在跑的导入或生成，`server.run()` 会等它们结束（uvicorn 的 graceful shutdown），界面上却只显示"正在退出…"，看不到在等什么、还要多久。
3. **"退出后自动重启"没有做。** 两处需要重启的场景（保存设置、恢复备份）现在都是让用户自己再点一次图标。
4. **验收里的真实退出只在源码运行下验过**，`dist/ObsidianRAG` 那份冻结版没有重打、也没有重跑这条（它是 0.2.1 发布产物，不为未发布的改动重打）。
