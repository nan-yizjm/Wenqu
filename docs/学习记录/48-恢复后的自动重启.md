# 学习记录 48：恢复后的「立即重启」

> 日期：2026-09-19。补上退出/重启这条线最后一个手工步骤：恢复备份或迁移恢复之后，应用处在"待重启"状态，此前只提示"请退出后重新打开"——用户得自己回桌面再点一次图标。现在设置页与恢复页都有一键重启，并且**等服务真的回来**才刷新页面。落地过程中验证抓出两个真问题：Windows 的 `execv` 语义，和前端判据在一秒级窗口下不可靠。

## 一、机制：退出与重启共用一个出口

`shutdown` 与 `restart` 对 uvicorn 是同一件事（都要它停），区别只在停完做什么，所以启动器里只有一个 `stop(restart: bool)`：

```python
intent = {"restart": False}
def stop(restart: bool = False):
    logging.info("stop_requested restart=%s", restart)
    intent["restart"] = intent["restart"] or restart
    server.should_exit = True

create_product_app(paths, shutdown_callback=lambda: stop(False),
                          restart_callback=lambda: stop(True))
```

`server.run()` 返回、`finally` 里放掉实例锁与 `instance.json` 之后：

```python
if intent["restart"]:
    os.execv(sys.executable, relaunch_command(port))
```

顺序很重要：**锁必须先放掉**，否则新实例拿不到单实例锁；`instance.json` 也要先删，让新实例重新登记端口与 PID。

## 二、重启命令的三个决定（`relaunch_command`，纯函数、可单测）

1. **端口固定**。前端等的就是这一个端口。让新实例重新 `available_port()` 可能拿到别的号，页面就永远等不到——那看起来像"重启失败"。
2. **不再开浏览器**。用户已经在页面上；再弹一个标签页是噪音。
3. **模块名走 `-m`**。`sys.argv[0]` 是 `product_entry.py` 的路径，直接执行它会让 `sys.path[0]` 变成 `src/`，`from src.product...` 这个绝对导入就找不到包。所以源码运行必须重建 `-m <模块名>`（模块名从 `__main__.__spec__` 取）；冻结版没有这个问题，直接再执行 exe。

三件事在真实环境里各踩一次都会表现为"重启后页面一直转圈"，所以它们是纯函数并各有单测。

## 三、验证抓出的两个真问题

### Windows 的 `execv` 不是 POSIX 的 exec

第一轮验证脚本把"**PID 不变**"当判据，结果报"重启没有完成"——而日志明明显示新实例已经在同端口监听了。查证：**Windows 上没有真正的 exec**，CPython 的 `exec*` 是"起一个新进程 + 结束调用进程"，**PID 必然变化**。判据改成端口不变 + 新实例出现（后来换成了更可靠的启动时刻，见下），注释里的错误说法也一并改掉。

教训：把 POSIX 语义的直觉直接套到 Windows 上，会写出一个"永远失败"的验证——**而失败的是验证，不是功能**。这种误判最危险，因为它会让人去改没坏的东西。

### 重启窗口只有一秒，前端判据不能靠"撞上断连"

实测：停机到新实例可用之间只有 **1.3 秒**（Windows 上新进程启动 + 建 app）。前端原本的判据是"轮询到一次断连、再等它回来"——轮询间隔几百毫秒，**撞不撞得上纯看运气**，撞不上就一路等到超时、报"服务没有停下"。

改成可靠判据：`/api/v1/health` 增加 **`started_at`**（实例启动时刻，lifespan 里记）。前端重启前读一次，之后轮询到"值和之前不同"就确定是新实例——**与窗口长短无关**。老服务不返回该字段时退回"断过又回来"的旧判据。

顺带一条相关设计：`started_at` 也让"重启是否真的发生"变得可判定——服务一直活着、启动时刻没变，就是重启没生效，前端会如实报"服务没有变化"而不是假成功。

## 四、可达性：重启必须在"待重启"状态的放行名单里

恢复备份后应用进入 `restore_pending`，中间件只放行 health / shutdown 等少数入口。重启**必须**在这个名单里——用户恢复完备份，下一步该做的就是重启，被自己的中间件拦成 409 会让这条路彻底走不通。这条有专门的测试（同一条测试里顺便断言了普通接口此时确实是 409，证明名单是有意义的而不是形同虚设）。

## 五、验证

- 后端 **354 项**（+8：`relaunch_command` 5 条、restart 路由 3 条），前端 **141 项**（+4），`tsc -b` + build 过。
- 短路 3 点（`.workbuddy/shortcircuit_restart.py`）：重启命令不固定端口 → 端口替换测试挂；路由去掉启动器检查 → "如实说做不到"测试挂；前端判据退回旧逻辑 → 新判据测试挂。全部"破坏后必挂"。
- **真实验证**（`.workbuddy/restart_check.py`，端口 8816）：`started_at` 变化、等了 **1.3 秒**、**端口不变**、PID 变化（Windows 预期）、产出接口正常；launcher 日志完整（`server_stopped restart=True` → `relaunch command=[…]` → `launcher_start` → `server_start port=8816`）。
- 界面验收 **57/57** 全过（改的是设置页与恢复页的提示区，没碰既有行为）。

## 六、边界

- **冻结版 exe 的重启分支只在单测里验过**（`relaunch_command` 的 frozen 分支断言了 `[exe, ...]`），真实 exe 上的重启要等下次打包后才有得验；0.2.2 装包不含本次改动。
- 重启不重建索引文件、不重跑迁移以外的启动逻辑——它只是把应用重新起来（这正是"恢复后需要重启"要的：DB 被换掉，连接必须重开）。
- 托盘与自动重启之外的退出遗留只剩"没有托盘"（38 号已说明为什么不做托盘）。
