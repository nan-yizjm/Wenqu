# 阶段 13：先测清楚，才决定哪些工作放在 GPU

日期：2026-09-12。实现入口：`src/deployment_lab.py`。本阶段没有修改默认部署配置，没有重新分片，也没有修改笔记或评测题。

## 1. 这次要解决的实际问题

之前知道本机有 8GB 显存、E5 和 Qwen 能运行，但“都能放进 GPU”和“这样部署最合适”不是同一个问题。

本轮拆成两组实验：

1. 本地生成：同一个提示词连续请求两次，观察模型加载、输入处理和输出生成分别花了多久。
2. 检索设备：固定索引、问题和参数，分别运行 E5 CPU、E5 GPU、GPU E5 + CPU 重排、GPU E5 + GPU 重排。

第二组**不生成答案**，避免把生成模型输出长短差异混进检索设备比较。它也不是一次新的答案质量评测。

## 2. 实验入口和数据边界


## 3. 先分清“慢”发生在哪一层

`OllamaClient.chat()` 仍返回字符串，保持现有问答接口兼容；现在额外保留 `last_metrics`，由 `ollama_metrics()` 从响应中提取：

- `wall_ms`：客户端等待整次请求的时间。
- `load_ms`：Ollama 报告的模型加载时间。
- `prompt_eval_ms`：输入处理时间。
- `eval_ms`：输出 token 生成时间。
- `prompt_eval_count`、`eval_count`：对应 token 数。
- `decode_tokens_per_second`：`eval_count * 1000 / eval_ms`。

Ollama API 的 duration 单位是纳秒，转换为毫秒要除以 1,000,000。字段缺失保留 `None`，不伪填成 0；输出时长为 0 也不做除零计算。依据：[Ollama Chat API](https://docs.ollama.com/api/chat)。

`last_metrics` 只对应最近一次成功调用，不是整个 RAG 请求的累计时间。如果问答因覆盖不足进行了第二次修复调用，不能把最后一次调用的耗时冒充两次总耗时。当前 HTTP 响应的 `elapsed_ms` 仍是原来的整次问答耗时；详细拆分在这个实验入口观察。

这组调用使用固定选项：temperature 0、seed 42、最大输出 96 token、num_ctx 4096；不是更改你的日常生成参数。stream=false，因此**没有测量真实的首 token 到达时间 TTFT**。

## 4. 冷加载和第二次请求：实测

| 指标 | 第一次 | 第二次 |
|---|---:|---:|
| 请求前模型驻留 | 空列表 | Qwen 已驻留 |
| 客户端总耗时 | 3095.09 ms | 590.27 ms |
| 模型加载 | 2451.07 ms | 1.03 ms |
| 输入处理 | 72.56 ms | 14.31 ms |
| 输出生成 | 566.60 ms | 570.33 ms |
| 输出 token 数 | 42 | 42 |
| 输出速度 | 74.13 token/s | 73.64 token/s |

这里第一次慢的主要差异来自模型加载，而不是生成每个 token 慢了五倍。不能拿 `42 / 3.095` 当作模型稳态 decode 速度，再与第二次比较。

两次提示词相同，输入缓存也可能参与；本机返回结果中 `prompt_eval_cached_count` 缺失，所以没有声称“第二次命中了多少 token 的前缀缓存”。它是一组自然冷加载/重复请求观察，不是完全隔离所有缓存因素的实验。

以后运行时如果模型已经驻留，脚本如实记录，不会把“本次第一条请求”强行命名为冷启动。

## 5. E5 和重排放哪里：实测

共同条件：hybrid 检索、20 个候选、最终 5 个片段；重排启用时处理 20 个候选。时间为 9 条热检索的中位数，不是包含生成的端到端问答时间。

| 组合 | 运行时加载 | 首次检索 | 热检索中位数 | 整卡显存采样最高值 |
|---|---:|---:|---:|---:|
| E5 CPU，无重排 | 4899 ms | 57.34 ms | 13.17 ms | 5095 MiB |
| E5 GPU，无重排 | 4981 ms | 258.96 ms | 9.13 ms | 5766 MiB |
| E5 GPU，重排 CPU | 6268 ms | 1493.41 ms | 1260.18 ms | 5766 MiB |
| E5 GPU，重排 GPU | 6547 ms | 420.93 ms | 96.16 ms | 6344 MiB |

可以据此做的局部判断：

- 这里 E5 的 CPU/GPU 热查询差距只有几毫秒。显存紧张时，把 E5 放 CPU 是值得尝试的取舍，不必看到 CUDA 就把所有组件放进去。
- CPU 重排的代价明显，约 1.26 秒；GPU 重排约 96 毫秒。它们处理的是同样规模的候选，但不能把“加了重排”当作免费功能。
- 模型加载完成，不等于第一次算子执行已经热。GPU E5 首次检索约 259 毫秒，热查询约 9 毫秒，两者应分开记。
- 这次 GPU E5 + GPU 重排与外部 Ollama 共存没有 OOM，但不能推断更长上下文、更大 batch 或并发也安全。

当前没有自动把 `rag.toml` 的重排设为 GPU，也没有自动开启重排：上一阶段没有证明它一定提高最终答案质量。你可以手动改 `rerank = true`、`rerank_device = 'cuda'` 后重启体验；如果只想保持轻量检索，则继续关闭重排。

## 6. 显存数字究竟包含什么

上表的 `nvidia-smi` 是**整张卡**的使用量，包含 Ollama、桌面应用和当前 Python 进程。不能说“E5 CPU 占了 5095 MiB 显存”。CPU 组合中那一大部分显存来自卡上其他工作。

另外记录了当前 Python 进程的 PyTorch CUDA 分配峰值：

- E5 GPU：约 481.19 MiB。
- E5 GPU + CPU 重排：同样约 481.19 MiB，但 CPU 重排占用的主机内存不在这个数字里。
- E5 GPU + GPU 重排：约 997.09 MiB。

`memory_allocated`、`memory_reserved` 和 `nvidia-smi` 不是同一个口径。本版不测 CPU RSS；采样线程在一次采样完成后等待 0.5 秒，所以短峰值可能漏掉。记录名刻意使用 `sampled_peak`，不称为精确峰值。

## 7. 实现中处理的测量陷阱

**GPU 异步执行。** 使用 CPU 时钟计时，在被测调用前后同步当前 CUDA 工作，避免只测到排队/提交。这个计时包含 Python、同步和算子执行的串行延迟，不是纯 kernel 时间，也不是高并发吞吐实验。参考 [PyTorch CUDA 语义](https://docs.pytorch.org/docs/main/notes/cuda.html)。

**模型实例残留。** 同进程不断 `.to(cpu)` / `.to(cuda)` 会受到旧对象、allocator 和 CUDA context 的影响。本版各组合独立子进程；但磁盘页缓存不清空，所以加载时间仍不是严格的磁盘冷启动比较。

**测量对象改变。** `TimedComponent` 只在实验进程包装 vector search 和 reranker score，保留实际排序方法；没有为了好看的延迟换成不同候选数。

**缺失与失败。** 显存工具不可用记录 null；子进程失败记录 failed，不记成 0 毫秒。运行顺序固定、样本很少，没有严格控制笔记本温度、电源模式或后台负载，不能推广为通用硬件结论。

## 8. 参考练习

**问：为什么把 E5 从 GPU 移到 CPU，整卡显存不会变成 0？**

答：Ollama 和其他进程仍使用 GPU；CPU/GPU 选择是组件级别的，不是整机开关。

**问：怎样测重排的新增成本？**

答：固定索引、问题、候选集合规模和设备，比较相同入口启用/禁用重排；同时看 rerank_ms 与总检索时间，而不是把生成长短也混进来。本版比较了部署组合，不是保证同一文档排名或答案不变。

**问：第二次请求快很多，是 KV Cache 起作用的证明吗？**

答：不是单凭总耗时就能证明。模型加载、kernel 热身、prompt 缓存等都会影响；这里观测到最大的差异是 load_ms。下一章直接在张量层验证 KV Cache，避免把不同缓存混为一谈。
