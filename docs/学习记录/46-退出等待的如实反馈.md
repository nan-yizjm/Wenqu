# 学习记录 46：退出等待的如实反馈

> 日期：2026-09-19。38 号退出入口留下一条已知缺口："退出看起来是立即的，但服务端会等正在跑的导入/生成结束，界面看不到在等什么"。这次定性后修掉：那不是体验瑕疵，是**一句假话**——用户看到"工作台已经停止"，而进程还在等一条流跑完。

## 一、缺陷的机制

`POST /api/v1/system/shutdown` 的实现只是 `shutdown_callback()` = 把 uvicorn 的 `should_exit` 置真，然后**立即**返回 200 `shutting_down`。uvicorn 收到标志后走优雅停机：**等所有在处理的请求结束才退出**——问答/产出的流式响应（StreamingResponse）会拖住它，一条 30 秒的生成就让"退出"慢 30 秒。而前端拿到 200 就切到 `SignedOff`（"工作台已经停止"）。

于是：接口说"正在退出"（没说谎，但没说全），界面说"已经停止"（说谎）。这与 38 号自己立下的规矩——"没有启动器时如实报 503，不假装成功"——是同一条线上的漏洞：**"已退出"必须等它真的退出之后才能说**。

## 二、修法：数清楚在等什么 + 用端口死亡背书"已退出"

**后端**（`app.py` shutdown 路由）：调用 `shutdown_callback` 之前数一遍在跑的任务，塞进响应：

```json
{"status": "shutting_down",
 "waiting": {"imports": 0, "answers": 0, "artifacts": 0},
 "message": "本地服务正在退出。……正在等待 N 个进行中的任务完成（导入 x、回答 y、产出 z），可能需要一点时间。"}
```

三个计数各有出处：`materials.active_job_count()`（`import_jobs` 里 pending/running）、`chat.active_stream_count()`（`_active`）、`studio.active_count()`（`_active`）。数据库迁移失败时服务对象不存在，计数自然为 0——shutdown 在中间件白名单里必须始终可用。

**前端**（`ExitControl.tsx`）：`shutting_down` 不再触发 `onExit`。发出退出请求后进入等待态——

- 显示后端报来的任务数（"正在等待 3 个进行中的任务完成（导入 1、回答 0、产出 2），完成后自动退出。"）；没有任务就显示"正在等待本地服务停止…"；
- 每 1 秒轮询 `GET /api/v1/health`，**请求开始失败（连接拒绝）才调 `onExit()`**——端口没了是"服务真的退出"的唯一可验证信号；
- 不设等待超时：长生成可能几分钟，期间用户随时可以关标签页；取消按钮保持禁用（服务已经在退出流程里，取消没有意义）。

这样 `SignedOff` 的"工作台已经停止"从"收到 200 就显示"变成"**端口真的没了才显示**"——收尾页的每一句话都有了背书。

## 三、测试与真实验证

- 后端 **345 项**全过（新增 1：空载 `waiting` 全 0 + 塞入一条回答/一份产出/一个导入作业后三个计数各归各位；连点两次 shutdown 仍 200）。
- 前端 **132 项**全过（新增 2：等待中显示任务数且 health 存活时不退出、health 死亡后才 `onExit`；改造后原"quit → onExit"测试改为经 health 失败触发——**这是行为变化，测试跟着改是对的**）。
- 真实冒烟：临时实例（`--data-root` 临时目录、8799 端口）→ `POST shutdown` 返回上述 JSON → 3 秒后 health 无响应。空载场景全链路（含优雅停机）真实走通。

## 四、环境坑：curl 到 localhost 被代理截胡

冒烟第一次输出 `upstream connect failed: 由于目标计算机积极拒绝`——这不是产品的话，是**HTTP 代理的 502**：自动化环境里 `curl http://127.0.0.1:...` 默认走了代理。本地请求必须加 `--noproxy '*'`。诊断线索：报错的话不像任何一方的正常输出时，先问"这句话是谁说的"。

## 五、边界

- `waiting` 只覆盖三类已知的长任务（导入/回答/产出）；恢复备份、重建索引这类同步操作走 HTTP 请求本身，uvicorn 一样会等它们，但它们不在"可以显示进度"的范围里。
- 轮询 1 秒是体验值不是契约值；服务死亡由连接失败判定，不依赖响应内容——所以不存在"轮询读到了半死的服务的假 ready"的问题。
