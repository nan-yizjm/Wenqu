历史 `Source Recall@5` 的实现是“前 5 名命中任一允许的来源文件”。为避免歧义，新报告叫 **Source Hit@5**。不是“所有相关文档的召回比例”，也不判断具体片段是否支持答案。

| 开发集，26 道库内题 | BM25 | 76.9% | 92.3%（24/26） | 0.840 |
| 开发集 | 向量 | 84.6% | 92.3%（24/26） | 0.878 |
| 开发集 | 混合 | 92.3% | 100.0%（26/26） | 0.955 |
| 保留集，8 道库内题 | BM25 | 75.0% | 100.0%（8/8） | 0.823 |

| 保留集 | 混合 | 75.0% | 87.5%（7/8） | 0.812 |

每个集合各有 4 道库外题，三路均由同一个静态守卫拒绝 4/4，库内误拒绝 0。不能因此说“向量或混合检索学会了 OOD”，也不能推广成所有库外问题都能拒绝。

## 三个值得保留的案例

### 1. 好证据也可能被现有标注判失败

`retrieval-018` 的向量第一名是 `hello-agents/第8章 记忆与检索.md` 中的“RAG 系统工作原理”，明确写出在线流程。但标注只允许 `07_应用系统/应用系统.md`，所以文件命中指标判失败。

这是标注覆盖的局限，不能据此断言向量没找对；本轮只记录，没有把新答案来源偷偷加进去。将来需要单独、统一地审核标注版本，并在新旧标注下分别报告结果。

### 2. 两路各自命中，融合仍会漏

`holdout-006`：RAG、Agent 和多模态能力分别补足什么？BM25 的标注来源首次出现在第 3，向量第 5，融合后却没有进入前 5。

首次命中的来源可以对应不同 chunk；RRF 按 chunk ID 融合，不按文件投票。不同 chunk 无法互相累加，而两路共同支持的其他 chunk 会升高。因此融合不是取两路 Top-5 的简单并集，也不保证保留每个好结果。

### 3. 检索改善终于反映到一个综合回答

`gen-010` 的 BM25 回答把离线知识添加和在线查询混在一起，缺少上下文组织。Hybrid 回答包含“提问 → 检索 → 上下文压缩 → 生成”，通过现有规则。这一条是可以指向具体答案与上下文的改善，不只是汇总分数上涨。

## 本地生成端到端比较

两次都使用 Ollama 的 qwen2.5:7b、同一套旧评分规则；顺序执行 BM25 后再 Hybrid，每种只跑一次，没有挑选最好的一次，也没有调用 DeepSeek。

| 指标 | BM25 | Hybrid |
|---|---:|---:|
| 规则通过数 | 13/18 | 14/18 |
| 规则通过率 | 72.2% | 77.8% |
| 引用标签有效 | 14/14 | 14/14 |
| OOD 拒绝 | 4/4 | 4/4 |
| 运行错误 | 0 | 0 |
| 实际生成调用数 | 17 | 16 |
| 平均单题耗时 | 2345.87 ms | 1832.10 ms |

平均时间包含 OOD 的极短路径和部分题的重写调用。先后顺序、Ollama 模型热身、输出长度均影响时间；两次调用数也不同。**不能把这张表解释成 Hybrid 天生更快，也不能用一次 18 题比较宣称模型能力稳定提高。**

BM25 用词面选行，Hybrid 用原始片段正文，二者的生成比较还混合了上下文策略差异。纯检索归因应看前面的固定口径检索实验。

### 仍未解决的回答问题

- Hybrid `gen-001` 出现“推测”，还把相邻技术的描述混入 PagedAttention；即使标签有效，仍是有依据约束失败。
- 两路 `gen-012` 都缺少针对本项目的固定题集和比较口径；泛列 MMLU 等能力榜单，不等于完整回答“这个知识库助手是否变好”。
- Hybrid `gen-013`、`gen-014` 的文字确实表达了资料不足，但旧拒答短语检查未命中。保留原判分，同时注明人工观察，避免把这种失败全归因于模型。
- BM25 `gen-014` 则真的在资料不足后继续推测，并把 Agent 的 MsgHub 通信当成训练通信的参考，不能和上面的规则误判混为一谈。
- `gen-004` 通过也不代表全面正确。例如“参数减少 256 倍”仍需核对适用条件，不能只因关键词齐全就对整段事实背书。

## 当前决策

保留 BM25 为默认，vector/hybrid 作为正式可切换选项。继续保留原始失败和小规模回归检查，不为追求 100% 改写评测要求。

工程复核：41 项离线检查通过，覆盖缓存命中不重算、顺序/正文/配置变化失效、损坏缓存恢复、RRF 去重与单次降权、微小上下文预算、重复概念条目、最多一次重写等。连续入口切换与退出、报告离线阅读、旧评测模块入口、混合模式下天气问题零次生成调用均已实际执行。`git diff --check` 没有空白错误；存在 Git 的 LF/CRLF 提示，未修改用户的换行配置。

这些检查只证明相应工程路径被验证，不等于所有问答质量问题已修复。报告已保存在本地，未提交或推送 Git。


练习：两种方法的 Source Hit@5 都是 100%，为什么还要看 MRR、实际上下文和回答？参考答案：好证据可能位于第 5 而被预算截掉；文件命中也可能只是目录片段。MRR 观察排名，实际上下文观察证据是否被保留，最终回答再检查证据是否被正确使用。
