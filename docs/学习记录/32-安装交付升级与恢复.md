# 阶段 32：安装交付、升级与恢复

日期：2026-09-15

## 1. 用户问题

阶段 28～31 已经有了可用的界面和主要工作流，但“在开发环境里能跑”不等于“可以交给朋友”。真实用户会遇到下面的问题：

- 电脑没有 Python、Node.js 或 Docker；
- 安装新版后，旧资料、会话和收藏不能丢；
- 数据库升级失败时，页面仍应该能进入恢复模式；
- 不能用一个损坏或恶意 ZIP 覆盖用户数据；
- 用户提交诊断时，不应意外泄露密钥、问题、原文或本机路径。

本阶段的目标不是再增加一个问答算法，而是让现有功能可安装、可升级、可恢复、可诊断。

## 2. 交互设计

设置页增加“数据与支持”：

1. 下载完整备份；
2. 选择备份 ZIP 恢复，恢复前再次确认；
3. 恢复成功后禁止继续使用旧进程，引导退出重启；
4. 下载脱敏诊断报告。

数据库迁移失败时不进入普通主界面，而是显示独立恢复页。该页只列出迁移前自动生成的备份，允许用户选择一个恢复并重启。这种设计的重点是：故障状态下不再构造资料库、检索和问答服务，避免错误连锁扩大。

## 3. 实现

### 3.1 可校验完整备份

`SupportService` 使用 SQLite backup API 获得一致数据库快照，再收集资料副本、历史快照和导出文件。备份不包含：

- DeepSeek API Key；
- 日志；
- E5 模型缓存；
- 可从快照重建的索引。

ZIP 中的 `manifest.json` 记录备份格式、产品版本、生成时间和每个成员的字节数与 SHA-256。恢复时先在隔离目录完成所有校验，包括：

- 压缩包和展开后的大小上限；
- 文件数上限；
- 成员白名单、路径穿越和重复文件名检查；
- 清单成员集合、字节数和 SHA-256 检查；
- SQLite `quick_check` 和 schema 版本范围检查。

校验全部通过后，系统先生成 `before-restore` 安全备份，再替换数据库与快照目录。替换中出错会尝试回滚到原位置。

### 3.2 迁移失败安全模式

`Database` 不再因迁移失败让整个 Web 服务退出，而是保存 `migration_error`。产品入口据此只启用健康检查、设置概况、备份列表、恢复和退出接口；普通 API 返回 503。

恢复时只接受备份目录中已列出的精确文件名，并再次运行数据库完整性与版本检查。恢复后要求重启，因为运行中的各个 service 可能仍持有旧索引状态，不能假设替换文件后内存对象也自动更新。

### 3.3 脱敏诊断

诊断 JSON 只保留产品版本、数据库版本、后端类型、检索模型状态和数量统计。密钥只显示“是否已配置”，不读出具体值。测试使用故意显眼的私密文件名、问题、密钥和中文绝对路径，逐一确认报告中不存在它们。

### 3.4 可安装交付物

发布脚本在独立 Python 3.12 CPU 环境中安装固定产品依赖，生成 57 项运行时依赖的许可证清单，构建 React 静态资源和 PyInstaller onedir，再用 Inno Setup 生成当前用户安装程序。安装包内附带：

- 用户指南；
- 0.2.0 版本说明；
- 第三方依赖与许可证清单；
- 可直接导入的合成 Markdown 示例。

构建后自动生成安装包 SHA-256，用于分发后检查文件是否完整。

## 4. 真实故障与原因

### 故障 1：Inno Setup 已找到，却不能执行

第一次正式构建中，PyInstaller 成功，但 PowerShell 报错：

```text
The expression after '&' ... was not valid.
```

原因是 `Get-Command` 返回的对象有 `Source`，而从固定路径找到时得到的是 `FileInfo`，只有 `FullName`。脚本错误地对两种对象都访问 `Source`。修复后根据对象类型统一取出可执行路径，并重跑整个正式构建，没有用手工命令绕过故障。

### 故障 2：包内有中文文件，交付测试却说丢失

Windows PowerShell 5.1 会用本地代码页读取不带 BOM 的 UTF-8 `.ps1`。“用户指南.md”在测试进程中变成乱码，因此检查了一个并不存在的乱码文件名。最终交付脚本使用 Unicode 码点构造中文文件名，同时兼容 Windows PowerShell 5.1 和 PowerShell 7。

这个问题也说明：不能用“文件夹里看得到文件”替代用目标脚本的真实验收。

### 故障 3：打包日志中中文路径乱码

PyInstaller 日志将“项目”显示为乱码，但实际模块分析、文件收集、EXE 启动和安装都成功。这是控制台显示编码问题，不是文件路径已损坏。判定依据应该是产物能否启动和资源能否读取，而不是只看日志外观。

### 故障 4：清理命令被安全策略拒绝

一条同时创建、调用另一个 shell 和递归删除临时目录的命令被执行环境拒绝。这是对破坏性文件操作的保护，不是 E5 验证失败。后续改为新建唯一临时目录、先执行验证，不把跨 shell 调用和删除混在一条命令中。

## 6. 尚未解决

- 首版没有数字签名，Windows 可能显示未知发布者警告；
- 没有自动更新，覆盖安装是当前升级方式；
- 第三方许可证清单来自安装元数据，正式对外发布前仍应做人工法务复核；
- 打包了 CPU PyTorch/Transformers 使安装包约 166 MiB，仍有裁剪空间；
- 两位朋友的不同 Windows 环境、权限、网络和资料还未验证。

## 7. 手动练习

### 练习 1

为什么备份数据库不直接调用 `Copy-Item workspace.sqlite3`？

### 参考答案

SQLite 可能正在 WAL 模式下运行，最新事务未必全在主文件中。SQLite backup API 会从运行中数据库生成一致快照，比只复制一个主文件可靠。

### 练习 2

为什么恢复完成后不继续使用当前进程？

### 参考答案

数据库文件和快照目录已经替换，但材料服务、检索视图和后台任务可能仍保留恢复前的内存状态。强制重启能让所有组件从同一份恢复数据重建。

### 练习 3

为什么“安装成功”不是足够的发布验收？

### 参考答案

安装程序只证明文件被复制。还需验证 EXE 能启动、端口和 Web 资源正常、API 能用、数据能持久化、覆盖安装不丢数据、卸载策略符合说明，以及真实模型依赖能被打包环境加载。
