# 阶段 20：把 adapter 接进真实 RAG，定位“命中章节但没给到证据”

日期：2026-09-14。接续[QLoRA 训练与适配器评测](19-QLoRA训练与适配器评测.md)。本阶段不再只让模型回答人工给定的三条短证据，而是把实验 adapter 接到当前版本化 Obsidian 索引、hybrid 检索和完整块上下文。

## 1. 新增了什么功能

新增两个显式实验入口：

- `src/hf_qlora_client.py`：在一个 Python 进程内加载固定 4-bit 基座与 LoRA adapter，实现与现有 RAG 相同的 `chat(messages)` 最小接口；
- `src/adapter_rag.py`：复用 `rag.toml`、当前只读索引、hybrid/vector/BM25、上下文打包和引用校验，保存真实问题、上下文、检索轨迹、模型指标与源码哈希。

`RAGAnswerer` 新增可选的 `message_builder` 和 `enable_concept_repair`，默认值保持原行为。实验入口使用训练时的“问题/证据”协议，并关闭二次概念修复调用，因为本轮 SFT 没训练多轮 repair 对话。

这没有把 `hf-qlora` 加入 `rag.toml` 的默认 provider，也没有修改 `runtime`/HTTP 默认模型。原因是阶段 19 已证明 adapter 存在部分证据过度作答回归。

## 2. 第一次真实知识库问题

问题：

```text
PagedAttention 是什么？它解决什么问题？
```

adapter 得到当前 hybrid 检索上下文后输出：

```text
结论：PagedAttention 是一种用于管理键值缓存的系统，通过像操作系统分页一样管理 KV Cache，减少碎片，从而解决键值缓存管理的效率问题。
依据：[S1][S2]
```

两条引用都来自本次上下文，且对应“系统级优化”和“推理框架”段落。该次运行：

| 指标 | 数值 |
|---|---:|
| 固定索引版本 | `20260912T062623795056Z-2d6e3a20` |
| prompt tokens | 1412 |
| generated tokens | 50 |
| 模型/adapter 加载 | 约 3.2～3.5 s |
| 生成 | 约 3.5 s |
| 生成阶段 PyTorch peak allocated | 约 1923 MiB |

训练样本总长约 191～211 tokens，而这里 prompt 为 1412 tokens。一次成功说明 adapter 能在更长真实上下文上工作，但单个样本不能证明长上下文泛化。

## 3. 风险问题：合法引用为什么仍不可靠

问题：

```text
PagedAttention 是什么？请给出它解决的问题、完整 CUDA Kernel 和逐行执行过程。
```

知识库只支持定义和显存碎片问题，没有完整 kernel 与逐行过程。按照训练契约，问题有多个要求且资料不完整，应该整题拒答。adapter 却输出了 PagedAttention 的局部定义：

```text
结论：PagedAttention 是一种优化的 attention kernel，它像操作系统分页一样管理 KV Cache，减少碎片。
依据：[S2]
```

引用校验显示“标签合法”，但这不代表回答合格：

- 没有回答 kernel 和逐行过程，也没有声明资料不足；
- “优化的 attention kernel”未必由所引段落完整支持；
- 用户的多项要求没有做证据覆盖检查。

最终可复查报告：

```text
data/generated/adapter_rag_20260914_202331_960546.json
```

报告中保存了实际上下文和源码哈希，继续位于 `.gitignore` 覆盖目录，因为它可能包含私人笔记正文。

## 4. 综合流程题先暴露了上下文故障

问题：

```text
一个基础 RAG 系统从用户问题到最终回答通常经历哪些步骤？
```

hybrid 检索 Top-1 已经是：

```text
第8章 记忆与检索 > 8.3.2 RAG 系统工作原理
```

原文明确写着：

```text
RAG 的基本流程可分为两阶段：
- 数据准备阶段（离线）：数据提取 → 文本分割 → 向量化；
- 应用查询阶段（在线）：提问 → 检索 → 注入 Prompt → 生成。
```

但第一次实际 prompt 只包含图片、引导句“基本流程可分为两阶段”，没有包含两条列表。模型随后从其他代码片段拼出“初始化管道、创建实例、检索、生成”。这说明：

```text
文件/章节召回正确
        ≠
关键证据进入上下文
        ≠
模型的每项陈述有据
```

## 5. 根因：Markdown 列表被拆成了三个竞争块

`markdown_blocks` 为了保留单条列表完整性，把下面内容分成三个 block：

1. `RAG 的基本流程可分为两阶段：`；
2. 第一条离线列表；
3. 第二条在线列表。

完整块上下文又在五个来源之间轮流分配 2200 字符预算。引导句含 `RAG/流程/阶段`，相关性较高，先被选中；具体列表与其他来源代码竞争剩余预算，最终被跳过。诊断显示 Top-1 有 5 个 blocks，只选 2 个、跳过 3 个。

这是结构语义问题，不是调大 top-k 能解决的问题。top-k 更大反而会让更多来源竞争预算。

## 6. 修复：短列表与冒号引导段组成语义单元

`src/evidence_context.py` 新增 `semantic_spans`：

1. 合并连续且没有空行隔开的列表项；
2. 若紧邻的上一段以中文/英文冒号结尾，将引导段与列表绑定；
3. 只对合并后不超过 800 字符的短列表这样处理；超长列表仍逐项处理，避免一个列表独占全部上下文；
4. 代码块、续片围栏和去重逻辑保持原规则。

修复后，同样的检索结果和 2200 字符预算中，Top-1 的引导句、两条步骤和核心思想全部进入上下文；另一个来源中的完整流程：

```text
用户问题 → 查询改写 → 检索 → 重排序 → 上下文压缩 → 生成 → 引用与校验
```

也被保留下来。Top-1 诊断从 `selected 2/5` 变为合并后的 `selected 3/3`。

这里有明确 trade-off：一个 700 字符列表会作为整体放入或整体跳过，可能不如逐条选择节省预算；超过 800 字符则回退到原逐项策略。800 是当前实现边界，不是普遍最优参数。

## 7. 修复上下文后，模型问题仍然存在

上下文修复后，adapter 输出：

```text
结论：一个基础 RAG 系统从用户问题到最终回答通常经历的数据准备阶段、应用查询阶段、多查询扩展阶段和生成阶段。
依据：[S1][S2][S3][S4]
```

它不再编造“初始化/创建管道实例”，说明更好的上下文确实改变了回答；但仍有问题：

- 没有按顺序给出提问、检索、注入、生成等步骤；
- 把可选的 Multi-Query Expansion 当成基础必经阶段；
- 引用了并不都直接支持这条压缩结论的来源。

最终报告：

```text
data/generated/adapter_rag_20260914_202300_060544.json
```

这说明上下文工程和微调各自解决不同问题。证据缺失时模型不可能可靠回答；证据完整后，短格式合成 SFT 仍不保证长列表综合能力。

## 8. 实验报告现在记录什么

每次 `src.adapter_rag` 会把以下内容写到新的时间戳 JSON：

- adapter config/weights 的字节数与 SHA256；
- 索引版本和 manifest SHA256；
- `rag.toml` 普通参数与配置 SHA256；
- 训练时 system contract 的来源与 SHA256；
- 问题、真实上下文、来源、检索轨迹和打包诊断；
- 回答、引用标签合法性、生成耗时/token/显存；
- answer、adapter client、证据打包与 hybrid 检索源码 SHA256。

最初报告只记录了 adapter/client/answer 源码，遗漏 `evidence_context.py`；上下文修复后才意识到这会让两次不同打包逻辑看起来像同一实验。最终 schema 已补齐直接影响结果的证据打包与检索源码哈希。

## 9. 运行方式

```powershell
Set-Location -LiteralPath '<项目目录>'

.\.venv\Scripts\python.exe -X utf8 -m src.adapter_rag `
  "PagedAttention 是什么？它解决什么问题？" `
  --adapter data/generated/qlora_runs/20260914_200637_007529/best_adapter

# 只检查实际上下文，不加载生成模型
.\.venv\Scripts\python.exe -X utf8 -m src.explain_context `
  "一个基础 RAG 系统从用户问题到最终回答通常经历哪些步骤？" `
  --chunks-file data/generated/index_store/versions/20260912T062623795056Z-2d6e3a20/chunks.json `
  --method hybrid --context-policy blocks
```

每次 CLI 都重新加载模型，适合可复查实验，不适合日常交互。若下一步做常驻服务，应在启动时加载一次，并分别测冷启动、首题和热题。

## 10. 还没有解决的常见问题

- 引用验证只检查标签是否合法，不做逐陈述 entailment；
- 没有通用方法判断多项问题是否每项都有证据；
- adapter 仍会在部分证据时过度作答；
- 综合列表输出与训练的两行短答案格式不一致；
- 当前上下文预算按字符，生成模型实际限制按 token；
- 单次 CLI 重复加载 1.5B 和 E5，没有流式输出、取消或请求队列；
- 新入口是实验功能，没有加入 HTTP 服务或默认配置。

## 11. 练习与参考答案

### 练习 1

为什么检索 Recall@5 命中正确来源，回答仍可能错误？

参考答案：候选来源还要经过块选择和预算打包；正确句子可能被省略。即使句子进入 prompt，模型也可能忽略、误组合或无依据补全。Recall、context evidence 和 grounded generation 是三个层级。

### 练习 2

为什么“回答引用的 S1 存在”不等于“回答有依据”？

参考答案：标签存在只排除虚构编号。S1 可能与结论主题相关但不蕴含具体陈述；回答也可能遗漏用户其他要求。更强检查需要把陈述拆开，对每条做证据支持判断。

### 练习 3

为什么把连续列表作为整体既有好处又有代价？

参考答案：好处是保留列表的完整语义和引导关系，避免只看到标题；代价是整体更大，预算不足时可能一条都放不下。因此实现只合并不超过 800 字符的短列表，长列表仍逐项竞争预算。

### 练习 4

上下文修复后答案仍不完整，是否说明修复无效？

参考答案：无效和不充分不同。修复后错误从“根据代码编造初始化步骤”变成“错误概括已有流程并加入可选 MQE”，说明输入证据改善确实影响结果；剩余问题属于模型/训练目标和证据引用选择，不能要求一个上下文修复解决全部层级。
