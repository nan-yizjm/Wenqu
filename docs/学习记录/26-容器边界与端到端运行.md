# 阶段 26：容器构建边界、可移植索引与端到端运行

日期：2026-09-14。接续[阶段 25](25-阶段耗时与轻量监控.md)。本阶段不是把所有本机能力塞进一个镜像，而是先建立最小可解释基线：Linux 容器运行 RAG 服务和 CPU E5，生成仍调用宿主机 Ollama。QLoRA/CUDA adapter 保持独立实验，不假装一个 CPU 镜像已经解决 GPU 容器兼容性。

## 1. 容器边界

镜像内只有：

```text
Python 3.12
torch 2.13.0+cpu
sentence-transformers 6.0.0
FastAPI/Uvicorn 及传递依赖
RAG 服务与索引必需源码
容器专用非敏感配置
```

明确不进入镜像：

- `.env`、API Key 和本机 `rag.toml`；
- Obsidian Vault、chunks、向量索引和生成报告；
- Qwen/adapter 权重；
- 训练、QLoRA、tiny decoder 与实验 probe 源码；
- Git 历史、虚拟环境、测试与学习记录。

Vault 运行时只读挂载到 `/data/vault`；容器专属索引挂载到 `/data/index_store`；Hugging Face 缓存挂载到 `/cache/huggingface`。Compose 只发布：

```text
宿主机 127.0.0.1:8000 → 容器 8000
```

即使容器内部监听 `0.0.0.0`，也没有把服务发布到所有宿主机网卡。

## 2. 为什么不是直接复制 Windows 索引

版本 manifest 不只记录 chunks 和向量，还记录构建时 Vault 的绝对路径。Windows 索引是：

```text
C:\Users\...\Obsidian Vault\...\大模型
```

容器看到的是：

```text
/data/vault
```

运行时会校验 manifest，直接挂旧索引会拒绝启动。这不是多余限制：它防止服务悄悄用错语料目录。当前做法是在容器内对同一只读 Vault 构建独立版本，而不是篡改旧 manifest 冒充兼容。

最终容器索引：

```text
version: 20260914T144339967912Z-fbba2cc4
documents: 56
chunks: 911
encoded_chunks: 911
elapsed: 30.262 s（CPU）
host directory size: 3,286,956 bytes
```

原 Windows 索引和 current 指针没有改动。

## 3. 监听地址与信任 Host 不是一件事

首次容器配置写 `host='0.0.0.0'`，立即被 `Settings` 拒绝，因为原安全策略只允许 loopback。如果简单把 0.0.0.0 加入日常配置选项，用户可能在 Windows 直接启动时无意开放局域网。

修复将两个概念拆开：

- 配置仍为 `host='127.0.0.1'`，用于客户端 Host/Origin 约束；
- `src.serve --bind-host 0.0.0.0` 只覆盖 socket 监听地址；
- 只有 Dockerfile 明确使用这个覆盖；
- Compose 端口继续绑定宿主机 127.0.0.1。

容器网络需要监听所有容器接口，外部暴露范围则由端口发布决定。一个 `host` 参数同时承担两种语义很容易造成安全误配。

## 4. 模型缓存必须是显式步骤

索引代码固定 E5 revision，并默认 `local_files_only=True`。这保证日常运行不会偷偷下载或升级模型，但意味着一个空容器缓存不能直接 build。

新增 `rag-model-cache` 工具服务和 `src.container_prepare`：

```text
prepare_cache：用户明确运行时才联网准备固定 revision
offline_check：只读现有缓存，缺失就失败
```

本次没有重新下载 E5；把宿主机现有 Hugging Face 缓存只读挂入镜像后，Linux 容器离线核对通过：

```text
model: intfloat/multilingual-e5-small
revision: 614241f622f53c4eeff9890bdc4f31cfecc418b3
tokenizer: XLMRobertaTokenizer
dimension: 384
max_seq_length: 512
```

第一次实现调用旧的 `get_sentence_embedding_dimension()`，sentence-transformers 6.0 给出 FutureWarning；改用 `get_embedding_dimension()` 后消除警告。

## 5. Docker 环境和首轮构建失败

初始盘点：Docker CLI 29.1.5 已安装，context 为 `desktop-linux`，但 Docker Desktop/WSL2 均停止，Server 不可用。静态 Compose 仍可展开，但不能因此宣称镜像已构建。显式启动 Docker Desktop 后：

```text
Docker Desktop 4.58.0
Linux engine 29.1.5
WSL2 kernel 6.6.87.2
Buildx 0.30.1
```

BuildKit `--check` 无警告。第一次真实 build 在 CPU PyTorch wheel 下载到 176.9/191.8 MB 时失败：

```text
ReadTimeoutError: download-r2.pytorch.org
```

版本解析已经成功，失败点是传输停顿超过 pip 默认读取超时。Dockerfile 增加：

```text
PIP_DEFAULT_TIMEOUT=300
PIP_RETRIES=8
```

第二次成功下载并安装。期间另一份小 metadata 曾被远端主动断开，pip 自动重试恢复，说明重试设置确实覆盖了短暂网络故障。没有为“让构建绿”而换掉固定 torch 版本。

## 6. 两次镜像内容收敛

首个成功镜像可运行，但内容审计发现两类无关文件。

第一类：`src/__pycache__/*.cpython-314.pyc`。它们来自 Windows 主机的 Python 3.14 检查，进入的是 Python 3.12 镜像，不会加载却污染构建。原 `.dockerignore` 的 `__pycache__` 模式不够明确，改为：

```text
**/__pycache__/
**/*.pyc
**/*.pyo
**/*.pyd
```

第二类：`COPY src ./src` 同时带入训练、adapter、tiny decoder 和 probe。它们不含权重，但扩大运行面。通过 AST 相对 import 依赖盘点，从 `serve` 和 `index_store` 递归得到 19 个服务模块；Dockerfile 改为逐文件 COPY，另外加入显式缓存准备模块。

最终镜像：

```text
id: sha256:eee4fef388c9e8dd0a4f1f9cf09998d33f55d7f5938c5bff13e1bd80e5d9e319
size: 420,594,906 bytes
user: rag (uid 10001，非 root)
files under /app: 24
torch: 2.13.0+cpu
cuda: false
pip check: no broken requirements
```

最终镜像不存在 `.env`、`/app/data`、pyc、训练代码或 adapter 代码。构建 history 也只有公开基础镜像参数、依赖版本和 COPY 清单，没有密钥。

## 7. 静态预检的两个误判

预检报告会验证 Compose 展开、COPY 范围、忽略规则、loopback 端口、只读 Vault、环境变量和挂载目标，并单独报告 Docker daemon 是否可用。

首份失败报告：

```text
data/generated/container_preflight_20260914_214214_103240.json
```

当时错误要求 `.env.container.example` 必须重新加入 Docker 构建上下文。实际它只需要被 Git 跟踪，供宿主机 Compose 读取；镜像完全不需要它。修正为“所有 container env 文件都不进入镜像”。

最终预检：13 项全部通过：

```text
data/generated/container_preflight_20260914_225016_279790.json
```

这说明测试规则也需要语义审核；越严格不等于越正确。

## 8. 端到端服务中的三个问题

服务启动后，首次 Docker healthcheck 在应用加载 E5 前连接被拒绝，之后按 `start_period + retries` 自动恢复为 healthy。冷启动期间的首次失败不是容器崩溃；若没有 start period，编排器可能把正常冷启动误判为故障并反复重启。

真实问答首次返回正确答案和 S1 来源，但客户端看到 `retrieval_method=null`。原因不是容器序列化，而是普通 `RAGRuntime` 响应遗漏该字段；adapter 路径已有。补上 `result.retrieval_method`、重建并重启后为 `hybrid`。

第一份运行探针又把 Python 基础镜像自带的 `GPG_KEY` 识别成应用秘密：它实际上是 Python 发布包签名公钥指纹。失败报告：

```text
data/generated/container_runtime_probe_20260914_224622_031808.json
```

修复不再按任意名称中的 `KEY` 判断，而是提取应用前缀 `OLLAMA_ / DEEPSEEK_ / RAG_`，要求当前集合严格等于：

```text
OLLAMA_BASE_URL
OLLAMA_MODEL
```

最终运行探针 11/11：

```text
data/generated/container_runtime_probe_20260914_224650_445524.json
```

## 10. 运行与停止

详细命令见 [container/README](../../container/README.md)。顺序是：

```text
显式准备/离线核对 E5 缓存
→ 在只读 Vault 上构建容器专属索引
→ 启动 rag-service
→ 检查 ready/index/answer/metrics
→ docker compose down（不加 -v）
```

本次服务容器和 Compose 网络已删除，索引与镜像保留以便复现。没有执行 `down -v`、prune 或删除用户缓存。

## 11. 当前限制与下一步

- 镜像只支持 CPU E5 + 宿主 Ollama，不包含 GPU adapter；
- 依赖固定到版本，但还没有 hash-locked requirements 或 SBOM/漏洞扫描；
- 基础镜像使用 immutable digest 解析结果，但 Dockerfile 输入仍写 tag，后续可显式锁 digest；
- 索引首次构建依赖同 revision E5 缓存，空环境需用户主动下载；
- Docker Desktop 到宿主 Ollama 的连通性依赖 `host.docker.internal` 和本机防火墙；
- `/v1/metrics` 仍是进程内窗口，容器重启清零；
- 容器服务仍无认证，不应把端口发布到 0.0.0.0 或公网；
- 没有测试 Linux/NVIDIA Container Toolkit 下的 4-bit bitsandbytes 与 RTX 5060；
- 容器镜像保留在本机，没有推送 registry，也没有把私人索引制成 image/volume 导出。

下一阶段不急着做 Kubernetes。更有价值的是供应链和运行契约：生成机器可读 build manifest/SBOM 摘要，检查基础镜像/依赖/源码哈希；再做备份与恢复演练，确认索引可以重建而不是只会复制缓存。

## 12. 练习与参考答案

### 练习 1

为什么容器内部监听 0.0.0.0，不代表宿主机一定向局域网开放？

参考答案：容器监听范围和宿主机端口发布是两层。这里 Compose 明确发布 `127.0.0.1:8000:8000`，外部只到宿主 loopback；若改成 `0.0.0.0:8000` 才会扩大宿主暴露面。

### 练习 2

为什么不直接修改 Windows manifest 的 `vault_dir` 为 `/data/vault`？

参考答案：这会伪造构建来源，破坏版本审计。容器内重建能重新扫描只读源、编码并生成与实际路径一致的新 manifest。

### 练习 3

`.gitignore` 和 `.dockerignore` 分别保护什么？

参考答案：前者决定 Git 跟踪/提交范围，后者决定发送给 Docker builder 的构建上下文。文件可以需要被 Git 跟踪、却完全不需要进入镜像，例如容器环境示例。

### 练习 4

为什么只看 `docker build` 成功不够？

参考答案：成功镜像仍可能包含 `.env`、缓存、错误平台 pyc、训练代码或以 root 运行。还需检查文件清单、history、Config.User、依赖、端口、挂载和真实启动。

### 练习 5

healthcheck 第一次 connection refused 是否表示应该立刻重启容器？

参考答案：不一定。模型和索引冷加载需要时间；start period 内的失败应容忍。超过预期冷启动窗口且连续失败，才更像真实故障。

### 练习 6

为什么当前没有把 QLoRA adapter 一起装进镜像？

参考答案：它需要 CUDA 版 PyTorch、bitsandbytes、NVIDIA Container Toolkit、合适驱动和权重挂载，资源与兼容性都不同。先完成 CPU 检索 + 宿主生成的可验证基线，比声称一个未经实测的 GPU 镜像更可靠。
