# 阶段 24：单 GPU 有界队列、背压与排队断线

日期：2026-09-14。接续[阶段 23](23-真实Token预算与证据阶梯.md)。前一阶段已经限制单次请求的 prompt，但服务仍只有两种并发状态：GPU 空闲时接受，忙时立即返回 429。这个策略安全，却没有给短暂突发留下等待空间；反过来，若简单建立无限队列，请求和连接又可能无限堆积。

本阶段实现一个默认关闭的有界 FIFO：仍然只有 1 个模型执行席位，额外允许有限数量的请求等待。目标不是把 8 GB 单卡变成高并发服务，而是学习排队、背压、超时、客户端断开和资源所有权之间的关系。

## 1. 为什么“开一个线程池队列”不够

当前 QLoRA 生成占用同一张 GPU。让多个生成线程同时进入模型可能引起显存峰值、吞吐抖动或底层线程安全问题。因此容量的含义被明确写成：

```text
系统容量 = 1 个 active 执行席位 + max_waiting 个等待席位
```

`max_waiting=2` 时，第 1 个请求执行，第 2、3 个请求等待，第 4 个请求立即得到 `429 queue_full`。队列有限，才会形成真正的背压：上游必须等待、重试或放弃，而不是把压力隐藏在进程内存中。

不能直接依赖 `ThreadPoolExecutor` 自带的工作队列，因为它默认没有这里需要的业务语义：

- 无法向调用者报告初始排队位置和等待耗时；
- 很难在尚未执行时按 HTTP 断线精确删除某个任务；
- 无法区分“GPU 忙且未启用队列”和“队列已经满”；
- 无法独立统计排队超时、排队取消和成功准入；
- 任务提交到执行器后，取消 `Future` 不一定能取消已经开始的 Python/模型工作。

所以服务在执行器之前增加了一个显式 scheduler。

## 2. Ticket 状态与所有权

每个请求先取得一个 `Ticket`。关键状态是：

```text
new
 ├─ GPU 空闲 ───────────────→ admitted ─→ executing ─→ released
 ├─ 有等待容量 ─→ waiting ──→ admitted ─→ executing ─→ released
 │                         ├─ queue timeout ─→ timeout
 │                         └─ client disconnect ─→ cancelled
 └─ 未启用等待/队列已满 ────→ rejected
```

状态变更和 FIFO 双端队列都受同一把 `state_lock` 保护。执行锁仍只表示唯一模型席位。当前执行结束时，scheduler 在锁内完成三件事：释放当前 active、取出队首、立刻把执行锁交给队首。这样不会出现新请求插队到老请求前面的窗口。

这里最重要的概念是资源所有权：只有当前 `active` ticket 可以提交模型任务，也只有它可以释放执行席位。若错误 ticket 释放，会直接抛错，而不是悄悄把并发保护破坏掉。

## 3. HTTP 语义

新增配置：

```toml
max_queue_size = 0
queue_wait_timeout = 15
```

默认 `max_queue_size=0`，保持历史行为：模型忙时立即 `429 busy`。实验时可运行：

```powershell
.\.venv\Scripts\python.exe -m src.serve_adapter `
  --adapter .\data\generated\qlora_runs\20260914_200637_007529\best_adapter `
  --max-prompt-tokens 2048 `
  --max-new-tokens 160 `
  --queue-size 2 `
  --queue-wait-timeout 20
```

几种失败被有意分开：

| 情况 | HTTP | error | 含义 |
|---|---:|---|---|
| 默认模式下 GPU 正忙 | 429 | `busy` | 没有等待容量 |
| 等待队列已满 | 429 | `queue_full` | 背压立即生效 |
| 入队后等待超过上限 | 503 | `queue_wait_timeout` | 服务暂时无法在承诺时间内处理 |
| 入队后客户端断开 | 服务日志 408 | `client_disconnected_while_queued` | ticket 被删除，不应执行模型 |

429/503 会带短 `Retry-After`。成功结果增加：

```json
{
  "admission": {
    "queued": true,
    "initial_position": 2,
    "queue_wait_ms": 8833.46
  }
}
```

`initial_position` 是入队瞬间的位置，不是持续变化的实时排名；否则每次前序退出都要向连接推送状态。`queue_wait_ms` 只测等待执行席位的时间，不含检索和生成。

`/health/ready` 与 `/v1/index` 暴露 scheduler 快照：当前是否忙、等待数、容量、累计准入、拒绝、排队超时和取消数。它们是进程生命周期内的诊断计数，不是持久化业务指标。

## 4. 第一轮真实实验：断开的请求仍偷偷执行

第一轮失败报告保留在：

```text
data/generated/adapter_queue_probe_20260914_211751_643352.json
```

当时的真实现象：

- 明确建立一个排队请求，看到 `waiting=1` 后关闭 TCP 连接；
- 代码通过轮询 `request.is_disconnected()` 检查断线；
- 探针一度看到 `waiting=0`，误以为请求已被删除；
- 最终三个可见请求的模型执行序号却是 `1、3、4`，而不是 `1、2、3`；
- scheduler 的 `admitted_total=4`；
- 后两个可见请求分别等待约 6.1 秒和 9.7 秒。

序号缺口证明被放弃的请求不是“统计显示问题”，而是真的取得席位并执行了一次完整 RAG。单元测试能证明 ticket 删除逻辑正确，但没有证明 ASGI 层一定及时把 TCP FIN 变成 `is_disconnected()` 的真值。

探针本身也有一个观测错误：首次只以 `waiting==0` 判断删除成功。等待项也可能因为被错误准入而从队列消失。修复后必须同时满足：

```text
busy == true
waiting == 0
admitted_total == 1
cancelled_waiting_total == 1
```

这说明可观测条件应描述业务不变量，而不是只盯一个表面数字。

## 5. 原因和修复

排队协程现在同时等待两个事件：

```text
线程侧 ticket.event：排到队首或排队超时
ASGI request.receive()：收到 http.disconnect
```

用 `asyncio.wait(..., FIRST_COMPLETED)` 竞争。断线先到时，在 scheduler 锁内取消 ticket，再唤醒等待线程；准入先到时，取消断线监听并继续执行。若两者几乎同时到达，取消已经 admitted 但尚未执行的 ticket 也会释放席位并移交队首。

这里改用持续等待 `request.receive()`，而不是间歇轮询断线状态。真实 TCP 复验中，放弃请求在约 19 ms 后记录为 408，累计 `cancelled_waiting_total=1`，没有进入模型。

## 6. 最终真实 GPU 实验

最终报告：

```text
data/generated/adapter_queue_probe_20260914_212137_793617.json
```

固定环境：Qwen2.5-1.5B + 本轮 QLoRA adapter、911 chunks、hybrid 检索、2048 prompt token 上限、160 最大生成 tokens、1 active + 2 waiting。

| 请求 | 结果 | 初始位置 | 排队等待 | 客户端总耗时 |
|---|---:|---:|---:|---:|
| first | 200 | 0 | 0.01 ms | 4629.95 ms |
| abandoned | 客户端主动断开 | 1 | 约 19 ms 内移除 | 不执行模型 |
| second | 200 | 1 | 4539.24 ms | 8862.47 ms |
| third | 200 | 2 | 8833.46 ms | 13573.49 ms |
| fourth | 429 `queue_full` | 无 | 不入队 | 15.95 ms |

8 项检查全部通过：断线等待者被移除、达到队列容量、队满立即拒绝、三个请求完成、位置为 0/1/2、模型执行序号为 1/2/3、等待时间递增、最终 scheduler 空闲。

最终计数：

```json
{
  "busy": false,
  "waiting": 0,
  "max_waiting": 2,
  "admitted_total": 3,
  "rejected_total": 1,
  "queue_timeout_total": 0,
  "cancelled_waiting_total": 1,
  "cancelled_after_admission_total": 0
}
```

等待耗时近似累加前序生成时长，正符合单 GPU 串行执行，而不是“开队列后吞吐自动提高”。队列改善的是突发流量的接纳和公平性，不能提升模型本身每秒生成 token 数。

## 7. 自动检查覆盖了什么

服务级测试保留默认 429 行为，并增加：

- 1 个等待位时，排队超时返回 503 且 ticket 被移除；
- 直接构造三个 ticket，验证前两个依次准入、第三个 queue full；
- 取消队首等待者后，它永远不会在 active 释放时被准入；
- 运行任务结束后才移交唯一执行席位。

真实 `src.adapter_queue_probe` 则补上单元测试无法证明的部分：真实 HTTP 连接、真实 ASGI 断线事件、真实 GPU 生成、真实请求序号和最终清理。

复现命令：先按第 3 节启动服务，再在另一终端运行：

```powershell
.\.venv\Scripts\python.exe -m src.adapter_queue_probe
```

## 8. 当前限制与下一步

- 队列存在内存中，进程重启会丢失等待请求；这对 localhost 实验可接受，不是可靠消息队列；
- 只有 FIFO，没有租户公平、优先级、配额或动态预计等待时间；
- 每个等待者仍占用一个打开的 HTTP 连接；队列应保持很小；
- 普通非流式请求开始模型生成后，客户端断开仍不能中止一次整体 `chat()`；流式本地 adapter 已能模型级取消；
- 流式 producer 的 Python 文本队列目前没有单独容量上限，慢客户端场景仍值得检查；
- 进程计数不会跨重启聚合，也没有 p50/p95 等窗口统计；
- 429 重试由调用方负责，当前没有幂等键；只读问答风险较低，但未来工具执行不能照搬；
- 本阶段没有引入 Redis、Celery 或数据库，因为当前目标是理解调度和取消语义，而不是部署分布式任务系统。

下一阶段优先补结构化阶段耗时和轻量请求统计：把排队、检索、上下文打包、生成、收尾拆开，避免只看一个总耗时。之后再做容器化与启动检查。

## 9. 练习与参考答案

### 练习 1

`max_queue_size=2` 是否表示最多同时运行两个模型请求？

参考答案：不是。它表示最多两个等待者，仍只有一个 active 模型请求，所以系统最多暂存三个请求。

### 练习 2

为什么队列满使用 429，而排队超时使用 503？

参考答案：队满表示当前请求因服务的显式容量策略没有被接受；排队超时表示请求曾被接受等待，但服务暂时无法在等待承诺内提供执行资源。二者都可重试，但诊断原因不同。

### 练习 3

为什么 `waiting` 从 1 变成 0 不能证明断线请求已取消？

参考答案：它也可能已从 waiting 转为 admitted。还要同时检查准入累计数没有增加、取消累计数增加，并用模型请求序号确认没有发生隐藏执行。

### 练习 4

有了 FIFO 队列，模型吞吐为什么没有提高？

参考答案：同一时刻仍只有一个模型执行。队列只决定请求等待与拒绝的次序；吞吐由模型、输入输出长度、GPU 和生成实现决定。

### 练习 5

为什么普通 HTTP 请求超时或断开后，不一定能停止正在执行的模型？

参考答案：HTTP 协程结束和后台推理函数结束是两层事件。若生成 API 是一次阻塞调用，取消等待它的 Future 不会自动中断 CUDA/模型工作；必须在逐 token 生成层传播停止信号，阶段 22 的 streamer 与 stopping criteria 才做到了这一点。
