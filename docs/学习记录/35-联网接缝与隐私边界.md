# 35：联网接缝——把"数据不出机器"写成可执行的边界

> 2026-09-18 ｜ 对应 `docs/新功能实施计划-2026-09-18.md` 的 P2

**这一轮做了什么**：把联网补充做成一条接缝，并把四条隐私承诺变成测试与接口规则。

**这一轮刻意没做什么**：**没有接任何真实搜索后端**。所以交付的是"分层 + 边界 + 降级"，不是"能搜到东西"——这一阶段的验收也按这个口径写，不拿检索质量充数。

**这一轮的顺序与上一轮相反**：测试先写、先跑红，再写实现（P1 的教训见学习记录 34 §五.7）。

## 二、遇到什么问题

### 问题 1：我自己的"禁网"守卫把测试框架掐死了

第一版守卫直接把 `socket.socket.connect` 换成抛异常的桩。3 项测试立刻挂在：

```
File "asyncio\proactor_events.py", line 786, in _make_self_pipe
    self._ssock, self._csock = socket.socketpair()
```

asyncio 的事件循环自己要建一个**回环 self-pipe**，那是 `socketpair()` → 本地 `connect`，被我一起禁掉了。

**改法**：不按"用没用 socket"判，按**目标地址**判——"数据不出机器"的准确含义就是"不连本机以外的地址"，回环通信不算出网。三层一起堵：`getaddrinfo`（任何真实请求的第一步是解析域名）、`create_connection`（urllib / requests / http.client 的入口）、`connect`/`connect_ex`（兜底）。

> **教训**：断言"没有网络"时，把本机回环也一起禁掉是过头的，而过头的方法会先坏在无关的地方（这里是事件循环），而不是坏在被测行为上。守卫要贴着承诺的字面意思写："不出机器"，不是"不用套接字"。

### 问题 2：把"没有后端"说成"没搜到"，等于替产品瞒事

出厂状态没有搜索后端。这时开关打开，`search()` 会返回空列表——**这与"搜了但没结果"在数据上完全一样**，如果只按结果判，界面只能显示"本次没有网络结果"，用户会读成"今天没什么可网的"。

**改法**：协议里加 `configured` 字段。没有凭据、没配自建实例的后端应当报 `false`，产品据此上报 `unconfigured`，界面说"联网已开启，但还没有配置搜索后端，本次没有发出任何网络请求"。

这也让"未配置密钥的 Tavily"和"没有后端"能被区分开——它们是两件事。

### 问题 3：前端测试与"答完后重取会话"赛跑

ChatPage 在答完后 350ms 会重新拉一次会话。我的测试桩在重取时返回**空消息列表**，于是断言有时通过、有时找不到元素——同一份代码跑两次结果不同。

**改法**：重取的桩返回同一条消息（id 与流式事件里的一致）。**这类间歇性失败的根因通常不是被断言的行为有 bug，而是测试夹具没有把组件的真实生命周期走完。**

### 问题 4：断言写错了，看起来像实现坏了

两条新测试报 `Unable to find an element with the text: 答案 [S1]。`。原因是答案里的 `[S1]` 会被 `AnswerMarkdown` 渲染成引用元素，文本节点是断开的；另一条断言"网络层名会出现"失败，是因为**只有一个层时不显示层名**（P1 定的规矩）。

两条都是**断言错**，不是实现错。改法：用来源卡片的标题等消息落地；测层名时给"笔记 + 网络"两个层。

> **教训**：测试失败时先分清"实现错"和"断言错"。特别是断言 UI 文本时，得知道那段文本有没有被渲染管道改写过。

## 三、为什么这样处理

**为什么接口规则比界面文案更可靠？**
"首次开启必须显式告知"如果只是设置页的一段文字，它会随着改版被挪走、被折叠、被跳过。所以后端**拒绝**在没有 `web_disclosure_acknowledged` 时打开 `web_enabled`（422 `web_disclosure_required`）。这条规则有测试，也在真服务上用 HTTP 验过。界面里"未确认前开关不跳到开启"是配套：否则用户点保存会撞上 422，而他并不知道自己在确认什么。

**为什么"只发查询词"要写进测试？**
这是产品"数据不出机器"主张在联网这一侧的边界。测试拿被检索到的片段原文去反查提供者的实参，必须不在里面。**只断言"提供者收到了查询"是不够的——那不能证明它没同时收到别的。**

**为什么 `empty`（搜了但没结果）不显示提示？**
那是真实结果，不是故障。每轮都提示等于噪音，噪音会把真正的告警（`failed` / `unconfigured`）淹掉。

**为什么失败不拒绝服务，但要落事件？**
与记忆同一个取舍：联网是辅助通道，它坏了不该让用户连自己的笔记都问不了。但**降级必须显式**——失败写 `app_events` 并在回答旁边标出"本次未能联网"，不允许静默成"看起来就像没开联网"。

**为什么这一轮不加本地缓存表？**
原计划里写了"本地缓存"。但缓存键的规范化与 TTL 策略取决于后端（关键词怎么归一、新闻与常青内容的过期时间不一样），现在加表就是加一份**没有任何写入方的 schema**。等接了真实后端、能拿真实请求跑出命中率与过期行为，再加表。**P2 因此没有数据库迁移。**

**为什么网络来源的面板要分"发布时间"和"抓取时间"？**
这一层的整个价值是时效。"一篇 2023 年的论文，2026 年才被搜到"——两者差很远，混成一个"时间"会让用户以为这条事实是今天成立的。拿不到发布时间就写"发布时间未知"，不编。

## 五、还没解决什么

1. **没有真实搜索后端**。`NullSearchProvider.configured` 是 false，所以即使开关打开也一个请求都不发——这是当前出厂行为的**如实描述**，不是缺陷掩盖。
2. ~~**联网状态没有入库**。`failed` / `unconfigured` 只存在前端组件的内存里，翻回旧的回答看不到当时有没有联网失败。要存就得给 `messages` 加列（v9），为一个提示条加一列经不起追问——但这是一个已知的口径缺口。~~ **已补（2026-09-18）：** DB v10 = `messages.web_state_json`，见 `docs/学习记录/39-联网状态入库.md`。当时的顾虑"为一个提示条加列经不起追问"被反过来证伪了——追问下来发现 `failed` / `unconfigured` 正是**唯一需要它说话**的两种状态，而它们只活了几秒；旧行留 `NULL`、不补成 `off`，所以这一列没有替任何历史编结论。
3. **缓存、正文抽取、时效判定都还没做**。`SearchResult` 里留了 `published_at` / `fetched_at`，冲突归因（笔记与网络说的是两回事时怎么呈现）也还没动，那是 `技术打磨路线` 里"证据归因内核"的正题。
4. **`configured` 依赖接入方自觉**。协议要求后端如实上报；产品不（也无法）验证一个自称 `configured=True` 的实现是否真的会出网。测试能固定产品这一侧，固定不了第三方。
5. **关键词之外的发往内容没有单独测试**。目前"只发 `query`"是把整个实参记为一次调用再整体比对；如果将来后端协议变成"查询 + 选项对象"，需要把断言拆到字段级。
6. **`heading_repeat` 默认 1 → 0 仍待拍板**（与 P1 相同，未动）。
7. **便携版与安装包仍未重打**，`dist/` 里还是 0.2.1 的前端；本阶段的界面验收是对**源码运行 + 新构建前端**做的，结论只对这个组合成立。
