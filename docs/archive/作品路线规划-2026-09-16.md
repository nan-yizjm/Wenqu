# 作品路线规划：四条功能方向重排

> 2026-09-16 ｜ **前提已变更**：用户确认这是**作品**，不是产品
> 本文取代 `docs/archive/功能方向评估-2026-09-16.md` 中"按产品护城河排序"的那部分结论

---

## 一、前提变了，评价标准跟着变

| 维度 | 产品视角（作废） | **作品视角（生效）** |
|---|---|---|
| 核心问题 | 有没有护城河 / 能不能赢 | **能不能证明我的能力** |
| "别人已经做了" | 致命（说明没空位） | **不成立**（你不是要赢，是要证明你会建） |
| 功能数量 | 越多越像样 | **不是加分项**——堆功能是套壳调 API 的常见症状 |
| 最值钱的东西 | 差异化 | **可验证的证据 + 能讲清楚的设计决策** |
| 最大风险 | 打不过竞品 | **烂尾 / 摊子铺太大 / 每个都浅** |

> **一句话**：作品里，"我也做了个 RAG 助手"是淘宝款；"我有一套能跑出数字的检索评测，还报告了负结果"是稀缺品。

---

## 二、先把你真正的王牌拿出来

**不是功能，是评测集。** 这一点在作品视角下比在产品视角下更值钱。

大多数人的作品长这样：搭个 RAG → 接个大模型 → 截图聊天框 → 完。
你手里有：

| 资产 | 为什么在作品里稀缺 |
|---|---|
| `src/evaluate_product_retrieval.py` + 双口径判定 | 能跑出**数量化指标**（Source Recall@1/@5/@8、MRR），面试官能自己复现 |
| 消融实验记录 | Multi-Query 实测 0 改善 4 退化 → 退回默认；重排实测负结果 → `rerank=false` |
| **负结果** | 敢报告"我这个方案退化了"是**研究诚信**的标志，比全是好消息可信得多 |
| 159 项离线测试 / 7 版 DB 迁移 / 原子落盘 / CSS token 门禁 | 工程素养的硬证据，不是嘴上说的 |
| 42 篇 docs + 33 篇学习记录 | **文档体系本身就是作品的一部分**——多数人没有 |

**结论：功能是装饰，评测集是骨骼。做功能的任何时候都不能削弱这条线。**

## 三、建议的主线叙事（作品必须一句话讲清）

> **"一个全本地、引用可溯源、检索质量可量化的 Obsidian 知识助手——每个回答和每份产出都能点回原始笔记。"**

这条叙事的好处：
- 把已有资产（评测集 + 引用溯源）放主线，新功能当支撑
- 有**可量化的证据**（不是"我觉得好用"）
- 有**明确的技术取舍故事**（负结果也是故事）

四条新方向在叙事里的位置：

| 方向 | 在这个叙事里扮演什么 |
|---|---|
| MCP 联网补充 | "我懂 agent 工具调用，还处理了证据分层" |
| Studio 式产出 | "我能把检索结果变成落回笔记的可用产物" |
| 记忆系统 | "我懂状态管理与上下文工程" |
| 多模态 | "我碰过硬骨头" |

## 四、作品视角下的四条重排

排序依据变成：**能展示什么能力 ÷ 成本**。

| 方向 | 能展示的能力 | 作品加分 | 成本 | 建议 |
|---|---|---|---|---|
| **MCP / API 联网补充** | Agent 工具调用、协议实现、**证据分层设计** | **高** | 中 | ✅ **优先做** |
| **Studio 式产出（挑可视化的）** | 完整产品链路、结构化输出、前端渲染 | **高**（演示效果最好） | 中 | ✅ **做** |
| **记忆系统（最小版）** | 状态管理、数据生命周期、可删可查 | 中高 | 中 | ✅ 做，但要克制 |
| **多模态** | 多媒体管线（硬骨头） | 中 | **高** | ◐ 只做信息图，音频/视频缓 |

### 逐条的作品视角说明

**① MCP 联网 —— 作品首选**
- MCP 是 2026 最热的技术话题，接上就是加分项
- 代码量适中，一次能讲清"协议接入 + 工具设计 + 证据分层"
- **设计决策值得写**：为什么默认关、为什么库内和网上要分层标注、断网怎么降级——这些是能体现判断力的地方
- 关键：**别只说"能联网"，要说清"为什么联网之后还守住本地承诺"**

**② Studio 式产出 —— 作品的演示担当**
- 作品需要"看得见的东西"。产出物（思维导图、信息图、学习指南、PPTX）截图效果最好
- 但要挑：**优先做可视化强的**（思维导图 / 信息图 / PPTX），闪卡/测验放最后（插件已饱和，且演示效果平）
- **你的差异点仍然是"落回 vault + 回链源笔记"**——这不是护城河，但是在作品里是**一句能讲清的设计主张**

**③ 记忆系统 —— 讲架构用，但要克制**
- 作品视角下，Mem0/Zep 式的时序图谱**反而可以讲**了（展示架构能力）
- 但我仍建议**只做到"会话 + 偏好"两级**：投入产出比最高，且能讲清"为什么不上全自动事实抽取"（这本身就是一个有判断力的取舍）
- 三条硬约束不变：落 `%LOCALAPPDATA%`、可查可删、默认关

**④ 多模态 —— 性价比最低，最后做**
- 作品里"我做了视频生成"确实唬人，但成本极高，容易挤掉别的
- **信息图（HTML/SVG → PNG）** 仍是最优解：不需要生成模型，演示效果好
- 音频（TTS）可选；**视频建议直接放弃**（重资产，收益不成比例）

## 五、排期建议（按时间预算分档）

| 时间预算 | 做什么 | 交付形态 |
|---|---|---|
| **6 周内** | MCP 联网 + Studio 产出（只做思维导图 + 学习指南两个） | 一个能演示的完整链路 + README + 评测集报告 |
| **约 3 个月** | 上面 + 记忆最小版 + 信息图 + PPTX | 上面 + 架构文档 + 演示视频 |
| **半年以上** | 全上（含音频） | 但要警惕：**大概率烂尾**，不建议 |

**排期的一条纪律**：**每完成一条，就把它写进 README 和一篇 docs**。你的作品的价值有一半在文档里——别做完不写。

## 六、作品独有的两个风险

1. **烂尾（最大风险）**：一个人 + 四条大方向 = 大概率每条都做一半。"做了一半"在作品里等于"没做"——面试官看不到完整链路。
   **对策：宁可 2 条做透，不要 4 条做浅。**
2. **变成"套壳调 API"**：如果每个功能都是"调大模型 → 返回结果"，那展示不出能力。
   **对策：每条功能都必须能讲清一个非平凡的设计决策**（联网的证据分层、记忆的可删可查、产出的回链、评测的双口径判定）。

## 七、待你拍板

1. **时间预算**：大概多少？（决定做 2 条还是 4 条，见第五节）
2. **受众**：给面试官 / 导师 / 开源社区看？（我目前**假设是面试官或评审**，默认他们会看 README + 想跑一遍评测）
3. **要不要为作品补一个"入口"**：目前产品是本地 Windows 应用，评审未必愿意装。是否需要一个能在线体验的 Demo（哪怕功能受限）？
4. **评测集要不要再加强**：作品视角下它是最值钱的东西——考虑加一个"新用户能照着跑出数字"的一页说明。
