# 新功能实施计划：Studio 产出 / 记忆接口 / 联网补充 / 图片产出

> 2026-09-18 ｜ 依据：使用者提出四项新功能；本文给出落点、接缝、分阶段与需拍板项
> 前置阅读：`功能方向评估-2026-09-16.md`（四条方向的原始评估）、`技术打磨路线-2026-09-16.md`（当前生效的排序）

## 〇、先把一个矛盾摆出来

`作品路线规划` §六把"摊子铺太大"列为**最大风险**：四条大方向一起做，大概率每条都做一半，而"做了一半等于没做"。它给的对策是"宁可 2 条做透"。

但**换一种切分方式，这个矛盾就化解了**——因为使用者自己（经 `技术打磨路线` §二确认）已经发现：

> **记忆层与联网补充是同一个技术内核**："当同一件事有多个互相冲突的说法时，如何归因、判定时效、并按来源分层。"

所以四条功能实际是 **3 个模块、4 张脸**：

| 使用者的诉求 | 实际归属 | 说明 |
| --- | --- | --- |
| 2. 留出记忆系统的接口 | ↓ **来源分层内核** | 记忆是"来源分层"的一个 provider |
| 3. 联网补充 | ↓ **来源分层内核** | 联网是同一个内核的另一个 provider |
| 1. Studio 式产出 | **产出模块** | 独立模块，消费检索结果 |
| 4. 图片模态产出 | **产出模块的一个导出器** | 是 Studio 的一种产出形态，不是独立体系 |

**结论：按 3 个模块 + 4 个阶段串行推进，而不是四条并行。** 这样每个阶段的产出都是完整的，避免了"每条做一半"。

## 一、可以直接复用的家底（已核实，带位置）

做之前先认领现成的接缝，避免重复造轮子：

| 现成资产 | 位置 | 四个功能怎么用 |
| --- | --- | --- |
| `ChatClient` 协议（`chat` + `stream_chat`） | `src/llm.py:127`，实现有 `OllamaClient`/`DeepSeekClient` | Studio 产出与联网摘要都复用它，不新增大模型客户端 |

| 导出通道 | `organize.py:266/274` 的 `export_markdown/export_collection` → `paths.exports`，配 `safe_filename` + `.tmp` 原子落盘 | Studio 产出复用同一目录与命名/落盘约定 |
| 后台作业机制 | `materials.py` 的 `_job/_advance_job/_finish_job` + `/api/v1/import-jobs` | Studio 生成是长任务，走作业而不是阻塞请求 |
| SSE 流式 | `/api/v1/conversations/{id}/messages/stream` | 产出过程的进度推送复用同一套 |
| 凭据托管 | `credentials.py`（keyring，`has_deepseek()`） | 联网的搜索 key 进这里，**绝不写文件**（沿用现有约定） |
| 设置白名单与校验 | `app.py` 的 `ALLOWED_SETTINGS`/`SettingsPatch`（带 `ge/le` 校验） | 三个新功能的开关都走这里，默认全关 |
| 诊断上报 | `/api/v1/system/diagnostics` | 记忆条数、联网开关、最近一次联网是否发生，都在这报 |
| DB 迁移 | `database.py`，**已到第 8 版**（v8 = `message_sources` 与 `favorite_sources` 的 `origin` 列） | 新字段继续走 v9，沿用"迁移前自动备份 + 单事务逐条执行" |
| 前端壳 | `App.tsx:8` 的 `type Page = 'library' \| 'chat' \| 'favorites' \| 'settings'` + `nav` 数组 | Studio 加一个页面就是在联合类型与 nav 里各加一项 |
| 本机浏览器无头渲染 | Edge / Chrome 的 `--headless=new --screenshot=`，纯 `subprocess` | **图片产出用这个**（原写的"复用 CDP 通道"在冻结版不成立，更正见本节末） |

最后一条是本计划里最省钱的发现：图片产出不需要图像生成模型，也不需要 puppeteer/playwright——本机浏览器自带无头截图能力。

> **更正（2026-09-18，动手后补）**：这一格原写"图片产出直接复用 `scripts/ui_acceptance.cjs` 的 CDP 通道"。**那是错的**：该脚本靠 Node 驱动，而 `product.spec` 不打包 Node，`dist/ObsidianRAG/` 里只有 `ObsidianRAG.exe` + `_internal`，用户机器也不保证有 Node——冻结版里这条路根本走不通。改用本机 Edge/Chrome 的 `--headless=new --screenshot=`（纯 stdlib）。本机两者都在标准路径，已核实。

## 二、接缝设计

### 接缝 1：来源分层（记忆与联网的公共底座）

```
message_sources.origin ∈ { note, memory, web }
```

- `note`：现有检索结果，**默认唯一存在的层**，所以不开新功能时行为与现在完全一致
- `memory`：记忆 provider 召回的事实
- `web`：联网检索到的网页片段
- 回答生成时：各层上下文按"笔记 > 记忆 > 网络"的优先级拼进 prompt，并要求模型在答案里标出依据来自哪一层
- 前端 `SourcePanel.tsx` 按层分组显示，**冲突时并排呈现**（"你的笔记说 X，网上说 Y"）——这正是大厂没做的那个空位

**为什么先做它**：它是第 2、3 条的共同前提；先有它，后面两条各自只是"接一个 provider"。

### 接缝 2：`MemoryProvider` 协议（第 2 条的全部内容就是它）

```python
class MemoryItem(TypedDict):
    id: str
    text: str          # 一句可引用的事实
    origin: str        # 来自哪次对话/笔记
    created_at: str
    expires_at: str | None   # 时效：过期即不再召回

class MemoryProvider(Protocol):
    def recall(self, query: str, limit: int) -> list[MemoryItem]: ...
    def remember(self, items: list[MemoryItem]) -> None: ...
    def forget(self, item_id: str) -> None: ...
    def list(self, limit: int) -> list[MemoryItem]: ...
```

四条硬约束（沿用你既有的约定，不新开先例）：

1. **默认关**：`settings.memory_enabled = false`
2. **落 `%LOCALAPPDATA%`**，与安装目录/仓库隔离
3. **可查可删**：`list`/`forget` 必须对外有接口，界面上能看到、能删
4. **不自动写外部**：记忆只在本地，永不上传

**先只交付协议 + 一个 no-op 实现**（`NullMemoryProvider`：`recall` 返回空、`remember` 什么都不做）。这样：
- 第 2 条"留出接口"当场完成，且**零行为变化**
- 你后续接 Mem0 / Zep / 自研时，只需实现这一个协议，不用改产品其他代码

> 注意：接口形状取决于你要接什么。`recall/remember/forget/list` 是按"最小可用"设计的；若你打算接 Mem0/Zep 这类"事实抽取 + 冲突消解"的系统，接口需要额外留出**冲突与时效**的表达（`expires_at` 已预留，冲突消解可能需要 `supersedes_id`）。见 §五 待拍板第 3 条。

### 接缝 3：`WebAugmenter`（第 3 条）

分工：**联网本身不难（接个搜索 API），难在证据归因**——所以本模块的重心放在"来源分层 + 冲突呈现 + 隐私边界"，不是"能搜到东西"。

隐私边界（必须显式设计，因为产品卖点是"全本地、数据不出机器"）：

| 约束 | 做法 |
| --- | --- |
| 默认关 | `settings.web_enabled = false` |
| 开启时明确告知 | 首次开启弹一次说明："开启后，**查询关键词**会离开本机；笔记正文不会外发" |
| 只发查询词 | 请求体只含检索关键词，**绝不发送笔记正文或片段** |
| 本地缓存 | 搜索结果落本地，可查可删，避免重复请求 |
| 断网降级 | 请求失败/超时 → 只在笔记层作答，并在界面上标注"本次未能联网"，不静默失败 |
| 可插拔后端 | 搜索后端做成 provider，不写死某一家（见 §五 待拍板第 2 条） |

### 接缝 4：产出模块（第 1、4 条）

**统一抽象**：一次产出 = 一个作业（复用 `_job` 机制）+ 一个导出器。

| 产出形态 | 实现 | 依赖 | 优先级 |
| --- | --- | --- | --- |
| 学习指南 / 摘要（Markdown） | LLM 结构化输出 + 模板 | 无新依赖 | P3 先做 |
| 思维导图 | **Mermaid** 文本（前端已有 markdown 渲染） | 无新依赖 | P3 做 |
| 信息图（PNG） | HTML/SVG 模板 → 无头 Chrome 截图 | 复用 `ui_acceptance.cjs` 的 CDP 通道 | P4 做 |
| PPTX | `python-pptx` 套模板 | 新依赖 | **本计划不做** |

**每份产出必须带"回链"**：产出物里的每个论断都要能点回源片段。这不是护城河，但是一句能讲清的设计主张，也是你文档里点名的差异点——**产出物里不许出现没有来源的句子**。

## 三、分阶段（串行，每阶段一个可验证产出）

### P1：接缝与开关（第 2 条交付）— 约 1–2 天

> **状态：已交付（2026-09-18）**。实测 220 项 Python / 71 项 vitest / 17 项真实界面验收全过。过程与三个真实缺陷见 `docs/学习记录/34-记忆接缝与来源分层.md`。

- DB 第 8 版迁移：`message_sources.origin`（默认 `note`）
- `MemoryProvider` 协议 + `NullMemoryProvider` + 设置开关（默认关）+ 诊断上报
- 来源分层的数据结构与前端分组显示（此时只有 `note` 一层，界面不变）
- **可验证产出**：测试全过；**问答与检索行为逐字段不变**（有测试固定）；`origin` 已入库

**交付时比原计划多出的两处**（都是计划漏掉的，不是临时加戏）：

1. **`favorite_sources` 也要 `origin`**。原计划只写了 `message_sources`。漏掉的话，收藏页的来源会丢掉层标识——用户恰恰是为了核对依据才收藏的。抓到它的是既有的"收藏与实时消息形状必须一致"契约测试。同一条来源有三个存储点（`message_sources`、`favorite_sources`、流事件 payload），漏一个就有一处静默降级。
2. **前端不能按 `document_id` 取记忆来源的原文**。记忆条目的 `document_id` 是占位串，照它去请求 `/versions/memory/source` 必然 404。面板改为按 `origin` 分流：只有笔记层才取快照。

### P2：联网补充（第 3 条）— 约 3–5 天

> **状态：已交付（2026-09-18）**。实测 231 项 Python / 80 项 vitest / 24 项真实界面验收全过；后端**没有迁移**（v8 的 `origin` 列本来就接受 `'web'`）。过程见 `docs/学习记录/35-联网接缝与隐私边界.md`。
>
> **交付口径按待拍板第 2 条**：本期只交"分层 + 隐私边界 + 降级"，**不是"能搜到东西"**——没有接任何真实搜索后端。因此原计划的第 ② 项验收（"一组笔记与网络冲突样本上的分层与冲突呈现正确率"）**本轮无法成立**（没有真实结果可评），改为交付四条可执行的隐私边界测试；冲突归因留到接入后端之后。

- `src/product/web.py`：`SearchProvider`（`name` / **`configured`** / `search`）+ `SearchResult` + `NullSearchProvider`
- `WebAugmenter` 的落点即 `chat.py:_web_results()`：返回 `(来源, 状态)`，状态随 `retrieval` 事件到界面
- 来源分层真正用起来：`web` 层入 `message_sources`，SourcePanel 显示外链与两个时间（发布／抓取）
- 隐私开关 + **首次开启告知做成接口规则**（422 `web_disclosure_required`）、断网降级并显式标注
- **可验证产出**：① 关闭时零网络请求（**堵在 socket 层**证明，不只是断言提供者没被调用）；② 只发查询词（拿被检索到的片段原文反查实参）；③ 没有后端时打开也不出网且如实报 `unconfigured`；④ 后端失败时问答仍完成、事件落库、界面标注"本次未能联网"
- **没做**：本地缓存。缓存键的规范化与 TTL 取决于后端，现在加表就是加一份没有写入方的 schema

### P3：Studio 产出（第 1 条）— 约 3–5 天

- 作业化产出流程 + 产出物入库与列表
- 两种产出：学习指南（Markdown）、思维导图（Mermaid）
- 回链：产出物内每个论断指向源片段
- **可验证产出**：从一份笔记生成产出物，抽查 N 个论断，**回链命中率**（数字，不是感觉）

### P4：图片产出（第 4 条）— 约 2–3 天

- 信息图 HTML/SVG 模板（先用固定模板，不做自由生成）
- 无头 Chrome 截图 → PNG 落 `paths.exports`
- **可验证产出**：一张可下载的信息图 + 渲染耗时记录 + 无头 Chrome 不可用时的降级行为

### 明确不做（本计划范围外）

- PPTX、视频、音频（成本高、与"可溯源"主张无关；PPTX 待 P4 之后再议）
- 全自动记忆事实抽取（研究级问题，正是 `技术打磨路线` §五 点名的"深水区"）
- 图像生成模型（信息图已能满足"图片模态产出"，且无需新模型）

## 四、风险

| 风险 | 对策 |
| --- | --- |
| 四条一起做 → 每条做一半 | 按 3 模块 / 4 阶段**串行**，每阶段有可验证产出；一次只开一个阶段 |
| 联网破坏"全本地"卖点 | 默认关 + 只发查询词 + 首次开启显式告知 + 断网降级并标注；这几条要写成测试 |
